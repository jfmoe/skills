# 审查代码精简

把一个宽泛的"找找能精简的地方"请求，转化为少数几个论证充分的候选——删除、收编或降级现有的表面积。本 skill 是指导原则，不是检查清单：跟着代码走，保持判断力，宁要少数几个论证充分的候选，不要一堆站不住的猜测。

## 确立当前合同

在评判一个设计之前，先读适用的仓库指令、架构文档、现行决策记录、测试和公开文档。已被记录的接缝和有意保留的备选实现，在证据推翻其理由之前，一律视为有意为之。

一个精简方案必须指明：什么存在、谁拥有它、谁当前在消费它、它履行什么义务、改动后什么会消失。

## 强候选

一个强精简删除、收编或降级某个真实存在的东西，并有清晰证据表明当前设计的代价大于收益：

- 某个公共方法、事件、配置开关、注册表通知、辅助函数、包、持久事件或测试构件没有生产环境消费者。
- 测试或文档是唯一消费者，且它们钉死的行为并非承重。
- 两种表示映射同一个事实。
- 某个接缝有每个实现都必须支持、但没有消费者使用的方法。
- 某个包或模块只为测试、演示或支撑代码存在，还带来发布或依赖开销。
- 某个特性实现了没有产品负责人、没有当前消费者的投机性通用能力。
- 某个不变量、回滚路径、期望输出或特例测试只为保护一个未使用的 API 而存在。
- 某行未覆盖的代码或分支没有当前合同或生产消费者；覆盖率失败是删除的证据，不是要补测试的信号。
- 校验、回退或恶意输入测试保护的是在带类型的同进程接口下不可能出现的值，而不是真实的解析器、配置、模型或工具 JSON、持久文件、worker、进程或线上边界。
- 手写代码重新实现了有维护的依赖或平台内建能力，替换后能连同其专属测试一起删掉。
- 精简后的行为可以略有差异，但新行为仍然合理且更容易解释。

删一个笔误、跑一次未使用代码工具、报告"这看起来复杂"、或在没有消费者分析的情况下删除有意支持的备选实现，都不是强候选。

### 审计不变量伴生检查

不变量伴生检查只有在比较独立产生、可能发散的观察值时才有用。删除空的安装器和只检查服务存在性、插件元数据、固定示例、或调用它所声称验证的同一个变更操作所得结果的检查。每省略一处，要连同删除导出、构建入口、仅服务不变量的编译器引用或依赖、以及仅为伴生检查存在的测试，然后把原因记录到归属模块的文档或决策记录中。当伴生检查比较的是不同事件生产者、持久历史或独立可变数据时保留它，即使该模块同步校验输入。

## 广泛勘察

从最大的生产代码和生命周期表面开始，而不只是未使用符号的输出。跨接口、实现、配置、动态加载、运行时字符串、文档、测试、快照和脚本搜索。

对每一处防御性拷贝、冻结、校验器和回调捕获，说出值从哪里来、接下来归谁所有。同进程的带类型调用通常只是借用值；解析器、配置、队列、模型或工具 JSON、持久文件、worker、进程和线上解码器拥有或校验自己的数据。

对异步代码，画出所有权图，把每个哨兵、就绪 Promise、取消路径、释放器和状态标志映射到明确的所有者或状态迁移。多个机制镜像同一个存活性或结算事实，是合并为一个事务或生命周期控制器的候选。当分离的机制保护的是发布回滚、回调遏制、终局仲裁、worker 或进程所有权、或释放静默期时，保留它们。

## 随代码一起精简行文

把注释和文档视为需要维护的表面积。精简一个段落时，适用完整命题规则：枚举它承载的所有命题，每个仍然成立的命题都必须在精简后幸存。

- 删除复述代码、或解释归属他处行为的注释；保留必要的局部合同。
- 文档留在其归属层级；省略实现细节和罕见情形，除非它们改变一个需要维护的合同。

## 手写代码 vs 依赖

当引入依赖能删掉自有代码和测试时，它是一个正当的精简。

- 说出该依赖覆盖的确切手写表面。残留的语义差异要计入替换的代价。
- 检查维护状况、采用度、安全态势、许可证、平台支持和传递依赖足迹。受支持的运行时已提供该能力时，优先用平台内建。
- 权衡净删除量：实现加专属测试和文档，减去残留的胶水代码。
- 只是把同样复杂度挪了位置的包装层不算赢。
- 不要仅仅因为存在某个包就推翻一个已记录的架构决策；替代品必须胜过当前的理由。

## 证明或否决每个候选

下笔之前先对消费者分类：

- **生产：** 运行时代码、配置、加载器、公开 API 和已发布的入口路径。
- **非生产：** 测试、文档、决策记录、快照、生成的输出和注释。
- **待定：** 可能是产品冒烟或发布路径的示例和脚本；分类前先检查。

搜索确切的符号、事件、包名、配置键、方法和线上字符串，然后读完每一个实质调用点。静态未使用代码工具有助于发现，但不理解动态名字、公开接口、配置或产品入口路径。

现有测试描述行为；它们并不证明该行为仍然必需。当合同和消费者证据表明行为已过时，把行为和其专属测试一起改或删。不要为了让过时的测试保持绿灯而保留代码，也不要为了给死代码凑覆盖率而加测试。

出现以下情况时否决或降级候选：

- 存在生产调用方，且改动属于特性决策而非清理；
- 有现行合同或来之不易的防御性规则支持它，而新证据没有推翻那个理由；
- 删除带来无关的震荡，却没有减少公开 API 或必需行为；
- 想法正确，但太局部，不值得一份耐久的提案。

## 报告

对每个被接受的候选，提供：

- 当前所有者和受影响的表面；
- 生产、非生产和待定消费者的证据；
- 确切的删除、收编、降级或替换；
- 放弃的行为或能力；
- 对代码、测试、文档、依赖和运维的净影响；
- 风险和重新引入的条件；
- 可观察的验收标准，以及证明它们的窄化检查。

同时报告有代表性的被否决候选及其未达标的原因。不要编造候选数量。
