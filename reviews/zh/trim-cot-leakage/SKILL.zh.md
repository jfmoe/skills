# 修剪思维链泄露

思维链泄露是指其视角停留在创作会话而非仓库本身的行文：它引用只有该会话才能看到的产物，叙述变更而非陈述现状，或与一位已经离场的评审者争辩。当一个段落承载事实性子句时，修复手段绝不仅是删除——先把每个事实性子句重述为能立足于仓库当前状态的表述，再删除其周围的会话记录。不承载任何事实的段落，例如审查编号或控制流叙述，则直接整体删除。

完整命题规则：在删除一个段落之前，枚举它承载的所有命题；每个在仓库当前状态下仍然成立的命题都必须在修剪后幸存。本 skill 是指导原则，不是脚本。

## 唯一的判据

对每个可疑段落发问：**一个处于仓库当前状态的读者，在无法访问任何会话记录、评审线程或未提交草稿的情况下，能否解析其中每一个引用并核实每一条论断？** 如果不能，就从仓库的视角重述幸存的事实，并删除其余部分。如果能，它就不是泄露——无论听起来多么有历史感——但可解析性只达到本 skill 的门槛：在 README、文档和 JSDoc 这类面向当前状态的表面上，一个可解析的变更故事仍然是变更叙述，第 3 类会将其路由到它被认可的去处。

## 分类

1. **失效的设计会话引用** —— `(decision 7)`、`(audit C2)`、`design §4.7`、`plan §1.4`，`T4`、`W3`、`P-I` 之类的阶段标签，"the design ledger" 和 "(B ruling)"。如果该决策有已提交的归属者，按名称和路径引用它；否则删除该引用，并把其事实性子句重述为能独立成立的表述。
2. **栈与 PR 视角** —— "a later PR in this stack"、"this PR adds"、"the previous commit"。陈述已交付的机制或扩展点；被推迟的工作移到带有归属者的 TODO 标记或 issue 引用。
3. **变更叙述与版本印记** —— "used to"、"no longer"、"the old X"，以及 "v1"、"this cut"、"today"、"now" 这类与过去状态形成对照的指示性印记。陈述当前行为。一个已修复的回归应变成现在时的反事实表述，如 "without X, Y happens"，绝不能是仓库历史，如 "used to Y"。
4. **评审过程编排** —— "Rejected in review"、"the reviewer confirmed"、"v5 of this note" 这类草稿序数，以及轮次归属。把幸存的决策和理由保留为平实的事实；删除谁在何时说过它。
5. **面向评审者的辩解** —— "the cast is safe—it simply…"、"this is correct because…"。一条为自己正确性辩护的注释是在对评审者说话，而不是对维护者。陈述使代码安全的不变式；如果代码本身已经体现，就删除这条注释。
6. **复述与推导记录** —— "first we X, then we Y" 这类控制流叙述、测试过程复述，以及对显而易见分支的证明。删除它们；只保留非显而易见的契约或不变式。
7. **含糊措辞与规划残留** —— "probably fine for now"、"should be enough"，以及没有归属者的推迟表述。提升为带归属者的 TODO/FIXME，或重述出真实的界限；删除含糊措辞。
8. **创作语言混入** —— 在语言 otherwise 统一的行文中混入未翻译的工作语言片段或私人草稿分隔符。翻译或删除它们。

## 什么不是泄露

无辅助的引用排查在两个方向上都会失败：删掉耐久的引用，又留下失效的引用。请按原文应用以下保留规则；[示例](references/examples.md)对每条做了校准：

- **Issue 引用** —— `#1470`、`TODO(name):` 和 "issue #N owns the follow-up" 在仓库当前状态下可解析；在任何表面都保留。
- **决策记录与事故记录内部的已合并 PR 和 issue 引用** —— 当这些文档类型本身就负责承载变更历史时，它们是被认可的证据。
- **抑制说明** —— linter 禁用理由、覆盖率忽略理由和空 catch 解释是必需的行文；理由有误时修正理由，绝不删除。
- **反事实现在时的回归钉** —— "without X, Y happens"、"a naive X would…"。
- **实测界限** —— "measured: 512 nests ≈ 0.15s" 这类为常量定标的表述；来源词 "measured" 是承重的。
- **运行时的新旧状态** —— "the old connection drains before the new one accepts" 描述的是运行时生命周期，不是仓库历史。
- **记录文档变更故事章节内的历史阶段名** —— "the first cut shipped X" 在那里可能是安全的；但 "this cut" 这类指示性印记永远不安全。
- **按设计在仓库之外可解析的外部引用** —— 标准章节和具名设计产物。章节号问题针对的是未提交的内部草稿，而不是可解析的外部标准或已提交的文档。
- **项目语气和体裁形式** —— 作为项目语气的 "we" 和 "Alternatives considered" 章节本身不构成泄露。

## 工作流程

1. 明确划定范围和适用的受保护路径。不要编辑 vendor 或第三方源码，也不要编辑冻结的记录。记录型 fixture 和快照是衍生物，不是行文目标：改动其归属的源码或场景，并且仅当一次获授权的行为变更需要新证据时才重新生成它们。
2. 先只读审查。运行[召回探针组](references/recall-batteries.md)，在信任每个探针的输出之前，先用一个已知正例和一个险些误报的负例对它校准，然后对每个命中做语义判断。探针组是探针，不是定义。还要在手中不拿任何模式的情况下通读范围内最密集的行文。
3. 修复时归属者优先：生成的输出 → 追踪每一个消费者，修复源码或生成器，然后重新生成所有衍生物；复制的 API 文本 → 归属的声明处；成对文档 → 两侧同时更新，逐字块按字节完全一致地复制进两侧；对模型或用户可见的字符串 → 只有在拿到来自归属快照或 e2e 场景的行为证据时才改动，否则保持原样并报告该推迟。
4. 在删除任何内容之前，按完整命题规则枚举该段落的命题，并检查[过度修正陷阱](references/examples.md#overcorrection-traps)。不要把义务翻转成背书，不要把假设提升为已交付行为，不要删除真实的事实，也不要丢弃来源信息。
5. 重新运行探针组，预期只剩被认可的保留项和校准材料。确认每个留存的引用都能在仓库当前状态下解析，并对每个被触及的表面运行相应检查。
6. 报告所检查的范围、修复内容、被认可的保留项、未解决的案例，以及实际运行过的检查。
