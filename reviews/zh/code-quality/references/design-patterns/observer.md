# 观察者 / 发布-订阅

## 意图

让一个对象（主体）在状态变化或事件发生时可以通知许多依赖者（观察者），而主体不知道它们是谁。它建立一种可以在运行时改变的一对多依赖。

## 它解决的问题

当系统的几个部分必须对某事发生做出反应——缓存必须失效、UI 必须刷新、审计日志必须记录——从源头到每个反应者的直接调用会把源头耦合到所有反应者。新增反应者就要改源头。观察者把这一切倒过来：反应者订阅，源头只发布。

## 结构与参与者

- **主体 / 发布者**：持有订阅列表并发出通知。
- **观察者 / 订阅者**：注册兴趣并处理通知。
- **事件**：描述发生了什么的数据载荷。

## Python 示例

在 Python 中，主体常是一个按事件类型键控的事件总线：

```python
class EventBus:
    def __init__(self) -> None:
        self._subscribers: dict[type[Event], list[Callable[[Event], None]]] = {}

    def subscribe(self, event_type: type[Event], handler: Callable[[Event], None]) -> None:
        self._subscribers.setdefault(event_type, []).append(handler)

    def publish(self, event: Event) -> None:
        for handler in list(self._subscribers.get(type(event), [])):
            handler(event)
```

## 需要显式决定的设计关注点

观察者实现正是在这些地方出错的。没有哪一条有唯一正确答案，但每一条都必须是深思熟虑的选择，而不是意外。

- **订阅者生命周期**：谁取消订阅、何时取消？活得比订阅者还久的订阅会泄漏内存并让死对象活着。考虑对处理器用 `weakref`，或交回一个显式的取消订阅句柄 / 使用上下文管理器。
- **错误传播**：如果一个处理器抛异常，后面的处理器还运行吗？吞掉错误会藏 bug；让错误传播会让一个坏订阅者破坏整个发布。决定并记录策略。一个常见选择是隔离每个处理器的错误、记录日志、然后继续。
- **顺序**：订阅者按注册顺序运行，还是顺序未定义？除非你保证顺序，否则别让调用方依赖它。
- **重入**：处理器能否在分发期间发布、订阅或取消订阅？在订阅列表的副本上迭代（如上所示）可避免迭代期间修改的 bug。
- **同步 vs 异步**：进程内同步通知最简单。对 `async` 处理器，你必须在顺序 `await` 与 `asyncio.gather` 之间选择，并决定如何处理阻塞或永不完成的处理器。

## 何时使用

- 多个独立的反应者必须响应一个事件，且反应者的集合会变化或源头不知道。
- 你想把领域动作与其副作用（邮件、指标、缓存）解耦。
- 关系确实是动态的一对多。

## 何时不使用

- 恰好有一个固定的反应者；直接调用它。事件总线只增加了间接、隐藏了控制流，没有解耦收益。
- 严格顺序和清晰的顺序工作流比解耦更重要；显式流水线可读性更好。
- 需要跨进程投递：进程内观察者不提供投递、重试或持久性保证。使用具有明确语义的真正消息系统（队列、broker）。

## 失败模式

- **隐藏的控制流**：一次 `publish` 触发一串谁也无法通过阅读调用点追踪的效应。
- **内存泄漏**：被遗忘的订阅永远持有引用。
- **意外的重入**：处理器在分发中途改变主体，破坏迭代。
- **静默失败**：被吞掉的异常意味着事件"发生了"，但它的效果从未发生。

## 与其他模式的关系

当事件被具体化为可排队或重放的对象时，观察者与 [command.md](./command.md) 重叠。中介者（mediator）式协调是相反的立场：中介者集中交互逻辑，而观察者把它分散。对于跨进程扇出，这个模式让位于消息 broker 基础设施，而不是内存中的总线。
