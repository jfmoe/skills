# 仓储（Repository）

仓储模式在持久化机制之上提供类似集合的接口，把领域逻辑与存储细节隔离。它在领域模型与数据映射层之间充当中介，提供 `get`、`add`、`remove` 之类的方法，以及返回领域对象的查询方法。

核心价值在于：领域代码通过一个干净的接口操作领域对象，而无需知道数据来自数据库、文件系统、API、缓存还是内存集合。这让领域逻辑无需真实基础设施即可测试，也允许更换存储技术而不修改业务规则。

## 结构

- **仓储接口**（Protocol 或 ABC）：定义类似集合的方法（`get_by_id`、`add`、`remove`、`list_by_criteria`）。
- **具体仓储**：用特定技术实现接口（SQLAlchemy 会话、裸 SQL、HTTP 客户端、文件系统）。
- **领域对象**：仓储返回的纯领域实体或聚合。
- **应用/服务层**：使用仓储接口，而非具体实现。

依赖方向向内流动：领域代码依赖仓储*接口*，具体实现依赖它所持久化的领域对象。这是应用于持久化的[依赖倒置](../design-principles/dependency-inversion.md)。

## 何时适合这个模式

- 领域逻辑足够复杂，把它与持久化隔离能提升清晰度和可测试性。
- 可能有多个存储后端（生产数据库、测试内存存储、从一个 ORM 迁移到另一个）。
- 应用遵循分层或六边形架构，有显式边界。
- 业务规则应能在没有数据库 fixture 的情况下测试。
- 团队受益于一致、可发现的数据访问 API。

## 何时不适合这个模式

- 应用是领域逻辑极少的薄 CRUD 层。在 ORM 之上再加仓储只增加间接，不减少复杂度。
- ORM 已经提供了足够干净的抽象（例如简单应用中的 Django Manager/QuerySet）。
- 永远只会用一种存储技术，且领域逻辑微不足道。
- 查询高度动态或分析型。仓储接口会变成复杂 SQL 之上的漏抽象：这种情况下，专门的查询服务或 CQRS 分离更合适。
- 项目是单一数据源的脚本或小工具。

## 常见实现问题

**接口膨胀。** 长出几十个查询方法的仓储会失去其抽象价值。让接口聚焦[领域](../design-principles/ddd.md)操作，而不是通用查询构建器。

**泄漏抽象。** 暴露 ORM 特有概念（会话、flush、惰性加载、查询构建器）的方法违背了这个模式的目的。返回完整加载的领域对象。如果调用方需要分页、过滤或排序，把这些设计成仓储参数，而不是泄漏出去的 ORM 查询链。

**事务边界。** 仓储通常不拥有事务。事务边界属于应用/服务层或[工作单元](./unit-of-work.md)。内部自行提交的仓储让人无法跨多个聚合协调写入。

**急切 vs 惰性加载。** 如果 ORM 惰性加载关联对象，在仓储边界之外访问它们可能失败或触发意外查询。在仓储边界上决定加载策略，使返回的对象对其预期用例是完整的。

**测试。** 为领域逻辑的单元测试提供内存实现。集成测试仍需真实数据库仓储来验证查询、约束和迁移。

## 与工作单元的关系

仓储通过类似集合的 API 处理单个聚合的持久化。[工作单元](./unit-of-work.md)处理跨多个仓储的事务一致性。它们互补：仓储提供集合接口，工作单元提供提交/回滚边界。两者一起让应用层同时控制*持久化什么*和*何时持久化*。

## 与外观的关系

仓储是持久化子系统之上一个面向领域的[外观](./facade.md)。差别在意图：外观为任何消费者简化复杂子系统；仓储专门在领域对象与存储之间充当中介。如果你的"仓储"其实只是简化复杂外部 API、而没有领域对象，Facade 可能是更合适的名字。
