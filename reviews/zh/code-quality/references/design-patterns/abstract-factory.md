# 抽象工厂

## 意图

创建必须配套使用的相关对象族，而不让调用方耦合到具体类。调用方选择一个工厂；它产出的一切都保证属于同一个匹配的集合。

## 它解决的问题

有些对象只有组合在一起才有意义。一个 S3 读取器配一个 S3 写入器；一个深色主题按钮配一个深色主题菜单；一个 Postgres 连接配一个 Postgres 方言和迁移运行器。如果调用方逐个组装这些部件，没有什么能阻止他们把 Postgres 读取器和 SQLite 写入器混在一起。抽象工厂把"族"变成选择的单元：选一次后端，它交回的每个产品都是一致的。

这是它的区别性约束。[factory.md](./factory.md) 回答"我该构建哪一个具体类？"抽象工厂回答"我该构建哪一整*套*类，使得它们彼此契合？"

## 结构与参与者

- **抽象工厂**：为族中每个产品声明创建方法（`make_reader`、`make_writer`）。
- **具体工厂**：每个族一个（`S3Storage`、`LocalStorage`），各自产出自己变体的产品。
- **抽象产品**：调用方依赖的接口（`Reader`、`Writer`）。
- **具体产品**：特定族的实现。

调用方持有一个抽象工厂并调用其创建方法；它从不指名具体产品。

## 何时使用

- 一整套产品必须一起切换：UI 工具包主题、数据库后端、云厂商客户端、传输栈。
- 多个对象必须共享同一配置、凭据或生命周期，混用变体就是 bug。
- 测试需要把整组依赖（一个假存储族）换成真实的。

## 何时不使用

- 只有一个产品，或只有一个族。那你只需要 [factory.md](./factory.md)，或一个普通构造函数。
- "族"约束不是真的；产品其实并不需要匹配。把它们分组只增加了仪式，没防住任何错误。
- 它悄悄长成了一个按请求构建任何东西的通用服务定位器，丢失了当初证明其正当性的族保证。

## 失败模式

- 为单一族建出工厂对象、抽象产品和具体产品树：纯粹的开销。
- 族边界模糊，工厂堆积无关的创建方法，变成上帝对象。
- 产品偷偷取用全局状态而不是工厂的共享配置，破坏了这个模式存在所要维护的一致性保证。

## Python 示例

一个 `Protocol` 加一个选择器函数通常就能表达整个模式，无需接口森林：

```python
class StorageBackend(Protocol):
    def make_reader(self) -> Reader: ...
    def make_writer(self) -> Writer: ...


def build_storage(profile: StorageProfile) -> StorageBackend:
    if profile.kind == "s3":
        return S3Storage(profile)
    return LocalStorage(profile)
```

其他惯用形态：

- **模块即工厂**：一个 `s3_backend` 模块和一个 `local_backend` 模块，各自暴露 `make_reader`/`make_writer`，在组合根里导入正确的那个来选择。
- **dataclass 档案**：把族的共享配置打包进一个冻结对象，传给每个产品。
- **组合根**：启动时组装一次匹配集合并注入，而不是散落工厂调用。

当工厂契约需要静态检查时，使用鸭子类型或 `Protocol`；两者都不需要名义继承。

## 与其他模式的关系

抽象工厂是把 [factory.md](./factory.md) 从单个产品放大到一个协调的族。当单个产品的构造复杂时，其产品常通过 [builder.md](./builder.md) 配置。工厂的选择常常与为整个子系统选择一个 [strategy.md](./strategy.md) 重合。当对象族还需要一个简化的组合入口点时，把它包在 [facade.md](./facade.md) 后面。
