# 状态模式（GoF）

GoF 状态模式通过委托给多态的状态对象，消除状态相关行为的条件逻辑。上下文（Context）持有对当前状态对象的引用。每个具体状态类实现同一个接口，提供该状态特有的行为。状态转换就是替换上下文的当前状态引用。

这是状态机行为的一种特定 OO 实现。它并不等同于一般意义上的状态机；许多状态机用更简单的表示更好：枚举加转换表、reducer 函数、`match`/`case`、或分发表。在决定状态模式是否比更简单的实现更有价值之前，总是先做[状态机建模](../programming-paradigms/state-machine.md)，定义状态、事件、转换、守卫和非法转换策略。

## 结构

- 上下文（Context）：维护对具体状态的引用；委托状态相关的请求。
- 状态（接口/Protocol）：定义状态相关行为的接口。
- 具体状态（ConcreteState）：实现特定状态的行为；可以通过替换上下文的状态引用来触发转换。

## 何时适合这个模式

- 每个状态有可观且不同的行为，而不只是不同的返回值或标志。
- 状态数量适中且相对稳定。
- 状态特有行为复杂到拆成类比平铺条件更可读。
- 新增状态可以不修改现有状态类（OCP 收益）。
- 状态对象需要访问上下文数据来执行其行为。

## 何时不适合这个模式

- 状态少、转换简单、行为差异小。转换表或 `match` 更清晰。
- 工作流主要关于转换许可和副作用，而不是多态行为。用转换表。
- 状态类退化成包着单个表达式的琐碎单方法包装器；间接成本超过清晰度收益。
- 状态数量快速增长或由数据驱动。基于表的方法扩展性更好。
- 状态转换需要在一处可审计。状态模式把转换散落在各个具体状态类里。

## 常见实现问题

**转换归属。** 谁决定下一个状态？如果每个具体状态各自决定，转换散落在各个类里、更难审计。如果上下文决定，模式可能退化成上下文里的条件判断。在给定的上下文边界内一致地选择一种做法。

**共享上下文数据。** 状态对象常需访问上下文数据。显式把上下文传给状态方法，或使用共享数据对象。避免通过全局状态或模块级变量的隐藏耦合。

**状态身份。** 状态对象是单例，还是携带每实例数据？无状态的状态对象可以安全共享；有状态的需要显式的生命周期管理：谁创建它们、何时丢弃。

**测试。** 用聚焦的单元测试独立测试每个状态类，然后在上下文层面测试转换。验证非法转换被拒绝，而不是被静默忽略。

## 区分状态与策略

[策略](./strategy.md)和状态都委托给多态对象，但它们变化的是不同的东西。策略变化的是*算法*。状态变化的是*生命周期阶段*。如果对象在其生命周期内不在策略之间切换，那是策略，不是状态。如果主体走过一系列阶段、行为随每个阶段改变，那是状态。

## 区分状态模式与状态机

状态模式是一种实现技术。状态机建模是一种设计技术。状态机可以实现为枚举加转换表、reducer、`match` 块、分发表、专用库，*或者* GoF 状态模式。只有当每个状态携带受益于多态分发的可观行为时，状态模式才物有所值。

如果你只需要追踪合法转换并在转换期间执行副作用，而不给每个状态丰富的行为接口，[转换表](../programming-paradigms/state-machine.md)更简单、也更容易审计。

[命令模式](./command.md)封装的是请求而非状态；当转换把命令排队以待稍后执行时，它与状态模式互补。
