# 命令（Command）

## 意图

把请求封装为对象，使请求可以被传递、存储、排队、记录、重放和撤销。发出请求的调用方与知道如何执行它的代码解耦。

## 它解决的问题

一次直接调用 `service.send_email(to, template, context)` 立即执行且不留痕迹。你无法把它放进队列、持久化留待以后、记入审计日志、崩溃后重放、或撤销它。当一个请求需要超越其调用瞬间的生命时，它必须变成数据。命令把"做这件事"变成一个你可以持有和检查的值。

## 结构与参与者

- **命令（Command）**：携带执行请求所需一切的对象：操作及其参数。
- **接收者（Receiver）**：知道如何完成工作的对象。
- **调用者（Invoker）**：持有并触发命令（队列、调度器、菜单、快捷键绑定）。
- **客户端**：创建命令并为其配置接收者。

经典形式中，命令暴露 `execute()`，有时还有 `undo()`。要点是调用者统一对待所有命令，而不知道每一个具体做什么。

## 何时使用

- **排队与调度**：放上任务队列、重试或稍后运行的任务。
- **撤销/重做**：每个动作是一个配有逆操作的命令；历史栈驱动撤销。
- **审计追踪**：每次状态变更都被记录为一条命令，用于合规或调试。
- **宏录制 / 重放**：捕获一串命令并重新运行。
- **解耦 UI 与动作**：菜单项、按钮和快捷键持有命令，而不是直接调用服务。

## 何时不使用（杀鸡用牛刀）

- 简单、立即的函数调用就够了，请求不需要存储、重放或撤销。把它包进命令类是纯粹的仪式。
- 命令没有稳定的 schema，因而实际上无法持久化或重放；那你付出构建成本却得不到任何收益。
- 你拿起命令对象去"解耦"只有一个调用方和一个接收者的代码。

## 失败模式

- **贫血命令加肥胖处理器**：逻辑迁移进处理器，直到命令成了字段袋、分发成了上帝函数。
- **不稳定的序列化**：持久化的命令在重构后无法反序列化，因为 schema 没有版本化。如果你持久化命令，把它们的形状当作契约对待。
- **漂移的撤销**：不能完美逆转 `execute()` 的 `undo()` 会静默地破坏状态。撤销的正确性需要显式测试。
- **构造中的隐藏副作用**：构建命令不应执行工作；只有调用者应触发它。

## Python 示例

当命令是要被排队、序列化或审计的数据时，冻结 dataclass 是天然的载体：

```python
@dataclass(frozen=True)
class SendEmail:
    to: EmailAddress
    template: str
    context: dict[str, object]
```

由独立的处理器（或一个按命令类型键控的 `dispatch` 映射）执行工作，使命令本身保持为普通、可序列化的记录。当命令不需要持久化、只携带行为时，一个普通函数或 `functools.partial` 本来就*是*命令：Python 的一等函数吸收了最简单的情形。

对于撤销，命令必须捕获足够的先前状态来逆转自身，或与 [unit-of-work.md](./unit-of-work.md) 或备忘录（memento）配对来快照状态。

## 与其他模式的关系

命令和 [strategy.md](./strategy.md) 都把行为包进对象，但策略参数化的是*如何*做（可互换的算法），而命令参数化的是*做*什么以及*何时*做。命令队列是 [observer.md](./observer.md) 事件处理的常见搭档，事件在其中变成待处理的命令。撤销常把命令与备忘录或 [unit-of-work.md](./unit-of-work.md) 结合。在 Python 中，把每个命令类与一个普通可调用对象放在天平上比较；只有对状态、序列化、排队、审计或撤销的需要才能证明这个对象的正当性。
