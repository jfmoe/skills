# 外观（Facade）

## 意图

为复杂子系统提供单一、简单的接口。外观定义一个更高层的入口点，让子系统更易使用，同时不妨碍需要更细控制的调用方直达底层部件。

## 它解决的问题

一个子系统会累积许多必须按正确顺序协调的类和步骤：取客户、从订单行创建发票、发布事件、更新台账。如果每个调用方都自己编排这些步骤，协调逻辑会被重复、调用代码会耦合到内部结构，而改变工作流就意味着编辑每一个调用点。外观给常见用例命名（"给这个订单开票"），并在一处拥有编排。

## 结构与参与者

- **外观（Facade）**：暴露一小组高层操作，委托给子系统对象，编排它们的交互顺序。
- **子系统类**：干真正的活；它们不知道外观的存在，仍然可以直接使用。

外观自身不增加任何新功能；它把现有部件组合成一个方便的表面。调用方依赖外观；外观依赖子系统。

## 何时使用

- 一个多步骤工作流或第三方 SDK 在好几个地方以相同方式使用，你想要一个有名字的入口点。
- 你想让调用方与子系统的内部结构解耦，使它能在稳定表面之后演化。
- 你在给系统分层，希望每层向上一层呈现最小接口。

## 何时有害

- **隐藏调用方真正需要的复杂度。** 如果调用方必须控制重试、分页、部分失败或事务边界，一个把这些抹平的外观会迫使调用方绕过它或 workaround 它。暴露调用方必须推理的东西。
- **浅外观。** 如果它只是把一个调用转发给一个子系统方法，它增加了一层和一个名字却没隐藏任何东西。成本（多一跳、多一个要翻的地方）超过收益。
- **上帝对象。** 一个增长到覆盖系统每个操作的外观会变成垃圾场，耦合无关的用例、积累对一切的依赖。

## 失败模式

- 外观在签名中泄漏子系统类型，于是调用方终究还是耦合到了内部，抽象成了幻觉。
- 错误处理把不同的子系统失败塌缩成一个不透明的异常，调用方无法恰当响应。
- 外观变成唯一允许的路径、挡住了正当的高级用法，而不是作为方便的默认、同时保留直接访问的可能。

## Python 示例

模块本身就是天然的外观：包的 `__init__.py` 配上精选的 `__all__`，暴露几个入口函数，而实现住在私有子模块里。

当用例共享状态或依赖时，客户端类很合适：

```python
class BillingClient:
    def __init__(self, customers, invoices, events) -> None:
        self._customers = customers
        self._invoices = invoices
        self._events = events

    async def invoice_order(self, order: Order) -> Invoice:
        customer = await self._customers.get(order.customer_id)
        invoice = await self._invoices.create(customer, order.lines)
        await self._events.publish(InvoiceCreated(invoice.id))
        return invoice
```

好的外观是一个*深模块*：在可观的内部复杂度之前放一个小接口。正是这种深度让它值得拥有；它隐藏的是真实的工作，而不只是几行代码。

## 与其他模式的关系

[adapter.md](./adapter.md) 改变接口以匹配调用方期望；外观在许多对象之上定义一个*全新的、更简单的*接口；适配器包装一个东西让它适配，外观包装许多东西让它们简化。外观常常挡在 [abstract-factory.md](./abstract-factory.md) 之前，或协调由工厂构建的对象。好的外观背后的"深模块"思想，与设计原则参考中的信息隐藏原则相连。对比中介者（Mediator）：它同样集中交互，但让被协调的对象通过它回话，而外观是单向的简化入口点。
