# 策略（Strategy）

## 意图

在稳定接口之后定义一族可互换的算法，使算法可以在配置时或运行时被选择和替换，而不改变使用它的代码。

## 它解决的问题

当单个操作有几个变体算法（排序、评分、定价、路由、重试、压缩的不同做法）时，把它们嵌进一个不断增长的 `if/elif` 块会把调用方耦合到每个变体，并让新增变体成为对共享代码的修改。策略隔离每个算法，使调用方只依赖"能给条目评分的东西"，而不是具体的评分规则。

## 结构与参与者

经典形式有一个持有**策略**接口引用的**上下文（context）**，以及实现该接口的**具体策略**。上下文把它工作中可变的部分委托给注入的策略。上下文拥有稳定的工作流；策略拥有变化的部分。

## 何时使用

- 今天就有多个真实算法，且调用方不应知道运行的是哪个。
- 算法必须可在运行时选择（用户选择、配置、A/B）或在测试中替换。
- 变化沿一条清晰的轴（"如何评分"），接口小且稳定。

## 何时不使用

- 只有一个算法，或一个 `if` 就覆盖两种情况。预防性的"策略化"为没有收益的东西加了接口。
- 策略接口宽到调用方必须组装一个复杂对象才能变化一个决策；抽象切错了。
- "策略"们实际差异在于*需要哪些*数据，而不只是*如何*计算；它们可能并不共享一个连贯的接口。

## 失败模式

- 一个方法、一个实现的 `Strategy` 类，而一个函数能用更少的仪式说同样的话。
- 过宽的接口迫使每个具体策略实现只有其中一个用到的方法。
- 策略选择散落在代码库各处，而不是在一处（工厂或分发表）解析，于是新增变体意味着搜寻每一个选择点。

## Python 示例

Python 函数是一等的，所以实现策略最简单的方式是接受函数参数。通常不需要策略类：

```python
def rank_items(items: list[Item], score: Callable[[Item], float]) -> list[Item]:
    return sorted(items, key=score, reverse=True)

def priority_score(item: Item) -> float:
    return item.priority

rank_by_priority = partial(rank_items, score=priority_score)
```

按重量粗略排序的形态：

- **普通函数或 `lambda`** 作为参数传入：最轻的策略。
- **闭包**：捕获少量稳定配置；或 `functools.partial`，把参数预绑定成更窄的可调用。
- **`Protocol` 或可调用对象**：当策略需要状态、多个相关方法、或一个记录意图的名字时。
- **`functools.singledispatch`**：当策略由输入的*类型*而非配置值选择时。
- **分发表 / `match`**：当选择依赖配置值或多个条件时。

## 与其他模式的关系

[factory.md](./factory.md) 常常*选择*用哪个策略。[command.md](./command.md) 结构相似（行为作为对象），但其意图是捕获请求以待稍后执行，而不是变化算法。[state.md](./state.md) 模式看起来像策略，但它的变体是响应事件而*自行*切换，而不是由调用方选择。`functools.singledispatch` 和模式匹配是最常吸收掉策略的 Python 机制。
