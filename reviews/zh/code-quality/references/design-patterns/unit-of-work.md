# 工作单元（Unit of Work）

工作单元模式维护一个受业务事务影响的对象列表，并协调在单个原子操作中把变更写入数据库。它追踪哪些对象是新的、被修改的或被删除的，并一起提交所有变更——或在任一步骤失败时全部回滚。

主要价值是事务一致性：必须同生共死的多个仓储操作由工作单元协调，而不是每个仓储各自提交。

## 结构

- **工作单元**（接口）：声明 `commit()`、`rollback()`，并提供对仓储的访问。
- **具体工作单元**：包装数据库会话/连接，追踪变更，实现提交/回滚。
- **仓储**：通过工作单元访问；在其事务作用域内操作。
- **应用/服务层**：创建工作单元，通过其仓储执行操作，然后提交或回滚。

## 何时适合这个模式

- 一个业务操作触及必须原子持久化的多个聚合。
- 应用有编排领域逻辑的显式服务层方法。
- 事务边界需要在应用层可见且可测试。
- 多个[仓储](./repository.md)共享会话/连接，它们的写入必须协调。
- 架构受益于把"什么变了"与"何时持久化"分开。

## 何时不适合这个模式

- 每个操作都是无跨聚合一致性需求的单实体 CRUD。ORM 会话或简单的 `with db.transaction():` 块就够了。
- 框架已经声明式地管理事务（例如简单情形下的 Django `@transaction.atomic`）。
- 应用以读为主，写协调极少。
- 跨多个服务的分布式事务：工作单元适用于单一数据库边界之内；跨服务一致性需要 saga 模式或最终一致性。
- 对简单应用而言，显式追踪变更的开销超过收益。

## 常见实现问题

**作用域。** 工作单元应恰好存活一个业务操作。在应用启动时创建一个并跨请求共享，会导致过期数据和并发 bug。在 Web 应用中按请求划定作用域；在 worker 中按任务划定。

**ORM 集成。** SQLAlchemy 之类的 ORM 内部已经实现了工作单元；Session 追踪脏对象并在提交时 flush。把 ORM 会话包进显式的工作单元类，是为了让边界在应用层可见且可测试，而不是重新实现变更追踪。如果 ORM 内建的会话管理对你的需求已经足够显式，额外的包装可能只是徒增仪式。

**嵌套事务。** 避免深层嵌套的工作单元。如果子操作需要独立的提交/回滚，显式使用保存点（savepoint），而不是嵌套工作单元。

**错误处理。** 任何异常路径都必须回滚。上下文管理器（`with uow:`）是天然契合，因为 `__exit__` 在有异常时会调用回滚。这也是[资源生命周期](../programming-paradigms/resource-lifecycle.md)模式的工作方式：获取与释放配对。

**测试。** 工作单元边界是天然的测试接缝。mock 或内存实现让服务层测试无需数据库即可验证编排行为。

## Python 示例

在 Python 中，工作单元天然呈现为上下文管理器的形式：

```python
with unit_of_work() as uow:
    order = uow.orders.get(order_id)
    order.confirm()
    uow.payments.add(payment)
    uow.commit()
```

如果在 `commit()` 之前发生异常，上下文管理器的 `__exit__` 会调用 `rollback()`。这让事务边界显式可见，并保证意外异常之后的清理。

## 与仓储的关系

[仓储](./repository.md)为单个聚合提供类似集合的 API。工作单元协调这些变更*何时*持久化。它们自然组合：工作单元拥有或提供对仓储的访问，工作单元内的所有仓储操作共享其事务作用域。另见 [DDD 聚合边界](../design-principles/ddd.md)，了解如何界定一个聚合。
