# 测试坏味道

测试套件本身就是第二个代码库，它会以自己特有的方式腐坏。下面列出的坏味道来自 Gerard Meszaros 的《xUnit Test Patterns》、Google 的测试指南以及 Kent Beck 的测试期望属性（test desiderata）。与它们所对应的[代码坏味道](../refactoring/code-smells.md)一样，每一条都是*值得调查的症状*，而不是判决。一个读起来略有重复的测试可能恰到好处；一个与某个内部调用耦合的测试可能是钉住关键契约的唯一办法。判断标准始终是：这个坏味道是否正在损害测试套件的价值——即它捕捉回归、记录行为、支撑重构的能力——而每节末尾的误报边界与检测信号同样重要。

这里几乎所有坏味道背后都有一个统一原则，即 Kent Beck 的那句话：**测试应当与代码的行为耦合，与其结构解耦。**当一个测试在一次保持行为不变的重构后挂掉时，说明某种结构耦合漏了进来；当一个测试在行为已经坏掉时仍然通过，说明某种行为覆盖漏了出去。大多数测试坏味道，都是这两种泄漏之一披着特定的外衣。

## 脆弱测试（Fragile Test）

**是什么。** 当生产代码变化时就会挂掉的测试，即使*被测行为*并未改变。测试与结构耦合了——某个方法签名、调用顺序、内部数据形状、周遭上下文——而不是与可观察的契约耦合。Meszaros 归纳了四种敏感性：接口敏感（重命名或改签名会让测试挂掉）、行为敏感（一个无关的行为变化波及进来）、数据敏感（共享测试数据的改动弄坏无关的测试）、上下文敏感（测试依赖全局或环境状态）。

**为什么重要。** 这是日常工作中代价最高的测试坏味道，也是那句抱怨——"我改了一个地方，就得修一堆测试"——背后的元凶。脆弱的套件让每一次重构的代价都超出它应有的水平：本应赋能变更的安全网反而对变更征税。更糟的是，当大规模的机械式修测试变成日常，团队会不再读测试断言的内容，而是开始按模式机械地改，于是真正的回归就藏在这片噪音里。一个每次重命名都喊狼来了的套件，最终会被所有人无视。

**检测信号。** 一次保持行为不变的重构迫使你去改动许多测试文件。测试断言落在私有字段、内部方法名、或内部调用的*顺序*上，而不是返回值或可观察的效果上。重命名一个内部辅助方法，就弄坏了一批本来无意依赖它的测试。同一个字面量在几十个测试里重复出现，于是一次产品改动需要一次大扫荡。你发现自己正对许多测试同时施加*相同的*修改：这就是变更探测器（change-detector）的征兆。

**解决方式。** 通过公开接口做测试——即真实调用者使用的那个表面——并断言可观察的结果：返回值、抛出的异常、持久化的状态、发往真实边界的消息。把重复的字面量收进有名字的夹具（fixture）或构造器（builder）里，使一次契约变更只触及一处（见[测试代码重复](#test-code-duplication)）。当测试不得不引用某个内部细节时，问一问这个内部细节是否应当被提升为真正的、被测试的接口。注意：当构造函数新增依赖时，setup 合理地跟着变化是正常的；坏味道指的是*断言*追随结构，而不是 arrange 步骤跟随新签名。

**示例场景。** 一个服务被重构，把一个方法拆成三个私有辅助方法；行为完全一致。四十个测试失败了，因为它们用 mock 框架断言旧方法以特定参数被调用了一次。这四十个测试没有一个检查服务实际产出了什么，所以它们全都必须按新的内部形状重写，而这次重写没有证明任何新东西。

**误报边界。** 有些测试*本来就应该*对特定的实现选择敏感，因为这个选择本身就是行为：验证请求由缓存而非源站服务，或验证查询使用了索引，是正当的实现断言。Google 的指南允许这类测试，但期望它们稀少且被明确标注。坏味道是没人有意选择的结构耦合；一个有意为之、有据可查的实现测试不是脆弱，而是精确。

## 变更探测器测试（Change-Detector Test）

**是什么。** 一个只是把生产代码用第二种形式复述一遍的测试——通常全是 mock 和调用顺序验证——结果是代码的*任何*变化都会改变测试，而测试没有验证任何独立的正确性概念。Google 对此有明确命名：一个期望值是实现的镜像的测试是变更探测器，而不是正确性检查。

**为什么重要。** 这类测试趋向于*负*价值。它们是读着代码写出来的，断言的是"代码做了它在做的事"，不携带任何独立的正确性概念，所以当代码错了的时候，测试通常也跟着断言了错的东西，并且保持绿色。与此同时它们带来全额的维护成本——每次重构都会弄坏它们——还充塞套件，让真正的测试更难被找到。这是[脆弱测试](#fragile-test)的极端形态：最大的结构耦合，最小的行为覆盖。

**检测信号。** 一个测试几乎全是 `mock(...)` 的搭建和 `verify(...)` / `assert_called_with(...)` 断言，没有对真实结果的任何断言。测试读起来像方法体的逐字转录。删掉这个测试不会损失任何输入-输出关系的覆盖。当生产代码变化时，测试的 diff 与生产代码的 diff *形状相同*。

**解决方式。** 删除或重写。问一问这段代码负责什么可观察的行为，改为测试那个行为，并在协作者廉价且确定的地方尽量使用真实协作者。如果真正值得验证的只有某个真实边界上的交互（一笔付款恰好被扣款一次），那就在那个真实边界上保留一个聚焦的交互测试，丢掉那些镜像内部细节的断言。在套件规模上应用这条原则，就是在清除累赘，但要名副其实：删除之前，确认该测试没有钉住任何行为、没有杀死任何变异体（mutant）、没有提供其他测试尚未提供的诊断价值。变更探测器测试通常过不了这道门槛，但"通常"不等于"永远"，所以要逐个验证，而不是按类别整批删除。

**示例场景。** 一个方法计算总额并调用 `logger.debug`、`repo.save` 和 `bus.publish`。测试把三者都 mock 掉，并断言它们以那个顺序、以那些参数被调用。它从不检查算出的总额。总额计算里的一个 bug 带着绿灯上线了；一次无害的日志行重排却让测试变红。

**误报边界。** 真实系统边界上的真正的交互测试不是变更探测器：验证一封邮件被发出，或一笔扣款恰好发生一次，是用户关心的可观察行为，即使它以交互的形式表达。坏味道在于镜像那些没有任何外部契约提及的*内部*交互，而不是验证那些本身就是代码存在意义的真实副作用。

## 晦涩测试（Obscure Test）

**是什么。** 一个一眼看不出意图的测试。Meszaros 在这个名目下归纳了若干成因：贪婪测试（Eager Test，一个测试验证多种行为，于是没有任何单一意图是清晰的）、神秘来客（Mystery Guest，测试依赖它没有展示的外部数据或状态，读者看不出它为什么能通过）、通用夹具（General Fixture，一个过大的共享 setup 搭起了一整个世界，而测试只用了一小片）、无关信息（Irrelevant Information，噪音淹没了少数真正关键的值）、间接测试（Indirect Testing，测试隔着一层层其他对象来驱动被测单元）。

**为什么重要。** 测试是唯一不会悄悄漂移的文档，但前提是有人读得懂它。晦涩的测试没能解释自己守护的是什么保证，所以当它挂掉时，没人能判断是生产代码错了还是测试错了。这正是 DAMP 胜过 DRY 的地方：测试代码应当 Descriptive And Meaningful（描述性且有意义的措辞），哪怕以一些重复为代价，因为读者必须*用眼睛*验证测试——测试没有自己的测试。过度压缩、过度抽象的测试代码，是用测试最需要的那项属性（一眼可见的正确性）去交换它们最不需要的那项属性（最少的行数）。

**检测信号。** 单个测试里有多轮针对不同行为的 act-assert 循环。决定结果的值从某个文件、某行共享数据库记录、或定义在远处的夹具里加载，于是测试体看不出它为什么通过。`setUp` / 夹具构造的东西远远多于测试实际触及的。测试被循环和条件包裹，真正的用例难以提取出来。读懂测试花的时间比读懂它测试的代码还长。

**解决方式。** 每个测试只验证一个行为，并用它守护的保证来命名。把关键数据内联进来，让读者同时看到原因和预期效果。在这里宁取 DAMP 不取 DRY。用小型、按用途命名的夹具或工厂辅助方法替换通用夹具，让每个测试只引入它需要的部分。把澄清性的细节收进命名良好的辅助方法里，让它们去除噪音而不隐藏驱动断言的那些值。

**示例场景。** `test_user_flow` 创建一个用户、更新其邮箱、添加两个订单、取消其中一个、然后断言最终余额：十二行 setup、四个互不相干的断言。当它失败时，失败信息只说 `test_user_flow` 挂了，读者必须重建现场才能弄清四种行为里是哪一种回归了。

**误报边界。** 一个真正的多步骤行为——一个端到端工作流测试——合理地拥有更多 setup 和不止一个断言，因为工作流本身*就是*单元。而少量可读的重复也不算晦涩；DAMP 明确偏爱它。坏味道是把无关行为打包、或隐藏因果数据所造成的意外晦涩，而不是真实场景那不可约减的体量。

## 断言轮盘赌（Assertion Roulette）

**是什么。** 一个有许多裸断言、且没有任何按断言描述的测试，于是当其中一个失败时你无法分辨是哪一个——你得玩轮盘赌才能找到罪魁祸首。Kent Beck 期望属性中的 *Specific*（具体）正是正面表述：一个失败的测试应当直指到底是哪里坏了。

**为什么重要。** 诊断时间是真实的成本，每次测试失败都要支付，而且常常是在赶工期的压力下。一个在第 N 行以"expected true, got false"失败、而那行看起来和其他十个断言一模一样的测试，迫使读者去插桩或二分才能弄清到底什么坏了。它也暗示了[晦涩测试](#obscure-test)的存在：一堆没有描述的断言通常意味着多种行为被塞进了一个测试里。

**检测信号。** 一长串没有消息、没有结构的断言。失败输出只给出行号而不指明行为。多个各自本可成为有意义的独立检查的断言，毫无分隔地堆在一个测试里。

**解决方式。** 优先让每个测试只对一个行为做一个逻辑断言，让测试名本身就是失败描述。当多个断言确实属于一体时，给每个断言加一条消息，或使用能指明断言主体的断言风格。对不同输入参数化同一个检查，让每个用例单独报告结果。

**误报边界。** 对*同一个*结果对象断言多个属性不是轮盘赌：检查解析出的记录有正确的名字、年龄和 id，是一个行为（"解析产生正确的记录"），而且读起来清晰。坏味道是横跨*不同*行为的未描述断言，而不是对单一结果的少数几个相关检查。

## 不稳定 / 非确定性测试（Erratic / Non-Deterministic Test）

**是什么。** 一个没有任何代码变化却时而过、时而挂的测试。Meszaros 的 Erratic Test 归纳了各种成因：相互干扰的测试（一个测试遗留的状态影响另一个）、测试运行战争（被并行运行争抢的共享外部资源）、不可重复的测试（第一次通过、重跑就挂）、资源泄漏，以及真正的非确定性逻辑（时钟、随机数、网络、顺序、并发）。Fowler 那篇关于根除非确定性的文章把这视为对测试套件的生存威胁。

**为什么重要。** 不稳定性摧毁的是对*整个*套件的信任，而不仅仅是对那个不稳定测试的信任。一旦红色可能意味着"坏了"也可能意味着"运气不好"，每次失败都变成了主观判断题，人们开始反复重跑直到变绿，真正的回归也被"大概只是不稳定"放行过去。一个你无法信任其含义的套件，比没有套件好不了多少。这种坏味道是 Kent Beck 的 *Deterministic* 与 *Isolated* 期望属性的敌人，也是 Google"测试必须能以任意顺序运行"这条规则的敌人。

**检测信号。** 在 CI 上失败但本地通过的测试，或只在并行时失败、或只在某种顺序下失败的测试。读写共享状态——真实时钟、共享数据库、固定路径上的文件、模块级全局变量——而没有隔离的测试。立即重跑就失败的测试（它留下了状态）。用 sleep 来"等待"异步工作。

**解决方式。** 隔离：每个测试获得全新状态并自行清理，使运行顺序不改变结果（一个有意考察并发的测试仍然要控制并发——固定的调度或播种的交错序列——而不是放任竞争）。用测试替身或注入的控制替换不受控的边界：固定的时钟、播种的随机数生成器、替代网络的内存假实现。使用能自动恢复状态的框架工具（临时目录、在 teardown 时还原的环境补丁），而不是在测试失败时会跳过的手工清理。永远不要让一个已知不稳定的测试留在主套件里当警示灯：隔离它或修复它，因为一个被容忍的不稳定测试会训练所有人无视红色。

**示例场景。** `test_report_uses_todays_date` 调用真实的 `date.today()` 并断言一个格式化字符串。它顺利通过了数月，然后在月份边界、以及 CI 上跨时区时失败。行为从来没有错；是测试把自己耦合到了墙上时钟上，而不是注入一个固定日期。

**误报边界。** 一个合理考察并发或随机性的测试，只要控制住了它们，就不是不稳定测试：播种的生成器或确定性的调度器能让结果可重复。而一个触及真实外部系统的集成测试，被允许更慢，也应被正确地隔离到单独的套件里；只要它没有待在快速套件里假装自己是确定性的，它就不是"不稳定的单元测试"这种坏味道。

## 测试代码重复（Test Code Duplication）

**是什么。** 相同的 setup、断言或数据被复制到许多测试里，于是契约的一次变化需要编辑每一个副本。这是 DRY 坏味道在测试上的体现，但它与 DAMP 存在张力，所以解决方式比生产代码里的更微妙。

**为什么重要。** 结构性重复——一次契约变化迫使几十个测试做同步修改的那一种——是一种维护税，也是[脆弱测试](#fragile-test)行为的一个来源。但修复方式*不是*像对生产代码那样激进地对测试做 DRY，因为测试必须保持肉眼可读（见[晦涩测试](#obscure-test)）。Google 的指南说得很明确：测试应当是 DAMP 的，容忍可读的重复，把抽取留给*噪音*——那些遮蔽意图的样板代码——而不是留给让每个用例清晰可读的有意义的值。

**检测信号。** 相同的多行 setup 被粘贴进许多测试里，而所构造对象形状的一次变化会触及所有测试。同一个魔法字面量到处重复。几个文件里复制粘贴来的夹具定义微妙地（或完全）相同：这就是"不同位置出现重复夹具"的具体问题。一个本可以消除纯样板代码却从未被抽取的辅助方法。

**解决方式。** 抽取*噪音*，把*意义*留在原地。把重复的构造收进最近公共作用域上的单一共享 setup 位置（共享夹具、构造器、setup 模块，看测试框架提供什么），从而只有一份定义而不是五份近似副本，但仍让每个测试展示使其可读的具体输入和预期输出。对逐测试变化的对象使用工厂辅助方法或构造器。要走的界线是：消除那种会迫使*同步结构性修改*的重复，保留读者*理解用例*所需要的重复。

**示例场景。** 十二个测试各自以相同的八行代码开头来构造一个 `Config` 对象，只差一个字段。新增了一个必填字段；十二个测试以相同的方式挂掉。一个构造默认配置的单一夹具、加每个测试覆盖它关心的那个字段，本可以在一处吸收这次变化，同时保持每个测试的意图可见。

**误报边界。** 可读的、有意的重复不是这种坏味道：DAMP 认为，让测试自我解释的一点点重复，胜过迫使读者跳转到别处的抽象。如果抽取 setup 到共享辅助方法会隐藏解释测试为何通过的那些值，就不要抽取。坏味道是把许多测试耦合到一个结构上的重复，而不是让每个测试在局部可理解的重复。

## 测错了东西（Testing the Wrong Thing）

**是什么。** 把精力花在测试不携带任何值得保护的独立行为的代码上：琐碎的 getter、框架胶水代码、配置值，或者通过生硬构造的直接测试来考察的通用工具——而不是通过使用它们的行为来考察。Meszaros 的 Indirect Testing 和更宽泛的"测试行为，而非偶然存在的代码"原则都与此相关。

**为什么重要。** 每个测试既是资产也是负债：它必须被阅读、维护和更新。一个钉住无逻辑之值（常量、配置默认值）或无领域意义之工具的测试，增加了维护成本和覆盖率数字上的安慰，却没有保护任何有人会写错的东西。它还颠倒了覆盖率信号：套件看起来很全面，因为那些容易的、无行为的代码被大量测试，而真正的决策逻辑可能很薄弱。覆盖率是用来发现*未测试*代码的工具，永远不是要被最大化的目标；为了抬高数字而测试琐碎之物，正是 Fowler 直接警告过的反模式。

**检测信号。** 断言一个常量等于其字面量、或断言某个配置键具有其默认值的测试：值一变测试就得同步变，而测试从未表达过任何预期行为。为只返回一个字段的 getter 写的测试。一个通用 `utils` 函数用合成输入被孤立地测试，而它仅有的真实调用者已经考察过它。一场"把覆盖率提上去"的运动，为最容易的代码而非风险最高的代码添加了测试。

**解决方式。** 在行为被决定的层级上测试行为，让琐碎代码被使用它的行为顺带覆盖。删除那些只是复述常量或配置默认值的测试；如果一个配置值是承重的，测试它*驱动的行为*，而不是值本身。对于一个真正可复用、有真实边界情况的工具（日期解析器、棘手算法），直接的行为测试是合理的；判断界线在于该函数是否有*可枚举的、可能出错的行为*，而不在于它是否住在一个叫 `utils` 的文件里。

**示例场景。** 一个测试断言 `DEFAULT_TIMEOUT == 30`。有人把超时调到 45；测试失败，被"修复"为把 30 改成 45，于是它花了两次编辑的代价却什么都没保护：它从未检查过 30 秒的超时产生任何特定行为。真正值得测试的行为（请求在配置的超时后中止）从来没人写过。

**误报边界。** 一个有真实、易出错行为的工具，无论住在哪里都值得直接测试；坏味道不是"永远不要测 utils"，而是"不要为没有任何值得保护之行为的代码凭空制造测试"。同样，一个编码了真实契约的配置值（一个不得悄悄变化的监管限额）可以合理地有一个守护测试，理想情况下其表述应是保护契约而非镜像字面量。判断标准是测试是否保护了某个有人可能切实弄坏的行为，而不是代码属于什么类别。
