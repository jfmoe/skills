# 测试原则

测试套件同时以两种方式挣得自己的存在价值：捕捉回归，以及记录代码应该做什么。这两项工作由同一条纪律服务：**让测试与行为耦合，与结构解耦**。Kent Beck 直接陈述了这个目标：测试应当对*行为*的变化敏感，对*结构*的变化不敏感。下面的每条原则都是这句话的推论。

本文档与语言无关。它陈述原则和取舍；违反这些原则的反模式在 [test-smells](./test-smells.md) 中有专门的目录，而语言特定的机制（pytest 夹具、参数化、mock）放在相应的工程 skill 里。

## 测行为，不测实现

测试应当断言一个单元*从外部看做了什么*——它的返回值、抛出的错误、记录下的副作用——而不是它内部是怎么做的。理由是经济性的：可观察行为是你承诺的契约，所以钉在契约上的测试只在你违背承诺时失败，而保持行为不变的重构会让它保持绿色。钉在内部调用、私有字段或协作者调用确切顺序上的测试，则在每次重构时都失败，同时对正确性一无所证：它把实现复述给了实现自己。

这是对关于 agent 生成测试的最常见抱怨的直接回答：*"我改了代码，就得重写一堵墙的测试，其中大部分涉及根本不该测的细节。"*这种痛苦几乎总是[脆弱测试](./test-smells.md#fragile-test)和[变更探测器测试](./test-smells.md#change-detector-test)——镜像结构而非行为的测试。修复办法不是"少写测试"，而是"断言结果，只在真实边界上 mock"。

**边界情形。** 偶尔行为本身*就是*一个内部选择：你必须验证一次读取走了缓存而不是数据库，或一次重试确实发生了。测试这些是正当的，但应当稀少，并以所守护的保证来命名（"重复读取由缓存服务"），而不是以方法命名。如果你的大多数测试都需要探入内部，说明设计在要求把依赖作为参数注入，而不是在内部伸手去拿。

## 期望属性：一个好测试优化什么

Kent Beck 的 *Test Desiderata* 列出了测试可以具有的十二项属性。它们不是一份要同时全部满足的清单——其中几项彼此冲突——而是一套词汇，用来决定某个给定测试应当优化什么：

- **Isolated（隔离）**：测试互不影响；任何顺序给出相同结果。
- **Composable（可组合）**：可以独立于其他维度单独测试一个维度。
- **Deterministic（确定）**：同样的代码，每次运行同样的结果。
- **Fast（快速）**：便宜到可以持续运行。
- **Writable（易写）**：相对于被测代码，写起来便宜。
- **Readable（可读）**：读者能看出测了什么、为什么重要。
- **Behavioral（行为敏感）**：对行为变化敏感（一个 bug 应该弄坏一个测试）。
- **Structure-insensitive（结构不敏感）**：保持行为的重构不应弄坏它。
- **Automated（自动化）**：无需人工干预即可运行。
- **Specific（具体）**：一次失败指向一个原因。
- **Predictive（可预测）**：如果通过，代码就可以安全发布。
- **Inspiring（激励信心）**：通过能建立真实的信心。

这些属性彼此冲突，而这正是要点。*Predictive* 把测试拉向真实的全栈测试；*Fast* 和 *Specific* 把测试拉向小型隔离的测试。面向程序员的单元测试有意放弃一部分 *Predictive* 和 *Inspiring* 的广度，以换取 *Writable*、*Fast* 和 *Specific*；端到端测试做相反的取舍。知道一个测试是*为了*哪些属性而写的，就能阻止你对每个测试都要求全部十二项。

## 覆盖率是盲区探测器，不是目标

行覆盖率度量的是哪些行被执行了，而不是有没有任何东西被检查；一个调用函数却不断言任何东西的测试会报告满覆盖率，同时什么都没验证。Fowler 的立场是可操作的那种：覆盖率对*负向*信号有用（完全没有测试触及的代码是真实的缺口），作为*正向*目标则有误导性（高百分比对断言质量只字未提）。一个覆盖率百分比一旦成为目标，就会催生出为挪动数字而写的低价值测试。

更强的信号是**基于变异（mutation）的**：如果你把 `+` 改成 `-`、翻转一个边界、或删掉一行，有没有测试变红？存活下来的变异体是一个真实的洞——一个没有任何断言钉住的行为——其暴露方式是一条"被覆盖但未被断言"的行永远揭示不了的。你很少需要真的用变异测试工具来这样思考；写测试时问一句"这个测试能抓住哪种变异？"就足以暴露一个什么都没检查的断言。

这把目标从"覆盖每一行"重构为"**用尽可能少的测试，钉住每一个重要的行为。**"两个经由不同表面数据考察同一条路径的测试，常常只提供一个测试的防护和两个测试的维护成本。当两个用例杀死相同的变异体*并且*彼此都没有记录对方遗漏的独特场景时，保留更清晰的那个，把另一个并入；这正是如何用更少的测试获得同等覆盖，也正是你想要的精简。合并前的检查和下面那条相同：相同的变异分数提示重叠，但它们本身并不证明两个测试可以互换。

## 更少、更强的测试

更多的测试不等于更多的安全。当每个测试钉住一个独特行为时，套件是资产；而那些做不到的测试则按比例让它变成负债。三个习惯让套件保持精干：

- **每个测试一个行为。** 断言一个保证的测试只会因一个原因失败，并在标题里说出这个原因。走过五种行为的测试（贪婪测试，[晦涩测试](./test-smells.md#obscure-test)的一种形态）失败得含混，而且抗拒变化。宁要许多小型行为测试，也不要少数蔓延的大测试；但"小"指的是*行为上窄*，而不是*与某个函数的内部细节耦合*。
- **参数化等价用例。** 当一个行为应当在许多输入上成立时，把用例表达为数据，而不是复制粘贴的测试体。每个用例单独报告，于是失败能指明确切的输入，用例也以表格形式保持可见。这是边界与等价类测试的正确工具；而当用例需要真正不同的 setup 或断言时它就是错误工具：把它们硬塞进同一个参数化测试体只会隐藏分支逻辑。
- **删除死重：先证明它是死的。** 一个不提供任何其他测试尚未提供之防护的测试，是没有回报的维护成本。这种情况确实存在：在一项针对 LLM 生成套件的变异测试研究中（Bas Dijkstra 的，n=23），有 4 个测试对行覆盖*和*变异覆盖都没有任何贡献；这是一个具体案例，而不是可以指望的固定比率。但"杀死相同的变异体"并不是冗余的证明：删除之前，检查该测试是否没有提供独特的行为文档、没有更好的失败定位、也没有覆盖其他测试漏掉的变异体。变异工具无法枚举每一种可能的故障，所以相同的变异分数是重叠的强证据，而不是保证。在冗余被确立之后再删除；不要仅凭分数相同就删除。

## 在测试里，DAMP 优先于 DRY

生产代码倾向 DRY：消除重复的*知识*，让一条规则只住在一处。测试代码倾向另一头——**DAMP**（Descriptive And Meaningful Phrases，描述性且有意义的措辞）——这是有意为之，不是马虎。原因是*测试没有测试*：它们的正确性靠人来阅读验证，所以可读性优先于去重。一个内联了 setup、直接断言期望的测试可以一眼检验；一个把一切都经由共享辅助方法、循环和遥远的 `setUp` 路由的测试，则迫使读者在脑中组装出场景之后才能评判它。

这并不是给复制粘贴发许可证。调和是精确的：消除伤害*维护*的重复（值对象构造器、去除噪音的辅助方法），容忍帮助*阅读*的重复（在测试体中直接陈述的具体输入和预期输出）。Meszaros 的[测试代码重复](./test-smells.md#test-code-duplication)坏味道针对的是那种一次行为变化迫使多处修改的结构性重复；DAMP 针对的是让每个测试自足的表面重复。二者的一致性大于冲突：两者都希望一个行为的变化只触及少数测试，也都希望读者不用离开测试就能读懂它。

## 隔离与确定性没有商量余地

一个因顺序、时序、环境或前一个测试的残留而通过或失败的测试，不只是自己失败；它腐蚀对整个套件的信任，而一个不被信任的套件会被无视，这比没有套件更糟。Fowler 的规则很直白：根除非确定性，不要容忍它。反复出现的根因是：测试间共享的可变状态、对真实外部资源的依赖（网络、时钟、文件系统、远程服务）、无人看管的异步，以及未播种的随机数。

防止它的纪律是：让每个测试拥有自己的全新状态，使任何运行顺序都得到相同结果；在系统边界上用测试替身替换缓慢的或非确定性的依赖；控制时钟和随机种子，而不是读取真实的；并且永远不要让一个不稳定的测试留在主套件里"以后再修"：隔离它或修复它，因为一个不稳定的测试会教会所有人无视红色。Google 的 Small/Medium/Large 测试规模方案把这一点可操作化了：在小型测试中*禁止*高风险资源（网络、sleep、多线程），这正是它们构造上就快速、可并行、与顺序无关的原因。

## 不测框架、不测配置、不测琐碎之物

每个测试都永久消耗注意力，所以只有当它能抓住*你的*逻辑里的缺陷时，它才挣得自己的位置。三类代码通常做不到：

- **框架和库的行为。** 断言一个久经测试的库能对列表排序、或 ORM 能保存一行的测试，是在重复断言别人的保证，并在你升级时挂掉。在边界上测试*你*对库的使用，而不是库本身。
- **配置和常量。** 读取一个配置值并断言它等于同一个字面量、或断言设置对象有你刚声明的字段的测试，是[变更探测器测试](./test-smells.md#change-detector-test)；它复制了源，并在源变化时失败，却什么也抓不到。测试*配置驱动的行为*（`timeout` 为 0 时真的会抛错吗？），而不是值。
- **琐碎的机械代码。** getter、纯透传的薄包装、以及格式化工具或类型检查器已经守护过的纯数据持有类，很少值得一个专门的测试。如果一个辅助方法有值得测试的真实逻辑，就*通过使用它的行为*来测，而不是孤立地测；对一个工具的孤立微测试会把套件耦合到一个系统其余部分可能根本不依赖的细节上。

误报边界在这里同样重要：一个有真实的、被复用的逻辑的工具（解析器、日期运算函数、校验规则）*确实*值得直接测试，因为其中的缺陷会广泛传播。反模式是*为了覆盖率*去测试那些由机械手段保证的琐碎之物和内部辅助方法，而不是测试真正承重的逻辑——无论它住在哪里。

## 测试即文档

写得好的测试是一个项目所拥有的最可靠的文档之一，因为文档要在不变红的情况下偏离代码是很难的；不过，薄弱的断言、错误的判据（oracle）、或与被守护代码同步修改的测试仍可能悄悄漂移，所以这是一种强倾向，而不是保证。想知道如何使用一个函数的读者，应当能打开它的测试并看到带预期结果的真实调用。这是设计目标，不是副产品：**Arrange-Act-Assert** 结构让每个测试读作"准备、动作、期望"；每个测试一个行为，让失败指向一件事；名字陈述保证（`rejects_expired_token`，而不是 `test_validate_2`）。真实的数据会强化这一点：`"abc"` 或 `123` 这样的输入可能让一个真实世界的值本会弄挂的测试通过，所以要使用与生产相似的数据。以这种方式写出的测试同时充当工作示例，这正是测试驱动开发一次产出设计工具与活文档的深层原因。
