# 重复代码

## 是什么

重复代码是同一个东西被表达在多于一处地方的坏味道。它被列在冗余品之中，因为移除真正的重复通常让代码更清晰、变更更便宜。但它也是最常被误读的坏味道，因为表面症状——两个看起来相似的片段——并不告诉你是否真的存在问题。整个判断都系于一个区分。

## 知识重复 vs 巧合相似

这是关键区分，无论朝哪个方向弄错都会造成伤害。

**知识重复**是同一个*决策*被表达在多个地方：一条业务规则、一个校验条件、一个 schema、一个协议细节、一项税额计算、一次状态转换。检验是反事实的：*如果其中一个副本背后的需求变了，其他副本也必须跟着变吗？*如果是，它们编码的是同一份知识，而让它住在好几个地方意味着未来的某次编辑会更新一些、漏掉另一些，让系统自相矛盾。这种重复值得移除。

**巧合相似**是今天因无关原因看起来相似、被不同力量驱动的代码。两个结构相同但检查不同概念的校验器；两个样板平行但逻辑无关的处理器；与其他测试 setup 相似、却钉住不同场景的测试 setup。如果其中一个背后的需求变了，其他的不会动。这些片段在有意义的意义上不是重复，它们只是押韵，而统一它们会把本应独立演进的东西耦合起来。

对巧合相似去重的错误比留下真正的重复更隐蔽，因为它主动引入了耦合和一个错误的抽象，让未来的变更不得不与之搏斗。这一区分所依据的原则见 [duplicated-code.md](./duplicated-code.md) 的姊妹篇 [dry](../design-principles/dry.md)：DRY 关乎知识，不关乎文本。

## 什么时候提炼

当你确认这些片段编码了同一份知识时就提炼。对**高风险知识**——安全、权限、金钱、协议契约、数据一致性、schema 的单一事实来源——见到就提炼，哪怕才第二次出现。这些领域发散的代价太高，等不起。

对你相当确定、但变化方向尚不清晰的普通代码，**事不过三规则（Rule of Three）**是刹车：写第一次，容忍第二次，在第三次出现、或变化方向变清晰时提炼。到第三个实例时，你通常能看出什么真正在变、什么保持不变，这意味着你能选对接缝而不是瞎猜。见 [rule-of-three](../design-principles/rule-of-three.md)。

## 什么时候留着

当片段只是巧合相似时，或当它们确实相关但尚不清晰、且还没到第三个实例时，留着重复。过早统一会挑错抽象，而错误的抽象比它替换掉的重复更昂贵：你先付代价建它，然后在用例发散时再付代价拆它。容忍两个副本一段时间既便宜又可逆；一个不想要的抽象两者都不是。

## 抽象稳定性要求

提炼之前，抽象的形状必须已经合理稳定。如果你还不能干净地为提炼物命名，或者你已经能预见下一个用例会需要不同的参数或分支，那接缝还没准备好。好的提炼有清晰的名字、很少的参数、单一的变化理由，并隐藏了真实的复杂度。如果候选不满足这些，说明重复在告诉你底层概念尚未稳定：等一等。

## 错误的去重

常见的失败——尤其在 agent 辅助产出的代码里——是**比重复本身更难读的参数化包装**。你把两个相似片段提炼成一个函数，但它们并不相同，于是函数先长出一个切换行为的布尔标志，再长出一个模式参数，再为真正不同的部分长出一个回调，再为某个边界情况长出一条特殊分支。结果是一个没人读得懂的函数，由没人跟得上的调用点配置：严格地比两个诚实的副本更糟。当你发现这样的函数时，修复办法是内联它、把代码复制回去、重新寻找真正的变化轴。一个在两种行为间做选择的标志参数，常常是这个函数本应保持为两个函数的信号。
