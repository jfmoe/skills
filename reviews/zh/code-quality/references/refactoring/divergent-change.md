# 发散式变化

## 是什么

发散式变化是这样的坏味道：同一个模块因许多互不相干的原因被反复修改。每次数据库 schema 一变，你要编辑这个模块；每次报表格式一变，你又编辑它；每次业务规则一挪，你又回到同一个文件动另一个部分。这个模块变成了一个路口，好几个彼此独立的关注点恰好在此共存。一个文件，许多打开它的无关理由。

它是*变更阻碍者*，因为混在一起的关注点让每次变更的风险都超出应有水平：编辑报表格式化代码意味着绕过持久化代码和校验代码，对一个关注点的修改可能意外扰动另一个。这个模块也抗拒理解，因为要知道"这个模块是干什么的"，你得同时在脑子里装着好几个互不相干的话题。

## 信号

检测问题是：*这个模块因为多少种不同的原因被编辑？*如果你看看提交历史（或者只是想象一下未来的各种请求），发现这一个文件因"新税则"、"新导出格式"、"新存储后端"、"新校验策略"而变化，那就是四种原因、四个关注点、一个模块。文件内的信号是：一个类或模块的各节之间没有共同的数据或逻辑——方法聚成几组，组与组从不互相调用，也从不触碰相同的字段。

与 [shotgun-surgery.md](./shotgun-surgery.md) 的干净对比能让它更鲜明：那边是一次变更击中许多模块；这边是许多变更击中一个模块。它们互为镜像。

## 它在告诉你什么

发散式变化是**拆分职责**的信号。这个模块在做几份工作，而每份工作都应该住进自己的模块，以便能独立地、隔离地变化。重构通常是：

- 先用 [extract-function.md](./extract-function.md) 隔离内聚的组，然后用提炼类 / 提炼模块给每个关注点自己的家。
- 用 [move-function.md](./move-function.md) 把行为搬到拥有其关注点的模块。
- 分开缠在一起的层次：例如，把一个混合了业务规则、持久化和格式化的模块拆成三个，使格式化变更只触及格式化模块。

拆分之后，每个结果模块只有单一的变化轴：只有持久化变了你才编辑持久化模块，只有规则变了你才编辑规则模块。这就是内聚的实际含义。

## 与 SRP 和霰弹式手术的关系

发散式变化是被陈述为坏味道的**单一职责原则**。Uncle Martin 把 SRP 表述为"一个模块应当只有一个变化的理由"。发散式变化违反了这条性质，因为模块有许多变化的理由。解法是找到驱动变化的不同行为者或力量，给每一个自己的模块。见 [solid](../design-principles/solid.md)。

它也是**霰弹式手术的反面**，两者必须相互权衡：

- **发散式变化** → 一个模块，许多变化理由 → **拆**开。
- **霰弹式手术** → 一个变化理由，许多模块 → **收**拢。

无论朝哪边纠正过度，都会制造出另一种。拆得太狠，一次变更就开始需要在所有新碎片上做编辑（霰弹式手术）。收得太狠，合并出的模块又开始因许多原因变化（发散式变化）。两种坏味道指向的目标是同一个：模块边界应当跟随真实的变化轴，使一种变化映射到一处编辑。拿不准时，识别这段代码历史上实际因哪些原因变化过，让那些原因来定义边界。
