# 长函数

## 是什么

长函数是最常见的膨胀者，也是最常被误判的。坏味道不是以行数衡量的长度；当一个函数**混合了抽象层次、承载了不止一个职责、或含有只有通读才能理解的小节**时，它才算太长。长度是提示这三种情况之一正在发生的线索，而不是问题本身。一个读起来是单一抽象层次上一条清晰序列的四十行函数没问题；一个把高层策略和底层字节操作交织在一起的十二行函数则不然。

可靠的检验是你能否诚实地命名这个函数。如果名字是内部一切的真实概括，这个函数是内聚的。如果诚实的名字会是"校验订单，*并且*计算总额，*并且*格式化收据，*并且*发送邮件"，那它在做几件事，而那些"并且"标出了它想要拆分的接缝。

## 是什么让一个函数过长

- **混合抽象层次。** 函数体在"是什么"（编排业务流程）和"怎么做"（字符串格式化、下标运算、字典摆弄）之间跳跃。读者不得不不断切换高度。每个底层片段都想变成一个有名字的函数，让高层流程读起来干净。
- **多个职责。** 不同的阶段——解析，然后校验，然后变换，然后持久化——塞进一个函数里。每个阶段都是提炼的候选，尤其当它们通过少数几个构成天然接口的局部变量通信时。
- **难以命名的小节。** 一个标志性信号是用注释引出一个代码块：`# now compute the discount`。注释在命名一个代码拒绝命名的概念。那个块通常是一次等待发生的提炼函数，而注释将成为函数名。
- **深层嵌套和长条件。** 箭头形代码，用卫语句或提炼出的谓词可以压平逻辑、显露意图。

## 提炼信号

在以下情况求助于 [extract-function.md](./extract-function.md)：

- 你写了一条注释来解释接下来几行；把它们提炼出来，让名字承载注释。
- 一块代码使用了一簇紧密的局部变量，而函数其余部分不碰它们；那簇变量就是一个函数边界。
- 你发现自己要来回滚动才能把整个函数装进脑子。
- 某个阶段本可以被孤立测试，但目前因为被埋着而做不到。

## 什么时候长度可以接受

并非每个长函数都是坏味道，强行拆分反而会把一个线性故事散成许多读者必须重新拼装的小函数，让代码更糟。长度在以下情况可以接受：

- **它是单一抽象层次上的一条清晰序列。** 一个按顺序做十步、全部处于同一层次、没有分支复杂度的函数，像散文一样自上而下地读。拆开它只会增加跳转成本。注意与 [thin-wrapper-function.md](./thin-wrapper-function.md) 的张力：提炼一个只用一次、没有抽象边界的步骤，常常产生一个浅辅助函数，其伤害大于长度本身。
- **配置或数据。** 长长的字面量表、大映射、一组常量：这里的长度只是数据量，不是逻辑复杂度。
- **测试 setup 和测试体。** 测试即使较长，通常也以显式的线性 setup-act-assert 读起来更好；过度提炼测试辅助方法会隐藏测试实际考察的东西。
- **对许多用例的 `match` 或分派**，其中每个用例都很短、结构是扁平的。

## 与其他坏味道和重构的关系

长函数是 [extract-function.md](./extract-function.md) 的首要触发器。它常与过长参数列表和数据泥团同行：当提炼产出的函数需要同样的五个参数时，这些参数是在要求变成一个参数对象。它也可能是某个缺失抽象的症状：在 agent 辅助产出的代码里，函数变长是因为每个新需求都被追加成又一个分支，把函数变成变更垃圾场；那更接近 [divergent-change.md](./divergent-change.md)，修复方式是找到变化轴，而不是继续提炼。
