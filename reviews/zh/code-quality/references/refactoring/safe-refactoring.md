# 安全重构

## 行为等价是契约

如 [fowler-refactoring.md](./fowler-refactoring.md) 所定义，重构的唯一承诺是**外部可观察行为不发生变化**。同样的输入产生同样的输出；调用者依赖的副作用仍然发生；原来抛出的错误仍然抛出。内部结构可以随你喜欢任意改变，只要外部没人能分辨出差别。本文档里的一切，都是为了让你在做结构变更时守住这个承诺，并且是*证明*你守住了它，而不是指望守住了它。

"可观察"在这个定义里是真正承重的词。私有方法调用的确切顺序不是可观察的。返回值、写出的文件、发出的事件、抛出的异常、消费方会解析的日志内容——这些是可观察的。在重构靠近边界的代码之前，先弄清楚到底什么是可观察的，因为那就是你不能越过的线。对公开 API、序列化 schema 或 CLI 参数而言，可观察面很宽，约束很紧。

## 先备好测试，再动结构

你无法保持自己观察不到的行为，也无法在没有快速检查手段的情况下确认保持。所以重构的前提是一张安全网：一个考察你即将重组的行为的测试套件，快到足以在每一小步之后运行。如果这个套件存在并且是绿的，重构是低风险的。如果不存在，你要么先建它，要么不要重构。

这不是可选的严谨。重组行为未经验证的代码，是"编辑并祈祷"，也是重构引入 bug 最常见的方式。整套方法都依赖反馈回路是可信的。

## 特征化测试

当你需要重构没有测试的代码时——通常是遗留代码，或 agent 快速生成的代码——你先写**特征化测试（characterization test）**。特征化测试不断言代码*应当*做什么；它钉住代码*当前*做什么，包括任何怪癖。你运行代码，观察输出，写一个恰好断言该输出的测试。这个测试现在刻画了既有行为。

重点不是正确性——既有行为甚至可能略有错误——重点是绊线。当前行为一旦被钉住，你就可以自由重构，任何变红的测试都告诉你重组改变了什么。如果你后来认定旧行为是个 bug，修复它是一次单独的、有意为之的行为变更，有它自己的测试更新，而不是搭重构便车悄悄混入的东西。在 Python 里，快照/审批测试和捕获代表性输出，是快速特征化变换密集型代码的实用办法。

## 可逆的小步

每一步都应小到显而易见地正确、且易于撤销。重命名一个符号；跑测试。提炼一个函数；跑测试。搬移它；跑测试。这样做有效的理由：

- 失败能定位到你刚做的那一个改动上，所以调试是平凡的。
- 你持续处于可发布状态，随时可以停下。
- 撤销一个小步骤很便宜；撤销缠在一起的一小时改动则不然。

频繁提交。每个重构步骤（或每一小批相关步骤）一个干净的提交，意味着 `git` 本身就是你回滚策略的一部分。

## IDE 与工具支持

自动化重构（重命名符号、[提炼函数](./extract-function.md)、[内联](./inline-function.md)、[搬移](./move-function.md)）比手工编辑更安全，因为工具在所有引用处机械地执行变换，不会有手工编辑引入的笔误和漏掉的调用点。有它们就用。

在 Python 里要注意，工具比静态类型语言弱。动态分派、`getattr`、基于字符串的引用、monkeypatch 和鸭子类型意味着重命名工具无法确定地找到每一个引用。所以 Python 重构更依赖其他检查：类型检查器（mypy/pyright）捕捉坏掉的签名，`rg` 找到工具可能漏掉的文本引用，以及作为最终裁决者的测试套件。把 Python 自动化重构当作快速的第一遍处理、然后再验证，而不是当作保证。

## 什么时候手工重构有风险

一些情形会让常规安全机制失效，需要格外小心：

- **反射、动态属性访问、字符串键分派。** 工具和 grep 都会漏掉这些。广泛搜索，并倚重运行时测试。
- **公开 API 和序列化格式。** 可观察面延伸到你代码库之外、到你无法测试的消费方。把这类变更当作行为变更，而不是重构。
- **并发与顺序。** 重排操作可能改变行为，即使每一步在单线程测试里看起来都保持行为。
- **带难以在测试中复现的副作用的代码**（外部服务、时间、随机性）。先把副作用隔离到一道接缝后面，让核心变得可测试。

## 回滚策略

重构应当永远有一个干净的退路。开始之前，确保工作区已提交，从而有一个可返回的已知良好点。小步前进、频繁提交，让回滚单元保持小。如果某一步失败而原因并非显而易见，撤销那一步，而不是尝试向前打补丁；纪律是回到绿色，而不是在坏掉的状态上累积修补。而如果你中途发现正朝向的抽象是错的，正确动作常常是[内联](./inline-function.md)回先前的结构，重新寻找真正的接缝，而不是硬撑下去。一个可以干净放弃的重构，才是安全的重构。
