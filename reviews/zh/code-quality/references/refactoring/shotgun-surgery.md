# 霰弹式手术

## 是什么

霰弹式手术是这样的坏味道：一次概念上的变更迫使你在许多不同的文件或类里做许多小编辑。你决定新增一种支付方式、改变日期格式化方式、或重命名线上协议里的一个字段，突然间你就触碰了一打模块，每个模块分到变更的一小片。漏掉一处，系统就微妙地坏掉。这次变更在逻辑上是单一的，在物理上却是散落的。

痛苦在变更时感受到，这正是它成为*变更阻碍者*的原因：代码在任何一个地方读起来可能都没问题，但演进它的成本很高，变更不完整的风险常在。一个决策被涂抹到越多地方，未来的某次编辑更新了其中大多数、却忘掉剩下的可能性就越大。

## 信号

当一次例行变更在看似无关的文件间产生一个长长的、重复性的 diff 时，或当你对一次变更的心智清单是"记得还要更新 X、Y 和 Z"时，你会注意到它。"你是不是也改了校验器 / 序列化器 / 文档？"这样的代码评审评论是社会层面的症状。一个实用的检测动作是做一次变更并观察编辑如何扇出：如果单一职责需要在七处编辑，那七处拿着的是同一个概念的碎片。

这常常是基本类型偏执和知识重复的下游效应：当一个领域概念（状态、费率、格式）没有唯一的家时，每个使用它的地方都必须编码同一份知识，于是这份知识的每次变化都击中每个地方。见 [duplicated-code.md](./duplicated-code.md) 和 [primitive-obsession.md](./primitive-obsession.md)。

## 它在告诉你什么

霰弹式手术是**缺失的抽象**或**糟糕的内聚**的症状：本应在一处的东西被摊开了。解法是把散落的碎片收进一个拥有该决策的单一模块、类或函数——正是这个坏味道的逆操作。常见手段：

- 用 [move-function.md](./move-function.md) 和搬移字段把散落的行为和数据拉进同一个归属者。
- 引入缺失的类型（值对象、枚举、配置对象），让概念有个家，之后散落的用法收敛为对那一个类型的引用。
- 用单一事实来源替换重复的知识——一张表、一个分派映射、一个 schema——让一次变更就是一次编辑。

目标是未来同类的变更只触及一处。你并不总能做到恰好一处，但从十二处降到两处已经是风险的大幅削减。

## 与发散式变化的关系

霰弹式手术和 [divergent-change.md](./divergent-change.md) 是互逆的坏味道，值得同时记在心里，因为它们的修复朝相反的方向拉。

- **霰弹式手术：** *一次变更 → 许多模块。* 一种变化摊在太多地方。解法是**收拢**：把碎片拉到一起，让变更局部化。
- **发散式变化：** *一个模块 → 许多种变更。* 一个模块因许多无关原因被修改。解法是**拆分**：把职责分开，让每个只为一种原因变化。

两者都关乎让模块边界与代码实际变化的轴对齐。霰弹式手术说缺了一条边界（概念没有家）；发散式变化说边界画错了地方（模块装了太多概念）。统一的目标是读作"一个变化理由"的单一职责原则；见 [solid](../design-principles/solid.md)。修一个可能显露出另一个，所以每动一步都重新评估，而不要在一轮里过度收拢或过度拆分。
