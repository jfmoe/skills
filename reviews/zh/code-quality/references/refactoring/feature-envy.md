# 依恋情结

## 是什么

依恋情结是指一个方法看起来对它所属对象之外的另一个对象更感兴趣。它探入第二个对象，取出好几份数据，做了本应由那个对象自己做的计算。这个方法"嫉妒"它正在操作的那个类的特征。经典形态是：`A` 上的一个方法调用 `b.x`、`b.y`、`b.z` 并把它们组合起来，却几乎不碰 `A` 自己的状态。

这个坏味道之所以要紧，是因为它把行为放错了地方。逻辑依赖另一个对象的内部细节，于是那些内部一变，这个远方的方法就坏掉——这是本不该存在的耦合。而拥有数据的对象被晾成了贫血模型：一袋子字段，属于它的操作却住在别处。这与"行为应与它需要的数据住在一起"的原则恰好相反（见 [tell-dont-ask](../design-principles/tell-dont-ask.md) 和 [grasp](../design-principles/grasp.md) 中 GRASP 的信息专家）。

## 信号

看一个方法，数它碰的是谁的数据。如果它访问另一个对象的字段和方法多于访问自己的，那就是嫉妒。一个可靠的具体信号是一串喂给某个计算的 `other.a`、`other.b`、`other.c`；尤其当这些访问是 [law-of-demeter](../design-principles/law-of-demeter.md) 那种火车失事式调用链时——调用方正穿透它本不该知道的结构。

```python
# Envious: the method lives on Order but is all about customer.address
class Order:
    def shipping_label(self) -> str:
        c = self.customer
        return f"{c.address.street}, {c.address.city} {c.address.postal_code}"
```

这个计算完全是关于地址的；它想住在 `Address`（或 `Customer`）上，而不是 `Order`。

## 怎么办

通常的解法是 [move-function.md](./move-function.md)：把方法搬到它所嫉妒的数据所属的对象上。如果只有方法的一部分有嫉妒，先用 [extract-function.md](./extract-function.md) 隔离那一部分，再搬走提炼出的片段。搬完之后，原来的调用点变成请正确的对象做这件事（`address.formatted()`），对内部结构的依赖随之消失。

指导性问题就是信息专家的那个：哪个对象持有这段逻辑需要的数据？把逻辑放到那里。结果通常是更少的耦合、更丰满的对象，以及读起来是请求而非盘问的调用点。

## 什么时候可以接受

依恋情结是启发式，不是定律。好几种正当的模式看起来像嫉妒，应当放着不管：

- **工具函数和纯函数。** 一个全部职责就是操作传入数据的函数——格式化器、序列化器、对值对象的计算——本来就*应该*使用那份数据。把它搬到数据类上并不总是更好，尤其在函数式风格里，行为住在以数据为输入的具名函数中。函数式核心（functional core）刻意把数据和作用于其上的函数分开。
- **横切关注点。** 日志、指标、鉴权和事务处理，本质上必须触碰其他对象的数据才能完成自己的工作。那是它们的本性，不是放错位置。
- **数据传输与映射。** 一个从对象 `A` 读出、构造对象 `B` 的映射器，不可避免地会访问 `A` 的大量字段。那正是映射器的意义所在；它不是嫉妒。
- **数据是透明的记录。** 从一个没有不变量的 `dataclass` 或 DTO 里取字段没问题；没有行为被晾着，因为记录本来就没打算拥有行为。Tell-Don't-Ask 对读模型和 DTO 的例外适用于此。
- **搬移会制造更糟的耦合。** 如果"归属"对象是一个稳定的第三方类型，或一个你不想用单一调用方的关注点来塞胖的类，把逻辑留在原地可能是更小的代价。

判断标准是：行为依赖的是另一个对象的*内部细节*（搬走它），还是仅仅*消费它的公开数据作为输入*（通常没问题）。基本类型偏执常常藏着嫉妒：当行为嫉妒一个无法拥有方法的基本类型时，真正的修复是引入一个能拥有方法的值对象；见 [primitive-obsession.md](./primitive-obsession.md)。
