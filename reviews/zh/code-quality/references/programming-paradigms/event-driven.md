# 事件驱动架构

## 是什么

事件驱动架构把事件当作一等事实：某事发生了，这个事实被记录并发布，而不是直接触发某段已知的代码。生产者发出一个事件（`OrderPaid`、`FileUploaded`、`user.signup`），不知道也不关心谁消费它。消费者订阅自己关心的事件。两者之间的耦合是事件 schema，而不是直接的函数调用。

它出现在许多尺度上：进程内的信号与钩子（Django signals、pytest hooks、Qt signals）、应用内的发布/订阅，以及跨服务的消息队列或事件总线（Kafka、RabbitMQ、SQS、Redis streams）。统一思想是同一个：反转依赖，使*引起*状态变化的东西不持有对所有必须*响应*它之物的引用。

## 背后的假设

- 生产者与消费者因不同的原因变化，应当能独立地部署、测试和推理。
- "某事发生了"是比"调用这个特定处理器"更耐久的接口。新增响应可以不触碰生产者。
- 对某些系统，事件日志本身就是有价值的：一份只追加的事实记录是天然的审计轨迹，也是重放的基础。

## 什么时候适用

- **解耦生产者与消费者。** 一个动作需要触发好几个互不相关的响应（发邮件、更新分析、使缓存失效），而你不想让发起代码知道它们全部。
- **审计轨迹与事件溯源。** 事件序列*就是*事实来源；当前状态是一个投影。这带来重放、时间查询和内建的审计历史。
- **异步工作流。** 不应阻塞请求路径的工作——通知、索引、下游处理——天然表达为"发事件，让 worker 处理"。
- **扩展点。** 插件与钩子让第三方响应生命周期事件，而不修改核心代码。

## 风险

事件驱动系统用显式控制流换取解耦，这笔交换有真实代价：

- **隐藏的控制流。** 你读一个生产者无法知道接下来发生什么；响应在别处。这与 [declarative.md](./declarative.md) 提到的调试困难是同一问题，且被放大了：调用图是在运行时通过订阅组装出来的。
- **顺序与投递。** 事件可能乱序到达、被投递多次、或丢失。消费者通常必须幂等（处理同一事件两次不产生额外效果）；这也是 [state-machine.md](./state-machine.md) 对重复事件所需要的性质。
- **错误上下文。** 当消费者失败时，失败在代码和时间上都远离生产者。重建"是什么导致了它"需要关联 ID 和良好的事件元数据。
- **事件风暴 / 级联。** 一个事件触发发出更多事件的处理器，又触发更多处理器。不小心就会无界扇出或成环。

## 消费者失败与投递保证

直接函数调用有一条显而易见的失败路径：调用者看到异常。事件没有这种清晰性，所以消费者失败需要显式的策略。三个问题决定设计：

- **消费者抛异常时发生什么？** 在同步的进程内总线里，一个失败的处理器可能中止其余处理器，除非各自被隔离。决定一个失败的响应应当阻塞其兄弟还是被包容。
- **投递语义是什么？** 至多一次（发出后失败即丢弃）、至少一次（重试直到被确认，所以消费者可能看到重复）、或恰好一次（在传输层通常是虚构的，用幂等消费者加去重来近似）。大多数持久化 broker 给的是至少一次，这正是幂等性不可省略的原因。
- **毒消息去哪？** 一个总是让消费者失败的事件不能永远堵住队列。死信队列捕获反复失败的事件以供检查，而不是无限重试。

贯穿线：用直接调用时，失败契约是隐式而显而易见的；用事件时，你必须刻意设计它，因为出任何问题时生产者早已走远了。

## 与观察者模式的关系

观察者模式是事件驱动设计最小的、进程内的实例：主体维护一个观察者列表，变化时通知它们。事件驱动架构把它一般化："主体"变成事件总线或 broker，通知变成发布，观察者变成可能住在其他进程或服务里的订阅者。同样的依赖反转适用；差别在于传输、持久性以及投递是否同步。当解耦是本地且同步的，普通观察者（或一个简单的回调列表）就够了；只有当你需要跨进程投递、持久性或异步处理时，才动用 broker。

## 事件 vs 命令

一个值得保持清晰的区分：*命令*告诉一个特定处理器去做某事（`SendEmail`、`ChargeCard`）并期望它发生；*事件*宣告某事已经发生（`OrderPaid`、`EmailSent`），对谁响应不作任何要求。命令是有向的，通常恰好有一个处理器；事件是广播的，可能有零个、一个或多个。混淆两者——把事件命名成命令，或把已发布的事件当作某个特定消费者必须处理——会悄悄重新引入事件驱动设计本来要消除的耦合。用过去时把事件命名为事实；如果你发现自己在乎*哪个*消费者运行，你想要的多半是直接调用或命令，而不是事件。

## 同步 vs 异步投递

改变事件系统整体性质的一个选择是：`publish` 阻塞到处理器完成（同步），还是交出后立即返回（异步）。同步的进程内投递易于推理——生产者的调用栈仍包含处理器，异常传播回来，顺序确定——但它把生产者的延迟与失败耦合到消费者身上，部分抵消了解耦。异步投递（队列、broker、后台任务）恢复了解耦，但引入了所有分布式系统问题：至少一次投递、顺序、部分失败，以及对幂等消费者的需求。当响应廉价、本地、且必须在生产者继续之前完成时选同步；当响应缓慢、远程、或真正独立于生产者的成败时选异步。
