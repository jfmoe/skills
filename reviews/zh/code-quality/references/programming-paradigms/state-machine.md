# 状态机 / 有限状态模型

状态机把一个过程建模为：一组有限的具名状态、一组事件、以及支配状态间移动的规则。它回答具体问题：系统能处于哪些状态、接受哪些事件、哪些转换合法、非法转换如何被拒绝、转换期间执行哪些副作用。这个模型有用，是因为许多日常 bug 都是非法状态 bug。

它不是 GoF 状态模式的同义词。那个模式只是状态机的一种*面向对象实现*。这个模型更宽泛，可以表达为转换表、`Enum` 加分派、`match` 语句、纯 reducer 函数，或状态对象。

## 概念

状态机把工作流捕获为数据：一个事物能占据的模式、驱动它的触发器、以及对一切不被允许之事的策略。把合法移动显式化，能把"我们忘了处理已取消订单被支付的情形"从潜在的生产 bug，变成一条你能看见并评审的缺失表项。

## 核心模型

- **状态（State）**：系统占据的一个具名、互斥的模式（`draft`、`submitted`、`paid`）。任何时刻它恰处于一个状态。
- **事件（Event）**：可能引起转换的具名触发器（`submit`、`pay`、`cancel`）。事件是从状态机外部到来的事实或命令。
- **转换（Transition）**：响应一个事件、从一个状态到另一个状态的合法移动：`(state, event) -> next_state`。
- **守卫（Guard）**：转换的前置条件。即使转换存在，守卫也可以阻止它：余额充足、权限有效、资源仍在。
- **动作（Action）**：转换被采取时执行的副作用：写数据库、发消息、发事件、记审计条目。
- **非法转换处理**：针对当前状态不接受的事件的显式策略：抛错、拒绝、或空操作。这是一个决策，永远不是一条悄悄什么都不做的未处理分支。

## 什么时候适用

- 状态是有限的、可命名的，事件也是有限的、可命名的。
- 非法转换要紧：从 `cancelled` 走到 `shipped` 必须是不可能的，而不仅仅是概率低。
- 生命周期正确性是领域的一部分：订单、审批、订阅、协议/连接状态、任务与 worker 生命周期。
- 你需要审计*为什么* `A -> B` 被允许而 `A -> C` 不被允许，常常是为了合规。
- 过程与持久化、重试或并发打交道，精确的"当前状态"概念能防止数据损坏。

## 什么时候不适用

- 没有分支、也没有非法步骤概念的简单线性流程。
- 微小而显而易见的分支——一个布尔字段或一个单独的 `if` 已经读得很清楚。
- 没有真正的非法状态概念：任何值跟在任意值之后都无害。
- 为一个两状态问题预建"每状态一个类"；那是类爆炸，不是建模。

## 典型实现

- **Enum + 转换表**：一个 `dict[(State, Event), State]`。规则稳定时最清晰的默认选择。一眼可评审，极易测试。
- **纯 reducer**：一个无副作用的 `(state, event) -> new_state` 函数，动作由命令式外壳执行。与 [functional-core.md](./functional-core.md) 天然搭配。
- **`match`/`case`**：适合局部的、结构化的、分支适度的转换。它是表达转换的语法，不是状态机本身。
- **分派映射**：当每个事件携带不同的处理逻辑时，用 `dict[Event, Callable]`。
- **状态对象（GoF State）**：当每个状态真实地拥有大量差异化行为时（连接状态、编辑器模式、协议阶段）。
- **库 / 工作流引擎**：当你需要持久化、可视化或动态配置、且确有真实需要时——而不是投机。

## 状态设计

- 状态必须**互斥**。如果两个可以同时为真，它们就不是一台机器的状态；它们是两台机器或两个维度。
- 用**领域术语**命名状态（`awaiting_payment`），而不是实现术语（`flag2_set`）。
- **避免用布尔组合**充当隐式状态。`is_active`、`is_locked`、`has_failed`、`is_retrying` 四个独立布尔编码了 16 种组合，其中大多数非法且没有任何一种被定义。把它们塌缩成一个具名状态枚举。
- 把**事件建模为动词或事实**（`pay`、`OrderPaid`），与状态区分开。混淆两者（"`paying` 事件"）是模型含混的信号。

## 转换表 / 状态图

每个非平凡的工作流都值得一张显式的转换表或状态图。它可以是代码（程序实际执行的字面量字典）或文档（Markdown 表格或状态图）。代码形式最好，因为它不会偏离行为。要点是有人能在一处看到全部合法移动，并问"这完整吗？这正确吗？"，而不必在代码库里追踪散落各处的条件语句。

```python
from enum import StrEnum


class Order(StrEnum):
    DRAFT = "draft"
    SUBMITTED = "submitted"
    PAID = "paid"
    CANCELLED = "cancelled"


class Event(StrEnum):
    SUBMIT = "submit"
    PAY = "pay"
    CANCEL = "cancel"


TRANSITIONS: dict[tuple[Order, Event], Order] = {
    (Order.DRAFT, Event.SUBMIT): Order.SUBMITTED,
    (Order.SUBMITTED, Event.PAY): Order.PAID,
    (Order.DRAFT, Event.CANCEL): Order.CANCELLED,
    (Order.SUBMITTED, Event.CANCEL): Order.CANCELLED,
}


class InvalidTransition(ValueError):
    pass


def apply_event(state: Order, event: Event) -> Order:
    try:
        return TRANSITIONS[state, event]
    except KeyError as exc:
        raise InvalidTransition(f"{state} cannot handle {event}") from exc
```

## 评审模型

按顺序分三遍评审一个状态机：

1. **完整性**：所有状态都枚举了吗？所有事件呢？每个 `(state, event)` 对要么是一个有意的转换、要么是一个有意的拒绝吗？终态被标识出来了吗（`closed`、`cancelled` 不再接受任何事件）？
2. **正确性**：守卫正确且完备吗？动作是幂等的吗，重放或重试的事件会不会重复扣款或重复发送？并发施加安全吗（两个事件在同一实体上竞争）？
3. **表示**：只有现在才问用表、`match` 还是状态对象来表达最好。先把模型搞对，再争论形式。

## 快速信号

看到以下情况时考虑这个模型：

- 状态字符串在散落各处被赋值，没有合法集合的单一定义。
- 布尔标志组合充当状态，没有被强制执行的合法组合。
- `if/elif` 阶梯内联地同时检查当前状态*和*传入事件，并在好几个函数里重复。
- 重复的事件造成重复的副作用；这是动作不幂等、转换没被把门的信号。

## 误报边界

单独一个状态枚举**不是**状态机；在有支配其变化的转换规则之前，它只是个具名值。给真正琐碎的分支加转换表是过度设计；如果只有一条显而易见的线性路径、也没有非法状态的顾虑，表就是仪式。当非法转换是真实的、正确性要紧时，这个模型才挣得自己的分量。在那里应用它，而不是在每个出现状态字段的地方。状态加行为何时应归属一个对象，见 [object-oriented.md](./object-oriented.md)；表形式为何如此可评审，见 [declarative.md](./declarative.md)。
