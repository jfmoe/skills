# 声明式编程

## 是什么

声明式编程描述你*想要*什么——目标、约束、数据的形状——而把*怎么做*留给框架、库或引擎。你写的不是步骤，而是一份描述，让别的东西去执行它。SQL 是典型例子：你陈述想要的结果集，查询规划器决定如何产生它。配置文件、schema、路由表、CLI 参数定义、校验规则和规则引擎，都是声明式的。

在 Python 项目里，声明式风格出现得比人们注意到的多得多：`pyproject.toml`、`dataclass` 的字段列表、`TypedDict`、`argparse` 解析器、Web 框架的路由装饰器、权限表、状态机的转换表。它们每一个都是被某个引擎解释的数据，而不是你逐句步进的代码。

## 背后的假设

- 有些结构作为*数据*比作为命令式代码更容易检查、组合和记录。
- 框架或库可以拥有重复的执行逻辑，于是你的代码只表达与默认不同之处。
- 当规则稳定、执行模型被充分理解时，把规则声明出来能消除样板、集中事实来源。

## 什么时候适合

- 项目与工具配置：`pyproject.toml`、Ruff、pytest、pre-commit。
- Schema 与类型定义：`dataclass` 字段、`TypedDict`、Pydantic / FastAPI 模型、序列化元数据。
- 由框架执行的结构性定义：CLI 参数、Web 路由、权限表、映射表、转换表。
- 查询与变换：SQL、查询构造器、声明式数据映射。

共同线索：稳定的结构、定义良好的执行引擎，以及拥有一个单一可检查的事实来源的好处。

一个从命令式到声明式转变的小例子。命令式分派：

```python
def handle(event: str) -> None:
    if event == "submit":
        do_submit()
    elif event == "pay":
        do_pay()
    elif event == "cancel":
        do_cancel()
    else:
        raise ValueError(event)
```

声明式分派；映射*就是*逻辑，一个小引擎应用它：

```python
HANDLERS: dict[str, Callable[[], None]] = {
    "submit": do_submit,
    "pay": do_pay,
    "cancel": do_cancel,
}

def handle(event: str) -> None:
    try:
        HANDLERS[event]()
    except KeyError:
        raise ValueError(event) from None
```

声明式形式让全部用例在一处可见、极易扩展，并且能作为数据被检查、计数和测试。代价是"什么在何时运行"现在隔了一层间接——这正是下一节要讲的取舍。

## 什么时候变成问题

- 声明背后藏着真实的控制流，但执行顺序和错误位置不可见。当声明式管道失败时，栈轨迹指向框架内部，而不是你的意图。
- 配置膨胀到事实上变成一门编程语言：用 YAML 或 TOML 表达的条件、循环和模板，却没有任何语言工具支持。
- 一个 DSL 或扩展点"为了灵活性"而建，却恰好只有一个调用点。那是投机性结构；见 [yagni](../design-principles/yagni.md)。
- 调试需要理解引擎的求值模型，而那个模型文档糟糕或出人意料。

声明式风格用显式控制流换取简洁。当引擎可信、结构稳定时，这笔交换值得；当你需要看见并步进实际发生的事情时，它有害。

一个实用的检验：如果新人问"这运行起来会发生什么？"，而诚实的回答需要先解释引擎的求值模型才能作答，那这份声明可能吸收了太多逻辑。声明应当描述*事实与结构*；它们一旦开始描述*顺序与决策*，命令式形式通常更清晰。

## 与其他范式的关系

- [state-machine.md](./state-machine.md) 的转换表是声明式的：合法移动是数据，由一个小引擎应用。
- 声明式配置喂给命令式外壳（[imperative.md](./imperative.md)），由它读取并行动。
- 声明式与数据导向设计大量重叠：两者都把结构当作可检查的数据而非行为。差别在侧重：声明式关乎把执行交给引擎，数据导向关乎把数据本身建模好。
- "更声明式"本身永远不是目标。目标是让规则和数据形状居中、可检查、可记录。当一份声明不再能作为事实来读、而开始隐藏一个决策时，那就是退回到显式代码的信号。
