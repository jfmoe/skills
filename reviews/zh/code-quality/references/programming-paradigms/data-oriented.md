# 数据导向设计

## 是什么

数据导向设计从数据出发，而不是从行为出发。它不问"存在哪些对象、它们能做什么"，而是问"数据的形状是什么、它如何流经系统、它经历哪些变换"。你伸手取用的结构是朴素的：schema、表、记录、类型化字典、只当数据用的 dataclass。行为住在"数据进、数据出"的函数里，而不是绑定在数据上的方法里。

在它的起源地（游戏引擎、高性能系统），这个词带有关于内存布局和缓存局部性的强主张。在普通应用代码里，更有用的含义更宽泛也更安静：显式地为数据建模，让数据的形状驱动程序的结构。大多数 ETL 任务、API 边界、配置系统和批处理器本质上都是数据管道，按这个方式写出来最清晰。

## 背后的假设

- 数据有形状，而形状是程序中最稳定的东西：端点、规则和 UI 的变化都比核心记录频繁。
- 把数据（惰性结构）与行为（作用于其上的函数）分开，让两者都更容易检查、序列化、版本化和测试。
- 对管道形状的问题，"这份数据穿过哪些变换"是比"哪些对象在协作"更诚实的分解。

## 什么时候适用

- **ETL 与数据管道。** 记录流经解析、校验、变换、聚合和写出各阶段。每个阶段是一个从数据到数据的函数；这是数据导向设计和 [functional-core.md](./functional-core.md) 从两个角度描述同一个系统。
- **API 边界。** 请求体和响应体是数据。用单一事实来源的 schema（dataclass、TypedDict、Pydantic）为它们建模，把处理器逻辑保持为对这些数据的变换。
- **配置。** 配置是声明式数据（见 [declarative.md](./declarative.md)）；在边界把它解析成类型化结构，然后把这个结构向内传。
- **批处理。** 每条记录的规则是作用于纯记录的纯函数；外围的循环、检查点和 I/O 是命令式外壳。

## 与函数式风格的关系

数据导向设计和函数式编程是亲密盟友。函数式风格说"偏好作用于数据的纯函数"；数据导向设计说"让数据显式化并让它带路"。合在一起它们产生同一种架构：近似不可变的记录流经纯变换，副作用被推到边缘。差别在侧重——一个从函数出发，一个从记录的形状出发——实践中它们收敛。

## 什么时候带行为的对象更好

数据导向立场恰好在数据有必须始终成立的不变量时失效。纯记录是惰性的：没有什么能阻止调用方把它们放进非法组合。当一个概念有关于哪些字段组合合法的规则、有生命周期、或有必须与其状态保持一致的行为时，一个封装该状态并守护其不变量的对象是更好的模型；见 [object-oriented.md](./object-oriented.md)。

纯数据用过头的信号：

- 同一份记录的校验逻辑被复制粘贴到每个触碰它的函数里，因为没有唯一的地方拥有这条不变量。
- 调用方能构造出本应不可能的字段组合（[state-machine.md](./state-machine.md) 的"布尔标志汤"坏味道）。
- "数据"开始长出好几个函数需要共享并保持一致的行为。

到那时，封装。纯数据用于有效性是产出它的边界之属性的记录；对象用于有效性必须被持续维护的概念。

## 一个具体形态

数据导向管道读起来像一串作用于显式记录的变换，每个阶段是从数据到数据的纯函数：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class RawRow:
    name: str
    amount: str


@dataclass(frozen=True)
class Charge:
    name: str
    cents: int


def parse(row: RawRow) -> Charge:
    return Charge(name=row.name.strip(), cents=round(float(row.amount) * 100))


def charges(rows: list[RawRow]) -> list[Charge]:
    return [parse(r) for r in rows]
```

记录不携带行为；函数不携带状态。读、写和检查点发生在外围的命令式外壳里，不在这些函数里。正是这种分离让每个阶段可以用字面量数据测试，并能组合进更长的管道。

## 让非法数据难以表示

认真对待数据的一个更安静的好处是：选得好的形状能在任何逻辑运行之前就消灭整类 bug。如果一个字段只能取三个值之一，建模成枚举，而不是自由字符串。如果两个字段必须同生共灭，把它们放进嵌套记录，而不是两个独立的可选字段。如果一个列表必须非空，值得在边界编码或检查一次。这门纪律是把有效性推进数据的形状里，让下游函数能信任自己的输入而不必重新检查。这与 [state-machine.md](./state-machine.md) 拒绝让布尔标志编码状态是同一种直觉；类型是第一道防线。

这项工作发生在边界。把不可信输入（JSON、配置、请求体）一次性解析成类型化结构，边解析边校验，让边界之内的一切都操作可信的形状。这就是"解析，而非校验"（parse, don't validate）：把原始数据转换成一个其存在即保证其有效性的结构，而不是把原始数据传来传去、四处撒校验检查。
