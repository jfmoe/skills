# SOLID

SOLID 是五条面向对象设计原则的集合——单一职责、开闭、里氏替换、接口隔离、依赖倒置——由 Robert C. Martin 以*依赖管理*之名汇集在一起。它们的共同目的是控制耦合和变更的方向，使系统在增长时保持灵活、健壮、可复用。

在讲原则本身之前先有两点框架性说明。第一，应用的单元不总是类。这里的"模块"可以是函数、模块、包或服务对象；Python 很少需要 Java SOLID 示例所假设的那种每概念一类的密度。第二，这些是审查*问题*，不是模板。价值在于问"这里什么在变、契约是什么、依赖边界在哪里"，而不是机械地产出接口和工厂。当作模板用时，SOLID 会产生违反 [kiss.md](./kiss.md) 的类爆炸和间接层。

## 单一职责原则

SRP 通常表述为"一个模块应该只有一个变更理由"。"变更理由"的表述比流行的误读"一个类应该只做一件事"更重要。职责绑定到一个*变更来源*：一个行为者、一个利益相关方、一条独立演化的规则。正确的粒度来自内聚性，而不是最小化每个单元做的事。

SRP 捕捉的坏味道：一个模块混合了业务规则、展示格式化、持久化和外部 API 适配，于是对其中任何一项的修改都会危及其他项。人们*应用* SRP 时犯的错误：把一个内聚的对象砸碎成许多贫血的辅助件，从而散落了逻辑、降低了内聚。要问"这段代码响应的是不止一种规则、角色或外部系统吗？"，而不是"这个函数做了不止一件小事吗？"在入口点，解析、配置、日志和依赖装配可以放在一起；业务规则应该移出去到核心里。

## 开闭原则

OCP：稳定的核心应该对扩展开放、对修改关闭；你通过添加新的实现、策略或配置来增加行为，而不是每次都重新打开并编辑核心。现代、实用的读法是有条件的：只有当变化的*方向*稳定且变化确实反复出现时，扩展点才值得建造。

这让 OCP 与 [yagni.md](./yagni.md) 直接对峙。为一个假设中的第二个实现建造插件架构是投机性通用化。解决之道：从一个简单的分支或映射开始；只有在真实的第二个（最好是第三个；见 [rule-of-three.md](./rule-of-three.md)）变化出现之后，才引入注册表、分发表或 Protocol。在 Python 中，扩展机制通常是注册表、入口点、配置到函数的映射、`Protocol`、装饰器或策略函数——不一定是继承层级，后者容易产生脆弱基类。

## 里氏替换原则

LSP：子类型必须能在任何期望其基类的地方使用，而不破坏程序的期望。关键词是*行为*，不是签名。方法名和类型匹配是必要但不充分的；子类型还必须遵守基类的前置条件（不要求更多）、后置条件（不承诺更少）、不变量和异常语义。

经典违反：子类收窄了方法接受的输入、把继承来的方法变成空操作或 `raise NotImplementedError`、或纯粹为了复用代码而继承、并无真实的 *is-a* 关系。在 Python 中，鸭子类型和 `Protocol` 只表达结构；行为契约仍然住在测试和文档里。当你只想复用实现时，优先选择组合、一个小 mixin 或辅助函数而非继承，这样你就永远不会许下无法兑现的可替换性承诺（见 [composition-over-inheritance.md](./composition-over-inheritance.md)）。

## 接口隔离原则

ISP：客户端不应被迫依赖它们不使用的方法。一个宽大的"上帝接口"把每个客户端耦合到每一次变更，并迫使测试替身实现无关的方法。按真实调用方实际需要的来切分接口。

在 Python 中，这很少意味着 Java 风格的接口类。使用小 `Protocol`、普通可调用对象、模块级函数，或一个只携带调用方所需能力的参数对象。不要为每个函数都造一个接口；内部的一次性调用不需要声明的接口：让函数只接受它真正用到的对象即可。一条好的启发式：当测试替身不得不为被测代码从不调用的方法打桩时，接口就太宽了。

## 依赖倒置原则

DIP：高层策略不应依赖低层细节；两者都依赖抽象，而抽象由高层代码需要什么来定义（而不是从细节泄漏上来）。这让业务规则免于数据库、HTTP、文件系统、时钟、随机数和框架的具体细节。依赖注入是实现 DIP 的一种*技术*：从外部传入依赖，而不是在内部构造或查找。完整论述见 [dependency-inversion.md](./dependency-inversion.md)。

常见错误是把 DIP 等同于 DI 容器，或对永远不需要替换的稳定标准库代码也做倒置。在 Python 中，优先选择构造函数参数、函数参数、小 `Protocol` 和工厂函数，在组合根（`main()`、应用启动、框架入口）处装配具体依赖。

## SOLID 的张力与滥用

每条原则都把人拉向更多结构：更多接口、更多间接、更多注入点。不加判断地应用，整套原则产出的正是 [kiss.md](./kiss.md) 和 [yagni.md](./yagni.md) 所警告的过度设计、难以阅读的代码。具体的张力：OCP vs YAGNI（扩展点 vs 投机）、ISP vs 简单（接口数量）、DIP vs 简单装配（间接 vs 可追踪性）。纪律是：把 SOLID 应用在变更频繁且代价高的地方——长生命周期的业务系统、库、框架、SDK、插件点——对小脚本和稳定模块则不去打扰。把 SOLID 当作一组关于变更与耦合的审查问题，并让 Python 的函数、Protocol、组合和参数注入成为默认答案，而不是 ABC 和容器。
