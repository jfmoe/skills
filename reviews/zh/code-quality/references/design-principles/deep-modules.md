# 深模块与信息隐藏

本文档取材自 John Ousterhout 的《A Philosophy of Software Design》。其核心思想是一种判断抽象质量的方法：比较其接口的成本与它所隐藏之物的价值。

## 深度：接口成本 vs 实现价值

每个模块都有两面：**接口**（调用方要使用它就必须理解的东西）和**实现**（接口背后的一切）。Ousterhout 把模块质量表述为两者之间的比率：

- **深模块**拥有一个简单的接口，背后隐藏着大量有用的复杂度。调用方学得少、得到多。垃圾回收器、设计良好的文件系统 API、或 `requests.get(url)` 都是深模块：调用起来轻而易举，幕后却大有乾坤。
- **浅模块**的接口几乎和它的实现一样复杂。调用方仅仅为了使用它，就要付出几乎等同于理解其内部全部的成本，因此模块提供的净收益很小。一个签名复述其函数体的单行包装器就是极端例子。

模块的价值不在于它的大小。深模块内部可以很大；重要的是接口相对于它所吸收的复杂度而言很小。这重构了抽象的目标：不是"藏代码"，而是"让调用方可以忽略他们不需要推理的复杂度"。

## 信息隐藏

深度背后的机制是信息隐藏：每个模块封装一个设计决策——尤其是一个可能变更的决策、或一个难以做对的决策——使其他模块不依赖它。当被隐藏的决策发生变化时，变更保持在局部。

它的反面是**信息泄漏**：当一个设计决策出现在多个模块中时，一次变更就迫使所有模块都被修改。读取方和写入方都知道的存储格式、对每个调用方可见的线路协议细节、跨层复制的错误映射约定——这些都是泄漏。泄漏是[霰弹枪手术](../refactoring/shotgun-surgery.md)这类坏味道背后更深层的原因，而信息隐藏则是 [DRY](./dry.md) 应用于设计决策（而不仅仅是代码）的方式：知识只存在于一个模块中。

## 什么是好的抽象

- 它隐藏了真正值得隐藏的东西：一个困难的算法、一个易变的依赖、一个协议细节、一组错误与版本差异。
- 它的接口用调用方已经在思考的术语表达，而不是用实现的术语。
- 它不会强迫调用方必须知道正确的调用*顺序*或内部状态才能正确使用。需要这类知识本身就是一种泄漏的复杂度。
- 常见情况调用简单；罕见情况虽可能，但不会让常见路径复杂化。

一个常见的反模式是**透传方法**：一个除了用相同签名调用另一个方法之外什么都不做的方法。它增加了接口面积和间接层，却没有隐藏任何东西，使模块变得更浅。同样适用于那些只是给单个表达式改名的薄包装函数：见 [DRY](./dry.md) 关于浅辅助函数的论述。

## 与 KISS 和接口设计的关系

深模块让 [KISS](./kiss.md) 更锐利。"保持简单"并不意味着每个函数都必须短；它意味着最小化读者必须记在脑子里的复杂度。少数几个接口干净的深模块，留给读者的总复杂度要少于许多迫使读者在文件之间不断跳跃的浅辅助函数。为了短函数和小文件本身而追逐它们，会产生浅模块和*更多*需要学习的接口：这恰是简单的反面。

深度也调和了[接口隔离](./solid.md)那种小接口的本能：目标是相对于所交付之物而言*小*的接口，而不是切得薄到调用方必须组装许多个才能完成任何事。

## 这一原则被误用的情形

- 把信息隐藏理解为"把每个字段设为私有并加 getter/setter"。机械地暴露每个字段的访问器什么都没隐藏，只是增加了面积。一个简单数据载体的透明 dataclass 没问题；只有当存在不变量或可能变更时才需要封装。
- 隐藏调用方合理需要的东西：必要的配置、有意义的错误、或真实的性能成本。隐藏成本并不会消除它；只是让调用方日后感到意外。
- 为了满足文件大小或函数长度偏好，把一个连贯的深模块拆成浅碎片。
