# 迪米特法则

迪米特法则（LoD），又称最少知识原则，说的是一个单元只应与它的直接朋友交谈，避免穿过一个对象去操作它返回的对象。一个方法应该与以下对象交互：它自己的对象、作为参数传给它的对象、它创建的对象，以及它的直接组件。它不应导航一长串中间对象去够一个遥远的目标。

要点不在于一个表达式里有几个点。要点在于调用方被迫了解多少它并不拥有的对象的内部结构。当调用方走过 `a.b.c.d` 时，它已经硬编码了对三层结构的知识，而那一结构的任何变化都会向外波及每一个走过同一条路径的调用方。

## 它解决什么问题

结构耦合。当代码穿过对象时，它依赖的就不只是它的直接协作者，而是该协作者所暴露的一切的形状。图深处的一次变更——重命名一个字段、插入一个中间对象、改变一个类型——会传播到遥远的、看似无关的调用点。这正是霰弹枪手术的经典症状：一次小小的结构变更迫使许多地方被修改。

LoD 促使你给你的直接协作者一个表达*你想要什么*的方法，由协作者（它拥有结构）决定*如何*得到它。关于结构的知识留在结构所在的地方。

## 火车残骸

"火车残骸"是一长串像连挂车厢一样串起来的访问器：

```python
zip_code = order.customer.address.zip_code        # train wreck
tax_rule = order.customer.account.region.tax_rule # train wreck
```

调用代码现在知道了订单有客户、客户有地址、地址有邮编。如果 `Address` 日后被拆分，或 `Customer` 增加了一层间接，每一条这样的链都会断。修法是向最近的对象用领域术语索取答案：

```python
zip_code = order.shipping_zip_code()
needs_review = order.requires_tax_review()
```

订单现在拥有这次遍历。调用方表达意图；结构保持隐藏。这直接连接到 [Tell, Don't Ask](./tell-dont-ask.md)：不是跨好几跳把数据拉出来在外部做决策，而是给数据的所有者一个回答这个问题的方法。

## 何时重要

- 链式访问驱动业务规则的领域对象
  （`order.customer.address.zip_code` 决定税务行为）。
- 穿过仓储、客户端或响应对象深入其内部结构的调用方，把自己耦合到了那个内部布局上。
- 深入对象图打猴子补丁的测试：深层 mock 是一个坏味道，说明被测代码对遥远结构知道得太多。

在这些情况下，一次结构变更的波及面很大，LoD 是寻找在哪里添加语义方法的有用透镜。

## 何时过于严格

当被机械地应用为"数点、然后禁止"时，LoD 就变成了噪音。

- **流式接口和构建器。** `query.filter(...).order_by(...).limit(10)` 是设计出来的链。每次调用返回的是同一个概念对象，而不是更深的内部对象。
- **数据遍历库。** Pandas、SQLAlchemy 查询和 `pathlib.Path` 链式调用都是惯用法。`path.parent.parent / "config.toml"` 不是耦合问题。
- **透明的数据载体。** 从 DTO 或类 JSON 结构读取 `response.json()["items"][0]["id"]` 是普通的数据访问，不是对行为的结构耦合。一个纯粹用作数据容器的 dataclass 可以被直接遍历。

判别标准始终是：*调用方现在是否知道了一些关于内部结构的东西，一旦改变就会弄坏它？* 如果链跨过的是稳定接口或透明数据，就不存在违反。如果链编码的是拥有行为和不变量的对象的私有布局，那才是 LoD 发挥作用的地方。

## 错误的强制方式

解药可能比病更糟。把每一条链都包进转发方法，会产生一堆琐碎的透传方法（`def zip_code(self): return self._address.zip_code`），它们不增加任何语义，只是把耦合往里挪了一层。那是浅包装器：见[深模块的讨论](./deep-modules.md)。只有当方法表达一个有意义的领域问题时才引入它，而不仅仅是为了去掉一个点。

## 相关原则

LoD 天然与[信息隐藏](./deep-modules.md)搭配：两者都减少外部世界对内部结构的依赖，都限制一次变更能传播多远。它也与 [Tell, Don't Ask](./tell-dont-ask.md) 和 GRASP 的[信息专家](./grasp.md)启发式重叠：三者都把行为推向持有其所需数据的对象。
