# 测试驱动开发

测试驱动开发（TDD）是一种由测试驱动开发反馈循环的工作流。你草拟一个行为清单，挑一个，写一个会失败的小型可运行测试，写刚好够让它通过的代码，然后重构。Martin Fowler 把这个循环概括为
**红-绿-重构**，并强调重构这一步不是可选的装饰。设计正是在这一步得到改进的。

TDD 本质上不是一种测试技术。它是一种恰好留下测试的设计技术。先写测试这一行为迫使你在接口还不存在时就使用它，从而尽早暴露别扭的签名和不清晰的职责。

## 红-绿-重构循环

1. **红。** 为一个小行为写一个测试，看着它失败。失败确认测试确实锻炼了某个东西，而不是在静默通过。
2. **绿。** 写能让测试通过的最简单代码。不是优雅的版本：够用就行。这里允许抄近路；下一步会清理。
3. **重构。** 在测试变绿并保护行为的条件下改进结构：重命名、提炼、消除重复。全程测试保持绿色。

纪律是保持每步小、并在每步之间运行测试。一个常见的失败是塌缩循环：在一个测试下写一大批代码，或把一次大的结构变更偷运进行为尚未稳定的绿色步骤。

## TDD 给你什么

- **设计反馈。** 先写测试意味着在实现 API 之前先消费它。痛苦的准备、过多的参数或难以构造的协作者会以测试之痛的形式显现，这是关于设计本身的信号。这与
  [dependency-inversion](./dependency-inversion.md) 相连：难测的代码往往是依赖未被注入的代码。
- **行为规约。** 测试套件以可执行的形式记录代码应该做什么，不会静默过期。
- **回归保护。** 一旦行为被测试钉住，未来破坏它的变更会响亮地失败。这种保护让激进的[重构](../refactoring/safe-refactoring.md)
  和 [YAGNI](./yagni.md) 变得安全。你可以推迟抽象、日后再重塑，而无需恐惧。

## 何时 TDD 有价值

TDD 在行为可枚举、答错的代价真实的地方回报最大：

- 纯函数、解析器、变换与序列化逻辑。
- 输入清晰、输出可期的领域规则：定价、验证、状态转换。
- 修 bug：先写复现 bug 的失败测试，再修。测试成为永久的回归守卫。
- API 设计：先使用接口，能看出它调用起来是否舒服。

## 何时严格 TDD 适得其反

TDD 假设你对期望的行为了解得足够多、足以写出测试。当你不了解时，严格的测试先行就成了摩擦：

- **探索性代码和探针（spike）。** 当接口甚至需求都还未知时，先写探针来学习，等形状稳定后再补特征化测试或契约测试。在这里强行测试先行，测的是猜测。
- **UI 和视觉布局。** 大量价值在于外观和交互，单元测试很难捕捉。测 UI 背后的逻辑，而不是像素位置。
- **胶水代码。** 主要委托给久经测试的库的薄装配代码，从一个只是重新断言库行为的测试中获益甚微。

把 TDD 当作一种高价值反馈策略，而不是对每一行的道德义务。目标是能工作的、设计良好的、行为覆盖充分的软件，而不是测试先行的仪式或覆盖率百分比的奖杯。一个没有有意义断言的测试只增加了覆盖率，别无其他。

## 与"先码后测"和行为覆盖的关系

先写代码再写测试不是罪过；重要的性质是行为被覆盖、且测试断言了真实的东西。TDD 相比先码后测多出的是红色步骤的设计压力。许多团队混用两者：核心逻辑和修 bug 用 TDD，先探索出来的代码用后补测试。两者都应针对合理边界上的可观察行为，而不是内部实现细节，这样测试才能在重构后存活。为什么深入内部的测试（深层 mock、给私有成员打补丁）是关于设计而不仅仅是测试的坏味道，见
[law-of-demeter](./law-of-demeter.md) 和 [dependency-inversion](./dependency-inversion.md)。
