# GRASP：通用职责分配软件模式

## 它是什么

GRASP 是一套由九条启发式组成的词汇表，针对的是最常见的设计问题：*这个职责应该放在哪里？* 这个行为属于哪里、哪个对象应该创建那个对象、谁来协调一个用例、一条规则放在哪里才能让变更保持封闭。与 GoF 模式不同，GRASP 模式不是你要搭建的结构；它们是好好分配职责的推理工具。它们天然与 SOLID（见 [solid.md](./solid.md)）和 [tell-dont-ask.md](./tell-dont-ask.md) 搭配。

主要的误用是把 GRASP 当作 UML 驱动的流程，或者把 "Controller" 读作 "web 控制器"，然后把业务逻辑堆进请求处理器。用得好时，GRASP 只是一种精确谈论职责摆放的方式。

## 九个模式

**信息专家（Information Expert）。** 把职责分配给拥有履行它所需信息的类或模块。行为会自然地趋向它所操作的数据。这是 [tell-dont-ask.md](./tell-dont-ask.md) 背后的引擎，也是"特性 envy"坏味道的解药——那种函数深入另一个对象的字段来做决策的情形。

**创建者（Creator）。** 把创建对象 B 的职责分配给聚合了 B、包含 B、紧密使用 B、或持有 B 初始化数据的类 A。它把构造放在构造知识本来就在的地方，降低耦合。当创建逻辑复杂到会发生变化时，Factory 就在这里变得合理。

**控制器（Controller）。** 把处理系统操作（一个用例）的职责分配给一个*不是* UI、也*不是*领域逻辑本身的协调对象。控制器的工作是薄协调：接收请求、委托给领域、返回结果。在 Python 中，CLI 命令处理器或 API 视图应当是这样的薄控制器，业务规则住在核心模块里。

**低耦合（Low Coupling）。** 分配职责时让模块之间的依赖保持低。更低的耦合意味着一处的变更传播到更少的地方，单元也更容易被独立测试和复用。它是一种需要平衡的力，而不是绝对标准；有些耦合是必要的。

**高内聚（High Cohesion）。** 分配职责时让每个模块的内容强相关且聚焦。高内聚是 [solid.md](./solid.md) 中 SRP 的正面表述；它让模块可理解，并给它单一清晰的变更理由。低耦合和高内聚要一起评估；只优化一个而忽略另一个会产生坏设计。

**多态（Polymorphism）。** 当行为随类型变化时，用多态（在 Python 中：鸭子类型、基于 `Protocol` 的分发、分发表、或 `functools.singledispatch`）来分配变化的行为，而不是用散落的 `if/elif` 类型检查。这把每个变体局部化，并让新增变体成为一次添加而非一次修改：这正是 OCP 背后的机制。

**纯虚构（Pure Fabrication）。** 当没有任何领域概念是某个职责的合适归宿时，发明一个非领域对象来承载它：一个服务、映射器、适配器、仓储或策略函数。这保持领域对象的内聚性，防止你仅仅为了满足信息专家而把基础设施关注点污染进领域对象。纯虚构是正当且常见的；需要警惕的是不要把它们滥用成垃圾场。

**间接（Indirection）。** 把职责分配给一个中间对象或函数，以解耦两个否则会直接耦合的单元（例如在你的核心与第三方客户端之间放一个适配器）。间接是低耦合的工具，但每一层都增加一次需要追踪的跳转；为真实的耦合问题而加，不要条件反射地加。

**受保护的变化（Protected Variations）。** 把预计的不稳定点包在稳定接口之后，使一侧的变化不会波及另一侧。这是统一 OCP、DIP、间接和多态的思想。关键词是*预计*；保护那些真实且已被识别的变化，而不是每一个*也许*某天会变的点，否则你就滑进了 [yagni.md](./yagni.md) 所警告的投机性通用化。
