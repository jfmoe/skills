# 依赖倒置与依赖注入

两个相关但不同的概念，常被混淆：

- **依赖倒置原则（DIP）：** 高层策略不应依赖低层细节；两者都应依赖抽象。抽象由高层代码需要什么来定义，而不是由低层代码碰巧提供什么来定义。
- **依赖注入（DI）：** 一种技术，对象或函数从外部接收其依赖，而不是自己构造或查找它们。DI 是实现 DIP 的一种方式，也是可测试性和边界隔离的主要杠杆。

DIP 是设计目标；DI 是一种机制。你可以不需要精心设计的框架就遵循 DIP，也可以完全不使用任何"DI 容器"就使用 DI。

## 高层模块依赖抽象

DIP 要解决的问题：直接调用数据库驱动、HTTP 客户端、系统时钟或 `random` 的业务规则，被焊死在那些细节上。策略再也无法在不拖上基础设施的情况下被阅读、测试或复用，而低层细节的变更会向上波及高层规则。

倒置依赖意味着高层代码把自己的需求表述为抽象——"我需要一个可以向它询问当前时间的东西"、"我需要一个可以保存订单的地方"——然后由具体实现去满足这个需求。抽象属于高层一侧。它由策略需要什么来塑造，而不是由低层库的完整表面来塑造。这与[接口隔离](./solid.md)是同一种直觉：保持接缝狭窄。

## DI 容器何时合理、何时过度

DI 容器（一种根据配置或注解构建并装配对象图的框架）解决的是大多数 Python 项目并没有的问题。构造函数注入加上一个小的组合根可以走得很远。只有当对象图确实庞大且动态时，容器才值回它的成本：许多可互换的实现、复杂的生命周期和作用域需求、跨许多模块的配置驱动装配。

对于典型应用，显式的组合根比容器更易读、易调试、易追踪。全局的*服务定位器*（一个代码伸进去取依赖的注册表）比两者都糟：它隐藏了它所满足的依赖，把 DI 的显式性又变回了隐式的全局耦合。优先选择把依赖传进去。

## 测试收益

DI 是通往可测试代码最干净的路径。当一个函数把它的时钟、它的仓储和它的 HTTP 客户端作为参数接收时，测试可以直接传入假对象或桩：无需对模块内部做猴子补丁，无需深入到实现去打补丁。这让测试耦合到边界（抽象）而非实现上，因此重构内部不会破坏测试。过度打 mock 和深层的 `patch` 目标，通常是依赖*没有*被注入的症状；修好接缝就能修好测试坏味道。另见
[tdd](./tdd.md)。

## 何时不应倒置

倒置每一个依赖本身也是一种过度设计。不要倒置：

- **稳定的标准库依赖和纯函数。** 调用 `json.dumps` 或纯辅助函数的代码不需要把它藏在 Protocol 后面；没有会变化的实现，也没有需要伪造的东西。
- **从不变化、也永远不需要测试替身的东西。** 一个恰好只有一个实现且没有测试接缝的抽象是投机设计（[YAGNI](./yagni.md)）。

倒置那些不稳定、不纯或可替换的边界：外部系统、时间、随机性、文件系统、网络。让稳定的核心保持直接。
