# DRY：不要重复自己

## 它是什么

DRY 是软件领域最被误解的原则之一。其最初的表述（Hunt 和 Thomas，《程序员修炼之道》）是关于*知识*的："每一项知识在系统内都必须有单一、明确、权威的表示。"它不是"不允许两段代码看起来相似"。值得去重的东西是一条领域规则、一个 schema、一个协议、一个变换、一个错误处理策略——是一个一旦改变就必须在所有地方同时改变的决策。

DRY 警告的危险是：同一项知识存在于好几个可能逐渐失步的地方。当一条税率规则、一个权限检查、一个状态转换或一个验证条件住在三个文件里时，未来的修改很可能漏掉其中一个，于是系统开始自相矛盾。

## 底层的假设

- 当同一项知识出现在多个地方时，未来的编辑最终会更新其中一些而漏掉另一些。
- 单一权威表示让变更只发生在一处。
- 但看起来相似的代码未必表达同一项知识。两个片段今天形状相同可能出于完全无关的原因，明天又可能被不同的力量驱动。

最后这一点正是好的 DRY 与坏的 DRY 的分界。这个原则针对的是知识，而不是文本。

## 重复的知识 vs 偶然的相似

问：如果其中一份副本背后的需求变了，另一份副本是否*必须*跟着变？如果是，它们编码的是同一项知识；去重。如果否，它们只是此刻碰巧相似；让它们各自待着。

真正知识重复的例子，值得消除：

- 同一条业务规则（价格计算、资格判断、状态机转换）在不止一个地方实现。
- 一个 schema、API 契约或数据模型在客户端、服务端和测试中重复。
- 一个重试或错误处理策略被复制粘贴到各个调用点。
- 一条数据变换规则在好几个函数中各自独立地表达。

偶然相似的例子，通常可以安全地保持分离：

- 两个恰好结构相同、但验证的是将独立演化的不同概念的验证函数。
- 两个样板相似但业务逻辑无关的请求处理器。
- 看起来重复、但钉住的是不同场景的测试准备代码。

## 何时抽象，何时容忍重复

当重复的东西确实是一条规则时立即去重，尤其是高风险知识：安全、权限、金钱、协议契约、数据一致性，以及任何 schema 的单一真实来源。对这些，不要等待；分歧的代价太高。例外结构见 [rule-of-three.md](./rule-of-three.md)。

当两个片段相似、但被不同的变更理由驱动、且共享抽象的形状尚不清晰时，容忍重复。过早的统一会选错接缝。你从两个案例中提炼出的"通用"函数，往往会随着第三、第四个案例的到来而长出布尔标志、模式参数、回调、特殊分支和隐式前置条件——此时它比当初的重复更难维护。这正是与 [kiss.md](./kiss.md) 的直接张力：一个带着许多参数和分支的抽象，可能比两份清晰分离的副本承载更高的认知负担。

## 错误的 DRY

两种失败模式占主导，而且在 agent 生成的代码中都很常见：

1. **过早抽象。** 在变化方向尚未知晓时，就统一两个偶然相似的片段。结果是一个参数化的怪物。当你发现这一点时，修法是内联这个抽象、重新复制代码，然后等真正的接缝自己显现。

2. **参数化 / 薄包装器泛滥。** 以"消除重复"之名，把一两行代码抽成许多小包装函数。这很少隐藏真正的复杂度。它增加命名负担、跳转成本、更深的调用栈，而且在 Python 中还有真实的每次调用开销，因为每次调用都要建一个栈帧。一个只是给单个表达式换成同义词的包装器是浅辅助函数，不是去重。如何识别和拆解这类包装器，见 [`skills/code-quality/references/refactoring/thin-wrapper-function.md`](../refactoring/thin-wrapper-function.md)。

在提炼辅助函数之前，先问它是否提供了稳定的语义边界、隐藏了真实的复杂度、或承载了一条可复用的策略。"被用了两次"并不够。这正是 Rule of Three 存在的原因。
