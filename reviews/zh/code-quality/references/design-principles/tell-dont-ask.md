# Tell, Don't Ask（命令，别询问）

Tell, Don't Ask 说：不要把数据从对象里拉出来、从外部替它做决策，而是把决策推进拥有数据的对象里。告诉对象你想要它做什么；不要向它打听内部情况，然后替它行事。

这个原则关乎*行为相对于它所依赖的数据住在哪里*。当数据和治理它的规则放在一起时，规则可以依赖对象维护的不变量，对这些规则的修改也只有一个家。当调用方反复读取字段并在外部组装规则时，逻辑散落各处，对象也无法保护自己的一致性。

## 问题的形状

"问"式代码读取状态并从外部分支决策：

```python
# Ask: caller pulls data out and decides
if account.balance >= amount and not account.is_frozen:
    account.balance -= amount
    account.last_debit = now()
```

每一个给账户扣款的调用方都必须记住同样的检查和同样的记账动作。如果出现新规则（透支限额、冻结、审计日志），每一处都需要更新，而任何忘掉的一处都会让账户处于非法状态。

"命令"式代码把决策移到内部：

```python
# Tell: object owns the rule and its invariants
account.debit(amount)   # raises if frozen or insufficient
```

账户现在执行自己的不变量。调用方表达意图。规则只有一个家，对象不可能通过这条路径被驱入不一致状态。

## 与封装的关系

Tell, Don't Ask 是从调用方一侧看的封装。封装说对象应隐藏内部状态；Tell, Don't Ask 说调用方本来就不该需要那些状态；它们应该把一个命令交给对象，并信任它维护自己的不变量。两者互相强化：一个暴露行为而非裸状态的对象，让数据保持私有且有意义。

它也与 GRASP 的[信息专家](./grasp.md)启发式（把职责分配给拥有履行它所需信息的类）和
[迪米特法则](./law-of-demeter.md)（不要穿过结构去做外部决策）重叠。三者都把行为推向数据。

## 何时"问"是恰当的

Tell, Don't Ask 是保护拥有行为的对象之不变量的指南。它不是对读取数据的禁令。当没有不变量需要保护时，"问"是正确的：

- **查询和报表。** 计算合计、聚合和摘要本质上要跨许多对象读取许多字段。强行把它塞进每个对象的命令方法会扭曲模型。
- **序列化和 DTO。** 把对象变成 JSON、一行记录或线路格式是纯粹的数据访问。数据传输对象或 API schema 应当直白地暴露其字段。
- **UI 渲染。** 展示代码读取模型状态来绘制它。这是它的本职；它并没有在做模型应该拥有的领域决策。
- **读模型。** 在读写分离的系统中，读侧刻意是面向数据且透明的。

判别标准：调用方是在*决定某件对象应该拥有的事*（一条业务规则、一次状态转换、一个不变量），还是在*报告 / 变换 / 展示*确实属于调用方关注点的状态？前者违反 Tell, Don't Ask；后者正常且健康。

## 常见错误

- **消灭所有 getter。** 有些读者把这个原则理解为对象永远不应暴露数据。那会破坏报表、序列化和 UI，并产生别扭的纯命令模型。查询没问题。
- **往 DTO 和 dataclass 里塞行为。** 纯数据载体应该保持是数据载体。给传输对象添加领域命令会模糊其边界，并把它耦合到它无权知道的规则上。只有当数据有不变量要保护时才给它添加行为。
- **把昂贵的工作藏在看似无害的属性后面。** 一个触发 I/O 或重计算的 `property`，会让期待廉价属性访问的调用方大吃一惊。Tell, Don't Ask 主张行为靠近数据，而不是把副作用伪装成属性读取。
