# YAGNI：你不会需要它

## 它是什么

YAGNI 说：不要为你只是想象的未来建造能力。这条原则经 Martin Fowler 提炼，针对的是*臆想的特性*和*投机性的抽象*：因为你猜以后会有用而现在就添加的功能或灵活性。它是一个关于时机的陈述：等真实需求到来时再建，而不是提前。

YAGNI 经常被错误引用为反对测试、错误处理或认真设计的论据。它不是。Fowler 明确表示，YAGNI 并不反对让代码易于修改的重构、测试和技术健康。事实上 YAGNI *依赖*这些东西。

## 为什么投机性建造的代价比看起来更大

Fowler 把一个臆想特性的成本拆成四部分：

- **建造成本**：花在尚不需要的东西上的时间，是从需要的东西那里拿走的。
- **延迟成本**：你真正需要的特性更晚上线，因为你忙于投机性的那个。
- **携带成本**：未使用的能力让系统对*每个人、每一天*都更难理解和修改，直到它最终被使用或移除。
- **修复成本**：当投机特性猜错时（常见情形），你还要再付一次钱来修或删它。

携带成本是人们忘记的那一个。一个未使用的扩展点不是免费的地产；它是对理解力的永久税。每个读者都得琢磨它是干嘛的，每次重构都得保留它，每个测试都得考虑它。

## YAGNI 禁止什么

- 在出现超过一个真实实现之前，建造插件系统、基类、注册表或通用框架。
- 为一个假设中的第二个实现添加接口或抽象。
- 添加当前没有调用方使用的字段、参数、配置开关或扩展钩子。
- 泛化一个函数去处理永远不会出现的输入。

## YAGNI 不禁止什么

这是最常被搞错的部分。YAGNI 针对的是*投机性特性*，而不是工程纪律。它不为跳过以下事项开脱：

- **测试**：它们保护让你能安全推迟决策的行为。
- **错误处理**：针对真实会发生的失败，尤其在边界处。
- **类型安全**：公共 API 和模块边界上的类型提示降低、而不是增加未来变更的成本。
- **资源清理**：文件、连接、锁和事务的上下文管理器是正确性问题，不是投机。
- **重构**：保持代码可塑正是让 YAGNI 可行的东西。
- **已发布接口的 API 稳定性**：对公共 API、持久化 schema 或外部协议，预先设计稳定的边界不是投机；日后变更它的代价是真实且已知的。

判别标准：这项工作服务的是*已知的、当下的*需求（正确性、安全、一个真实的消费者），还是在为*想象的、未来的*需求对冲？前者是好的工程；只有后者才是 YAGNI 禁止的。

## YAGNI 要求可塑的代码

只有当日后改变主意很便宜时，YAGNI 才是安全的。如果代码没有测试、抗拒重构，推迟决策就会变成永久的缺口；当真正需要那个能力时，你会怕得不敢加。所以 YAGNI、[tdd.md](./tdd.md)（或后补测试）和重构是一个组合：测试和重构保持代码可塑，而可塑的代码让"以后再定"成为理性策略，而不是欠债的借口。

## 与其他原则的相互作用

- [kiss.md](./kiss.md)：YAGNI 移除投机性特性；KISS 移除你保留的特性中的不必要复杂度。
- [rule-of-three.md](./rule-of-three.md)：去重版本的"等到真正需要时再做"。
- SOLID 的开闭原则（见 [solid.md](./solid.md)）把人拉向扩展点；YAGNI 说只有在真实变化出现时才建它们。
