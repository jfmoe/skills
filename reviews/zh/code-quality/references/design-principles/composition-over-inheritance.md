# 组合优于继承

优先通过更小的部分——对象、函数、委托——来组装行为，而不是从基类继承实现。这里的措辞是"优先"，而不是"禁止"：继承有其真实用途，但它被过度用作默认的复用机制，而组合通常是更灵活、耦合更低的选择。

## 为什么继承会造成耦合

类继承把两件逻辑上分离的事情捆绑在一起：*实现复用*（子类获得基类的代码）和*子类型可替换性*（子类的实例被期望能在任何期望基类的地方工作；见
[里氏替换](./solid.md)）。当你仅仅为了复用代码而继承时，你也继承了遵守基类契约的义务，以及对基类每一处变更的暴露。

这会产生*脆弱基类*问题：对基类的一次修改可能以难以察觉的方式破坏子类，因为子类依赖的是基类的内部行为，而不仅仅是它的公共接口。深层次的层级结构会放大这一点：行为被摊散在多个层级上，理解一个类就意味着要读完它的所有祖先。

组合的耦合更松散。持有一个协作者的对象只依赖该协作者的接口，并且可以在不改变自身类型的情况下替换协作者。组合式设计的变更半径更小、更局部。

## 继承确实合适的场景

- **真实的 is-a 关系且契约稳定。** 当子类型确实是基类的特化，并且能够兑现基类的每一项承诺（里氏替换）时，继承忠实地建模了这种关系。异常层级是一个干净的例子：`class TimeoutError(NetworkError)` 表达了一种被 `except` 子句使用的真实分类。
- **框架扩展点。** 许多框架被设计为通过继承其提供的基类来扩展（一个 Django 视图、一个 `unittest.TestCase`）。此时继承是框架指定的钩子，抗拒它只会徒增摩擦而毫无收益。
- **小而稳定的抽象接口。** 从一个定义了狭窄契约（且几乎没有实现）的抽象基类继承，更接近接口实现而非实现继承，耦合也更少。

共同点是：当你需要可替换性且契约稳定时才继承，而不是仅仅想复用几个方法时。

## Protocol 作为 ABC 继承的替代

当目标是"这个对象必须支持这些方法"时，Python 的 `typing.Protocol` 让你可以结构化地表达这一点，而无需建立继承关系。一个类只要拥有正确的方法就满足一个 Protocol；它不需要从 Protocol 继承。这给了你接口的类型检查收益，以及[接口隔离](./solid.md)那种狭窄的、由调用方定义的契约的收益，却没有共享基类的耦合。当你只需要描述一种能力而非共享实现时，优先选择 Protocol 而非抽象基类继承。另见 [dependency-inversion](./dependency-inversion.md)。

## 常见错误

- **一刀切地禁止继承。** 当框架期望子类化、或者存在真实稳定的 is-a 关系时仍使用组合，只会增加样板代码并违背工具的脾性。
- **透传样板。** 组合可能退化为一个把十几个方法转发给所持有协作者的对象。如果几乎每个方法都是一行委托，请重新考虑：也许这个包装器通过收窄或适配接口而物有所值，也许调用方应该直接持有那个协作者。
- **为复用而伪造子类型。** 为了拿到几个辅助方法而继承，然后把其他方法覆写成空操作或 `NotImplementedError`，这违反了里氏替换，也是组合（或一个普通辅助函数）才是正确工具的经典信号。
