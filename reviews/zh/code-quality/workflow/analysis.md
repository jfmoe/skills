# 分析模式：代码质量

咨询模式。用户问的是*该做什么*，而不是*哪里错了*。没有待评分的 diff。帮助推理一个设计或重构决策并收敛到一个结论。

## 触发条件

- 设计讨论：“这个该怎么组织？”“这个行为应该放在哪里？”
- 模式选择：“哪个模式合适：策略还是就写一个函数？”“这里值得用工厂吗？”
- 重构规划：如何拆分一个模块、如何安排安全的重构顺序，或者是否要重构。
- 范式选择：命令式 vs 函数式核心、面向对象 vs 面向数据、状态机何时值得引入。
- 原则应用：DRY、KISS、YAGNI 或 SOLID 在具体情境中如何起作用。

## 步骤

1. 理解设计问题及其上下文：预期会有什么变化、现在哪里痛、存在哪些约束。缺少关键事实时先提问。
2. 阅读与主题相关的参考文档（`skills/code-quality/references/design-principles`、`design-patterns/`、`refactoring/`、`programming-paradigms/`），让讨论使用项目的真实词汇。
3. 给出选项及其权衡。大多数设计问题有多个站得住脚的答案；展示现实可行的那些，以及各自在变更成本、可读性和复杂性上的代价。
4. 在原则、模式和范式确实适用的地方用它们来组织讨论，但只有在其所管理的变化点确实存在时才援引某个模式。
5. 收敛。针对*这个*上下文推荐一个选项并解释原因，或者提出一个聚焦的澄清问题。不要只做罗列。

## 输出

对话式、以推荐为导向。没有僵化的发现格式。摆出备选方案，指出决定取舍的那个权衡，然后给出推荐。篇幅与问题相称。

## 停止规则

- 仅咨询。不修改文件。
- 不要把原则或模式硬套到不适合的情境上；没有模式往往就是正确答案。
- 不要仅凭相似性就推荐抽象。
- 由用户决定。如果讨论变成了实际工作，建议改用快速或完整审查，而不是悄悄切换模式。
