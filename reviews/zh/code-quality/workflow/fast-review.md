# 快速审查：代码质量

默认模式。开发完成后或针对小型 diff 的快速、高信号自检。以少量、有把握的发现为优化目标，而不是覆盖率。倾向于放过足够好的代码。

## 触发条件

- 未指定模式时的默认选择。
- 日常开发自检。
- 小型 diff、单个文件或聚焦的 PR。

## 前置条件

- 只读。不要修改代码。
- 有具体的目标：一个 diff、一个文件或一组明确指定的文件。如果范围是整个仓库或不明确，请用户缩小范围，或将该请求按完整审查处理。

## 步骤

1. 建立项目事实。阅读最近的 `AGENTS.md`/`CLAUDE.md`，并略读变更周边的代码，了解既有结构和约定。
2. 扫描 diff 或指定的代码。优先使用 `git diff`、`git show`、`rg` 和 `nl`，而不是把所有内容都加载进来。
3. 对照检查目标：
   - 错误的抽象：通用帮助函数、基类或参数集合与真实的变化不匹配。
   - 薄包装：只是给一个表达式改名、不增加任何语义边界的函数或类。
   - 知识重复：同一条*规则、schema 或决策*出现在两处（而不仅仅是看起来相似的代码）。
   - 明显的坏味道：混合多个阶段的过长函数、分散/全局状态、基本类型偏执、霰弹枪式修改。
   - 模式误用：在尚不存在变化点的地方套用了某个有名模式。
   - 无测试的重构：对没有测试覆盖的代码做改变行为的重组。
4. 输出 0-5 条发现，信号最强的排前面。零发现是有效结果。

## 输出格式

发现优先、紧凑。每条发现一个块：

```text
- [severity, confidence] path:line Title
  Fact: observable evidence.
  Impact: why it matters, change cost, readability, correctness, testability.
  Recommendation: smallest sufficient change.
```

除非有真实信号，否则跳过 Open Questions 和 Notes。不要为了凑够五条而填充。

## 停止规则

- 不要为了满足某条原则而编造发现。干净的 diff 得到零发现。
- 不要在未证明两处共享同一知识的情况下，以 DRY 为由推荐抽象。
- 不要自动重构或重组；只报告，不改写。
- 不要升级为完整审查，只有当 diff 明显值得更深入的工作时才建议升级。
- 上限 5 条发现；保留最有分量的。
- 跳过格式化工具或 linter 能机械发现的任何问题。
