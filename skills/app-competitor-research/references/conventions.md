# 记录规范

## 客观性

- 只写能观察到的行为，界面上的文字原文照录，包括错别字和标点。
- 不用评价词，比如"流畅""卡顿""好用""简洁"。手感类特性拆成可观察的行为来记：放大倍数、有没有动画、动画是什么形态、多长时间、会不会回弹、点击区域怎么划分、手势触发后的结果。
- 观察不到的项不推测，写进 `untested.md`，写明原因和需要的配合。
- 证据只能证明一部分时，写清边界，比如"不能据此判定……""只验证了本次样本"。
- 第三方说法（评论、社区帖子）原文引用，注明来源和日期，不收录昵称，只作为"某人说了什么"的事实。
- 界面上的说明文案只算文案，不等于行为已经验证。

## 事实条目

事实文件是给后续做分析的 agent 读的，格式以读取成本低为准：每条事实独占一行，按编号 grep 一行就能读到；同一文件内固定不变的信息写在开头，不在每行重复。

文件开头写一段"本文件口径"：来源（通常是真机）、App 版本、设备、测量方式和精度。个别行例外时，在该行的事实里注明。

表格五列：

| 列 | 内容 |
|---|---|
| 编号 | `<前缀>-<三位序号>`。编号分配后不再变动；删除的条目保留编号，标注"已撤回" |
| 设备 | `iPhone`、`iPad`；两端都验证过且一致时写 `通用` |
| 主题 | 不超过 12 个字的中性主题词，如"双击行为""跨页配对"，用来生成索引 |
| 事实 | 观察到的行为、界面原文、测量值。只在口径和文件开头不同时说明 |
| 路径 | 从 App 首页出发的操作路径，如 `书架 → 长按封面 → 菜单` |

- 证据不写进表格。证据文件名以编号开头，`ls screenshots/*/<前缀>/<编号>*` 就能找到；录像文件名也以编号开头。
- 结构相同的多条结果（比如每个素材的导入结果、模式 × 方向的组合）合并成一张矩阵表，挂在一条事实下面，矩阵里不再重复写口径。矩阵等辅助表的行首如果是编号，写成代码格式（如 `RD-010`）：`build_indexes.py` 会把行首是裸编号的表格行当成一条新事实。
- `build_indexes.py <app 目录>` 会生成 `INDEX.md`（每条事实一行：编号、设备、主题、所在文件）和 `screenshots/index.md`（给人看的可点击证据）。新增或修改事实后都重新运行一次。读事实时先看 INDEX.md，再按编号 grep。

## 文件组织

产物描述竞品**现在是什么样**，按主题组织；调研过程（轮次、会话、任务书、谁测的、哪次补的）只留在 `_process/`。每次新增内容，都放进它所属的主题位置，不在文件末尾按轮次另开一节。

**措辞**：判断标准只有一条：一个没参与调研、看不到任何过程材料的读者，能不能看懂每个指代，并核实每个说法。看不懂、核实不了的，就是过程残留。常见的有四类：
- **过程指代**："本轮""本次任务""任务书""简报"、R1／R2 这类轮次标签、执行工具名（PUA、Codex）。要说明时间就写日期，要说明条件就写具体条件（"F01 已读到末页时""Komga 书库解析完成后"），要引用别处的结果就写事实编号。
- **经过叙述**："后来补测""续测时""此前记为……，现改为……"。只写现在确认的结果；被推翻的旧结论不留痕，需要的话由事实编号的"已撤回"体现。
- **审核与分工**："经审核""主导方""用户要求"。保留决定本身（比如"未设置隐私密码"），不写谁定的、哪次定的。
- **不落地的含糊话**："暂时""应该没问题""以后再测"。改成 `untested.md` 里写明配合方式的一行，或者写出实际的边界。

删改前，先列出这段话包含的每一个事实：测试条件、测量值、界面原文、设备状态、证据边界。每个事实都要换成上面的写法保留下来，只删掉包着它的过程话。照录的 App 界面文字一律不改。

各文件的组织方式：

| 文件 | 组织方式 |
|---|---|
| `<app>/README.md` | 只有四节：概况（名称、bundle ID、开发者、版本）；环境（调研日期范围、设备与系统版本、权限授予情况、会员或试用状态、测试内容来源）；覆盖情况表（模块、文件、编号前缀、事实条数、验证过的设备、主要缺口）；设备上的测试数据现状（调研留下的、会影响后续测试的状态，比如被隐藏的书、累计的阅读统计、清过的缓存） |
| `screens.md` | 开头是页面层级树；正文按 App 的一级区域分节（比如书架、阅读器、服务、统计、我的、系统界面与外部页面），每节一张五列表。新页面插进所属区域的表里，编号照常递增，文件里的编号不要求连续。长篇页面原文放在末尾的"页面原文"一节；第二台设备的逐条对照表放在"设备对照"一节 |
| `settings.md` | 按设置所在的页面分节（比如书架设置、全局阅读设置、单本设置、我的、服务器表单）。每个设置项一行：选项全集、当前值；有付费锁时写锁的标记和文案；验证过效果的，写一句结论并引用证明它的事实编号。付费标记的含义、设备范围这类每行都相同的说明，写在文件口径里；没验证的效果记进 `untested.md`。不另开"效果"表 |
| `features/<模块>.md` | 按模块检查清单的小节分节，比如阅读器按 core-reader 的 7 节。后来补上的结果放进对应主题的那一节；矩阵表紧跟在它所属的事实后面 |
| `untested.md` | 只列**现在仍然存在**的缺口，按需要的配合分组：需要用户操作；需要用户授权或提供资源；工具测不了；待第二台设备复核；范围限制（样本或分支没覆盖到）。表头为：项目 \| 已有结果 \| 缺什么、为什么 \| 需要的配合。"已有结果"写事实编号。补上一个缺口，就删掉那一行；只补上一部分，就把那一行缩成剩下的部分 |

## 设备维度

- 截图按 `screenshots/<iphone|ipad>/<前缀>/` 分目录存放；iPad 截图文件名在编号后加 `-ipad`。
- 第二台设备上做对照时，写进 `screens.md` 的"设备对照"一节，列为：SC 编号、一致 / 有差异 / 未找到、差异原文；截图按命名规则存放，不进表格。布局不同就算"有差异"。
- 一端已经测过的行为，另一端只做复核：一致就把设备列改成 `通用` 并补上截图；不一致就新增一条事实。

## 证据

- 文件名用 `<编号>-<英文短描述>.jpg`，一条事实有多张图时加 `-a`、`-b`；iPad 截图在编号后加 `-ipad`；动效关键帧用 `<编号>-<描述>-seg<N>-start|mid|end.jpg`。
- 截图用 `wda shot <路径>` 直接存进调研目录。默认尺寸等于屏幕的 point 尺寸；要看清小字，另存一张 `--crop` 放大的局部图。
- 文件名要和图片内容一致。
- 截图、录像、测试素材都用 Git LFS 提交：`git lfs track 'research/*/screenshots/**/*.jpg' 'research/*/screenshots/**/*.png' 'research/*/recordings/**' 'research/test-materials/out/**'`。录像是动效事实唯一的原始证据；素材入库的是实际使用的那一版，重新生成不保证字节一致。
- 录像放在 `recordings/<前缀>/`，文件名以编号开头。测量的明细（每段的时间戳等）放在 `screenshots/<设备>/<前缀>/<前缀>-measurements.md`，事实里只写结论值。
