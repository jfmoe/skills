# 实施说明模板

复制到 `<本地目录>/implement-brief.md`，替换全部尖括号内容；不适用的行直接删除。工人每张票都会读这份文件，只写它从仓库里拿不到的内容。

```markdown
# 实施说明（架构师调度）

你由架构师（另一个 pane 中的 Agent）调度。用户原话：“<授权原话>”。据此，用户授权架构师决定：<范围，例如架构取舍、须经用户确认的文本、付费额度>。授权范围内，架构师的裁定等同用户确认（包括项目规定须经用户确认的事项），记录中写明批准方。

## 执行规则

- 按 <项目的 Agent 指引与工作流约定路径> 执行，门槛顺序为 <确切门槛名>。实施技能自带的测试要求由 <对应门槛> 满足。
- 提交到 <分支>；推送、打标签、发布、安装到用户环境，都由用户决定。
- 付费运行：<授权来源与每票常设额度>。额度是为了让运行有目的，必要时可以超出，并写明原因。
- <须经用户确认的文本类别> 的改动：把原文、拟改文本和理由写入 `<本地目录>/issue-<N>/prompt-change.md`，随结构检查点一起交架构师确认。其他文档按最终实现直接修改，随提交评审。
- 只在隔离环境中实测；<不能触碰的用户环境> 保持原样。

## 结构检查点

本票行为全部实现、目标用例通过后，把改动摘要写入 `<本地目录>/issue-<N>/checkpoint.md`，然后停下等架构师评审。<昂贵的验证，例如浏览器回归、手动实测、性能测量> 放到评审之后。摘要只写评审需要的决策，每项附 file:line：
- 模块与接口；
- 共享资源（缓存、连接、预算）的所有者和全部构造点；
- 迁移与索引；
- 新增的抽象或依赖；
- 删除的兼容代码；
- 偏离规格的地方。

已取得的验证只列日志路径。改动不超过 <200> 行、只涉及一个模块时，可以跳过检查点。

## 设计取向

选干净的方案：设想需求一开始就存在时会怎么设计，不在旧设计上打补丁；先减后加。兼容只为 <确实需要兼容的对象，逐条写明> 保留，其余旧接口与旧数据直接按新设计处理。遇到不合理的设计，提出干净的方案；超出本票范围的，附证据回报。

## 停下回问

遇到以下情况，把问题、证据（file:line）和你倾向的选项写进 `<本地目录>/issue-<N>/question-<序号>.md`，然后结束本轮回复。回问只走文件，选项弹窗会阻塞调度：
- 规格没覆盖的取舍，或规格与代码事实冲突；
- 需要改动其他票的范围，或需要规格没写的迁移；
- 查不出根因的失败，或需要破坏性操作；
- 发现与本票无关、但影响主路径的问题。

本票之外的既有测试或检查挡住门槛、修复不改生产行为时，直接修复，并在汇总中列出。

## 完成

在 Issue 写一条汇总评论，只写结论、提交、验证与证据路径，附 <项目要求的记录，例如操作日志>，然后关闭票；规格 Issue 由架构师关闭。最后一条回复只写：提交号、实际通过的验证、遗留项。
```
