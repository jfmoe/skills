# 实施说明模板

复制到 `<本地目录>/implement-brief.md`，替换全部尖括号内容，不适用的行直接删除。路径一律写绝对路径。工人每张票都会读这份文件，只写它从仓库里拿不到的内容。

```markdown
# 实施说明（架构师调度）

你由架构师（另一个 pane 中的 Agent）调度。用户已授权架构师做实施中的全部决定，架构师的裁定等同用户确认；要问用户的事都问架构师。本票的文件写在 `<主仓库绝对路径>/<本地目录>/` 下以票号命名的目录里，下称票目录。

- **约定**：按 <项目 Agent 指引路径> 执行，检查命令为 <确切命令>。
- **原则卡**：开工前读 <原则卡绝对路径>，实施中遵守；与项目规范冲突时以项目规范为准。其中的可选度量由架构师在规格收尾时安排，票内不跑。本票范围之外的不合理设计，附证据记入完成汇报的遗留项，继续做本票。
- **实施技能里要问用户的地方**：都改为问架构师。`tdd` 要确认的测试接缝，结合规格的 Testing Decisions 和本票的具体情况拟定：与规格定的接缝一致时直接写测试，有出入时按“回问”交架构师确认后再写。
- **提交与评审**：结构变化与行为变化分开提交。需要先为改动腾位置时，先做一个 `refactor` 提交；测试和实现合为一个 `feat` 或 `fix` 提交。之后运行 `code-review`，固定点取你开工时的 HEAD，规范来源加入原则卡和 <测试分层规则绝对路径>，并说明：项目规范优先于这两份；新增或改动的测试按后者的三条规则和它 `references/review.md` 里的 Smells 表检查。评审出的修正按性质分开追加提交：改变行为或测试预期值的进 `fix` 或 `test` 提交，纯结构的进 `refactor` 提交。
- **tracker**：票的评论和关闭由架构师负责，你只读票。
- **回问**：遇到规格没覆盖的取舍、规格与代码事实冲突、对规格的设计有异议（附替代方案和代价）、需要改动其他票的范围、项目文档要求用户确认的事项、查不出根因的失败或破坏性操作时，把问题、证据（file:line）和你倾向的选项写入票目录的 `question.md`，然后结束本轮回复。回问只走文件，选项弹窗会阻塞调度。
- **检查点**：派票消息要求检查点时，在目标用例通过后、耗时的验证之前，把改动摘要写入票目录的 `checkpoint.md` 并停下等评审。摘要列出模块与接口、新增的抽象或依赖、删除的代码、偏离规格的地方，每项附 file:line。
- **完成**：提交到当前分支，推送由用户决定。最后一条回复只写：各提交号及其类型、分支名、改动汇总、实际通过的验证、遗留项。

## 在 worktree 中实施时

- 只在自己的 worktree 里改代码、跑检查；主工作树的文件保持原样。
- 开工时确认工作区干净，按派票消息给出的分支名，从最新的 <集成分支> 新建分支。
- `code-review` 之后、回报完成之前，把 <集成分支> 的最新提交合并进本票分支，并重跑检查。合并进集成分支由架构师完成。
```
