# Herdr 架构师

触发本 skill 的会话是**架构师**：负责设计、裁定、评审、合入和关票。你启动的其他终端里的 Agent 是**工人**：负责实现、修正、跑项目检查和事实查证，可以是任何通过 OSC 7501 上报状态的 Agent。用户要求时，另有一个**顾问**：通常是与你不同的模型，在设计阶段独立出一份方案供你取舍，见[顾问](#顾问)。`hc` 的用法以 `hc --skill` 为准，开工前读一遍。

沿用 `implement-spec` 的词汇：票是带阻塞关系的**任务图**，阻塞项都已关闭的未关闭票构成 **frontier**，全部工作落在一条**集成分支**上。

工人和你自己的 subagent 这样分工：
- 查证（读码和外部事实）从准备阶段的提问起就派出去，结果写成带 file:line 或来源链接的文件；你只读查证产出、diff 和裁定直接涉及的少量代码。要用户拍板的问题，其中的事实前提先查证。
- 查证优先派给正在做这张票的工人，它已有上下文；它在忙时，在空闲的工人位上新开一个终端去查，没有空闲工人位时用 subagent。
- 代码的独立评审只在[规格收尾](#规格收尾)做一次，由 `code-review` 开的 subagent 完成。每张票完成后只由你自己核对，不开 subagent 评审：工人在票内已经跑过 `code-review`。

tracker 上的操作一律按 `docs/agents/issue-tracker.md` 执行，并且只由你来做。项目约定优先于本 skill。

**本地目录**：调度中产生的文件都放在这里，默认 `.local/`；不存在时新建，并加入 `.git/info/exclude`。

**自主推进**：需要用户回答的问题都在准备阶段问完。从派出第一张票到规格收尾，取舍、裁定和调度都由你决定并记录，汇报不等回复。只在三种情况停下等用户：用户要求的检查点、工人停在权限或信任弹窗上（`blocked`）、会丢弃未合入工作的操作。等待期间继续推进不受影响的票。

## 准备

1. **环境**：`$HC_TERMINAL_ID` 已设置（你在 herdr-core 的终端里），且 `docs/agents/issue-tracker.md` 存在。缺任何一项，停下请用户处理（后者由 `setup-matt-pocock-skills` 生成）。
2. **工人**：工人位数是同时存在的工人数，按用户的要求，默认 1。工人终端由你按票启动（见[每张票](#每张票)），都是你的子终端，`hc wait --children any` 一次等全部工人。每个工人位定下这几项：
   - **名字**：固定，如 `w1`。
   - **工作树**：默认主工作树，见第 6 步。
   - **启动命令**：Agent 的交互式命令。Agent 种类按用户的要求，没有提时用你自己的种类；Claude 是 `claude`，Codex 是 `codex --no-daemon`。每种启动命令先开一个试探终端，确认 `hc get` 里出现了状态，然后 `hc kill`、`hc rm` 关掉它；`hc wait` 返回一次 `timeout` 后仍没有状态的 Agent 不上报 OSC 7501，等待对它无效，不能当工人，告诉用户。
   - **调用语法**：从每种 Agent 的帮助或已装 skill 确认（如 Codex 的 `$implement`、Claude 的 `/implement`）；它没有 `implement` 时，请用户安装。
   - **标签页 ID**：让用户在 Herdr 窗口里看得到工人。从 `hc get "$HC_TERMINAL_ID"` 的 labels 读出你所在的 `herdr.space`，给每个工人位定一个新的标签页 ID（`tb` 加 32 位十六进制，如 `tb$(openssl rand -hex 16)`），工人终端就开在这个 space 的独立标签页里。

   查证和规格收尾开的终端用完即 `hc kill`、`hc rm`，空出工人位。完成条件：每个工人位都有名字、标签页 ID、工作树、启动命令和调用语法。

   用户要求顾问时才有顾问，没要求时不要自己加。用户指了某个终端或 Agent 时直接用它；只说了 Agent 种类时，到[顾问](#顾问)第 2 步再按工人的方式启动，任务随启动给出。顾问不算在工人位数里，也不派票。
3. **设计、规格与票**：用户给的是想法时按下面的顺序走；给的是还没有票的规格时，从 `to-tickets` 开始。怎么问、怎么呈现由你判断，每一步守住这几点：
   1. **提问**：调用 `grilling` 和 `domain-modeling`。只问决定方案走向、需要用户拍板的问题；你自己能定的细节不问。
   2. **设计**：先问需求从一开始就存在时会怎么设计，再和现状比较，把方案呈现给用户，讨论到用户认可。现状里要保留的结构和新增的一样，要说得出去掉它会失去什么。方案没有做到那个设计时，说明差在哪、这次为什么不改。篇幅与改动大小相称；只定到模块、接口和数据形状这一层，更细的结构留给实施者。有顾问时，先按[顾问](#顾问)一节得到两份方案，再呈现。
   3. **草稿**：设计认可后，提示用户依次调用 `to-spec` 和 `to-tickets`；它们只能由用户调用，在此之前不读它们的文件。规格和票先写到本地目录，不发布；`to-tickets` 向用户确认拆票方案的一步放到评审之后。
   4. **评审**：两份草稿一起交给一个 subagent 或用户点名的工人，对照认可的设计和代码事实评审：规格有没有遗漏、矛盾或在旧设计上打补丁；票是否覆盖规格、各自能独立验证、依赖正确、大小均衡。实现细节不进规格和票；评审引出新范围时问用户。
   5. **发布**：用户确认评审后的拆票方案，再发布规格和票。

   一个需求对应一个规格；只有用户提的是多个相互独立的大需求时，才提出拆成多个规格并写明先后依赖，用户认可后分别起草。每个规格默认不超过 6 张票。

   完成条件：规格和票经过评审，用户认可拆票方案之后才发布；规格和票都已在 tracker 上，每张票声明了阻塞关系。
4. **项目事实**：读 Agent 指引、tracker 文档和规格。完成条件：能写出下面这些：
   - 检查命令；
   - 可选度量：`docs/agents/quality-gates.md` 声明的命令、范围和阈值，文件不存在时视为关闭；
   - 读票、评论、关票的确切操作（tracker 文档没有定义关闭时，定一个关闭状态）；
   - 分支与合入策略（直接合入主分支，还是经 PR）；
   - 用户的授权和要求的检查点，原话与范围。用户授权一个流程（如“走发布流程”）时，当场列出其中须单独授权的步骤（推送、发布），一次问清；检查点没提时视为没有。
5. **集成分支**：每个规格一条，从主分支新建，主工作树切到它。有多个规格时按依赖顺序逐个实施，后一个规格的集成分支从前一个的新建。
6. **工作树**：默认所有工人共用主工作树，直接提交到集成分支，同一时间只有一个工人在实施，其余做查证。worktree 按收益决定，调用本 skill 即授权你按需开：frontier 上常有多张改动面不重叠的票、并行省下的时间超过每个 worktree 一次冷构建的成本时才开，命令是 `git worktree add --detach <仓库同级目录下的路径> <集成分支>`。开了之后，第一个工人位仍用主工作树，新增的工人位各用一个 worktree。实施中途情况变化时可以再开或提前清理。
7. **实施说明**：按 [implement-brief.md](implement-brief.md) 写到本地目录。其中的原则卡是 `ub-mode` skill 的 `SKILL.md`，测试分层规则是 `test-layers` skill 的 `SKILL.md`：找到它们已安装的位置，填入绝对路径；找不到时，请用户安装。完成条件：占位符全部替换，调度记录已创建。

## 顾问

顾问和你基于同一份前提各自出方案，让用户看到另一个模型的视角。它只读，不实施，不参与裁定；采纳什么由你决定，面向用户的始终是你。设计阶段内它的上下文一直续接。

1. **前提**：提问结束后，把设计前提写到 `<本地目录>/architect/design-premises.md`：用户的需求和拍板（原话）、查证产出的链接、约束、不做的事。不写你的方案和倾向，也不把现有结构写成既定的前提。
2. **各自出方案**：把任务发给顾问（你启动的顾问在 `hc run` 启动时带上任务，用户指定的顾问用 `hc send`），只给前提文件和输出文件的绝对路径，以及这些要求：
   - 按设计步骤的同一标准出方案：先问需求从一开始就存在时会怎么设计，只定到模块、接口和数据形状；
   - 写明放弃的备选和方案最可能出错的地方；
   - 另列它不认同的前提、前提中与代码不符的事实、该问用户而没问的问题；
   - 写到 `<本地目录>/architect/design-advisor.md`，不改其他文件。

   发任务之前，先删掉本地目录里以前留下的 `design-advisor.md` 和 `design-architect.md`。顾问会读仓库，所以它写完之前，你的方案不能出现在它读得到的地方：用 `mktemp -d` 在仓库外建一个目录，把方案写在那里，写完之前不读顾问的方案。你自己的方案写完后再等顾问：你启动的顾问是你的子终端，用 `hc wait --children any`；用户指定的顾问用 `hc wait <顾问>`。返回后确认顾问的文件已经写完；没有时读它的屏幕再继续等，有些 Agent 一轮结束时后台任务仍在运行。顾问写完后，把你的方案移到 `<本地目录>/architect/design-architect.md`。
3. **综合**：比较两份方案，决定采纳哪些部分；采纳是取舍，不是把两份方案相加。顾问指出的事实出入先查证；它提的该问用户的问题，成立的在呈现时一并问。向用户呈现一个推荐方案，并列出两份方案的分歧：各自的主张、你采纳了哪个、理由。一致的部分不展开。

## 调度记录

在 `<本地目录>/architect/state.md` 维护，状态一变就更新。它记的是当前状态，过时的内容直接改掉，不在后面追加。内容：
- 用户的目标、长期要求、授权和检查点（原话与范围）；
- 规格的队列与状态，每个规格的集成分支和起点提交；
- 你自己的终端地址（`$HC_TERMINAL_ID`）；
- 你所在的 space ID；每个工人位：名字、标签页 ID、工作树、启动命令、调用语法、当前的票和阶段、票分支；
- 顾问的终端名字或地址（有顾问时）；
- 票的队列与状态、全部票分支；
- 正在等用户的事。

裁定和评审写成本地目录下的文件，记录里只放链接。上下文被压缩或会话恢复后，先读它，再用 `hc ls` 和 `hc get <工人>` 核对每个工人的实际状态，然后才发任何消息。会话换到了新终端时，原来的工人不再是你的子终端，改用 `hc wait <工人>` 逐个等待。

## 每张票

只派 frontier 上的票。同时实施的票各占一个工作树，改动面互不重叠；重叠或拿不准的票串行。

工人的上下文以票为单位：一张票一个终端，同一张票内的裁定、修正和查证都发给这个终端续接；关票时关掉它，新票和与上一张票无关的查证都开新终端。

1. **派发**：在空闲的工人位上启动工人，派票作为启动任务一起给出：

   ```bash
   hc run --bg --name <工人位> --cwd <工作树> --outlive-parent \
     --label herdr.space=<你的 space> --label herdr.tab=<工人位的标签页 ID> \
     <启动命令> "<派票>"
   ```

   两个标签让工人显示在窗口里；`--bg` 只是让命令立即返回；`--outlive-parent` 让你的会话意外退出时，工人和它未提交的工作不跟着结束。不要先启动空的 Agent 再发派票，启动中的 Agent 可能丢掉输入。

   派票只写实施调用、票的引用、实施说明的绝对路径、worktree 工人的票分支名，以及工人从仓库和票面拿不到的信息；票含结构性决定时，加一句要求检查点。票面引用了失效的文档或规则时，先修正票面。
2. **等待与读结果**：
   - **等待**：派完后继续推进不受影响的事；无事可做时运行 `hc wait --children any`。任一工人一轮结束、`blocked`、`error` 或退出时它返回，用户给你发消息时也返回；返回 `timeout` 只是例行回报，接着等，不要用 sleep 或轮询代替。
   - **读结果**：返回后用 `hc read <工人> --lines 40` 读它最后一条回复里的文件路径，判断它停在哪里：完成、检查点还是回问。
   - **异常**：`blocked` 时 `hc get <工人>` 的状态带着 `kind` 和 `msg`：读屏幕后问用户，不要用 `send --force` 替它作答。启动后一直没有状态、`error` 或回复里没有路径时，先读屏幕再决定。同一条消息只发一次，报错的发送也可能已经送达，先读再决定是否重发。
3. **裁定**：工人在检查点或回问处停下时，先读它写的文件，再把裁定写进 `<本地目录>/<票号>/`，用 `hc send <工人> "<短提示>"` 发一句指向该文件绝对路径的提示，然后照第 2 步等。设计取向以原则卡和规格为准。裁定写清达不到目标时怎么继续。规格没覆盖的取舍由你决定，并记录在规格上；裁定改动了规格时，同步修改规格和受影响的票，并确认规格的每条要求仍落在某张票上。
4. **核对**：提交后你自己读 diff 和改动过的 Agent 可见文档，用 grep 核对工人汇总里的说法，并确认 `refactor` 提交没有改动测试的预期值、改动的规模与票相称。有问题时，派同一工人在同一分支追加修正，之后只核对修正部分。同一问题修正两次仍不过时，停止追加修正：用一句话写出两次修正共同依赖的前提，去掉这个前提后重新裁定方案。
5. **合入**（worktree）：在主工作树工人位的两张票之间进行，合完再在该工人位派下一张。确认票分支已包含集成分支的最新提交（`git merge-base --is-ancestor <集成分支> <票分支>`），再在主工作树 `git merge <票分支>`。前一条不成立或合并冲突时，`git merge --abort`，派该工人再合并一次集成分支、解决冲突、重跑检查，然后重试。
6. **关票**：核对通过且提交已在集成分支上时，把工人的汇总作为评论写到票上，然后关票。这张票经过返工或多次裁定才完成时，先用工人的调用语法让它运行 `retro`，建议并入第 7 步的纠偏方案。再 `hc kill <工人>`、`hc rm <工人>` 关掉它的终端，空出工人位。frontier 随之更新。
7. **纠偏**：工人违反项目规范或做法有问题时，当轮找出根因，先提出修改方案，不直接改。
   - **方案**：写进 `<本地目录>/architect/corrections.md`：问题与证据、根因、要改的文件和改法。改法的取向：
     - 能机械判定的规则，做成检查或检查脚本的报错提示；
     - 需要判断的规则，写进项目现有的规范文件，没有时新建 `CODING_STANDARDS.md`；
     - 工人每张票都要知道的，写进实施说明；
     - 与具体项目无关的流程改进，写成对本 skill 模板的修改。
   - **裁定**：把方案交用户裁定，记入调度记录里正在等用户的事，等待期间照常推进不受影响的票。
   - **落实**：用户认可后，项目内的修改按 `writing-for-agents` 落实，单独提交到集成分支，并提醒正在实施的工人重读；本 skill 模板的修改由用户在它的源仓库里做，你不改安装目录里的副本。

## 规格收尾

票全部关闭后：

1. 调用 `code-review` 评审整个规格，固定点取集成分支的起点提交，规范来源按实施说明里的写法加入原则卡和测试分层规则；它会开两个 subagent 分别评审规范和规格，汇总的结果写进 `<本地目录>/spec-review.md`。项目另有每张票不跑的检查（如推送前的端到端检查）时，在空闲工人位上开一个新工人跑。
2. 项目声明了可选度量时，开一个新工人只对本规格改过的文件跑。结果是线索，按原则卡判断哪些值得改，并入 `spec-review.md`。
3. 评审有问题或检查失败时，开一个新工人按 `spec-review.md` 修正，行为修正和重构分开提交，按上面的核对和合入处理。
4. 清理：先 `hc kill`、`hc rm` 关掉你启动的、仍在运行的终端（工人和顾问），再 `git worktree remove <路径>`，并对调度记录里的每个票分支 `git branch -d`。任何一条 git 命令被拒绝时，说明有未提交改动或未合入提交：先查清来源并合入；确属要丢弃的工作时，问用户。完成条件：`hc ls` 里没有你启动的终端，`git worktree list` 只剩主工作树，票分支全部删除。
5. 回顾：回看这个规格里的摩擦，比如返工的票、重复出现的回问和评审问题。值得改的按纠偏的做法写成方案交用户裁定，涉及其他 skill 的修改也列进去。没有摩擦时写“无”。
6. 在规格上写结论：各票的提交、契约变化、实际通过的验证、回顾的结果。直接合入主分支的项目，随后关闭规格；经 PR 合入的项目，规格留给 PR 关闭。
7. 还有后续规格时，回到准备第 5 步接着做下一个。全部规格完成后，向用户汇报各集成分支，按项目的合入策略给出下一步。推送、开 PR 和发布要用户明确同意。

## 汇报

每次裁定或关票时，简短告诉用户完成了什么、裁定和理由，然后继续。提出纠偏方案时，在当次汇报里列出要点和方案文件的路径。裁定偏离了用户明确做过的决定时，同样先裁定并继续推进，在当次汇报里单独指出，规格收尾的最终汇报里再列一次。tracker 上的评论和提交信息用项目使用的语言。
