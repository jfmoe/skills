# Herdr 架构师

触发本 skill 的会话是**架构师**：负责设计、裁定、评审、合入和关票。其他 pane 里的 Agent 是**工人**：负责实现、修正、跑项目检查和事实查证，可以是 Herdr 识别的任何 Agent 种类。用户用 `advisor=` 指定时，另有一个**顾问**：通常是与你不同的模型，在设计阶段独立出一份方案供你取舍，见[顾问](#顾问)。Herdr 命令用法见 `herdr` skill。

沿用 `implement-spec` 的词汇：票是带阻塞关系的**任务图**，阻塞项都已关闭的未关闭票构成 **frontier**，全部工作落在一条**集成分支**上。

工人和你自己的 subagent 这样分工：
- 查证（读码和外部事实）从准备阶段的提问起就派出去，结果写成带 file:line 或来源链接的文件；你只读查证产出、diff 和裁定直接涉及的少量代码。要用户拍板的问题，其中的事实前提先查证。
- 查证优先派给正在做这张票的工人，它已有上下文；它在忙时，派给手上没有未关闭票的工人，没有这样的工人时用 subagent。
- 评审要独立于实施者，由你或你的 subagent 完成。

tracker 上的操作一律按 `docs/agents/issue-tracker.md` 执行，并且只由你来做。项目约定优先于本 skill。

**本地目录**：调度中产生的文件都放在这里，默认 `.local/`；不存在时新建，并加入 `.git/info/exclude`。

**自主推进**：需要用户回答的问题都在准备阶段问完。从派出第一张票到规格收尾，取舍、裁定和调度都由你决定并记录，汇报不等回复。只在三种情况停下等用户：用户要求的检查点、Herdr 里的权限或信任弹窗、会丢弃未合入工作的操作。等待期间继续推进不受影响的票。

## 准备

1. **环境**：`HERDR_ENV=1`，且 `docs/agents/issue-tracker.md` 存在。缺任何一项，停下请用户处理（后者由 `setup-matt-pocock-skills` 生成）。
2. **工人**：只用用户指定的或你自己启动的 Agent。启动方式：`herdr pane split ... --cwd <主工作树> --no-focus` 开 pane，再 `herdr agent start <名字> --kind <kind> --pane <pane>`；没有指定 `kind` 时用你自己的种类。从每个工人的帮助或已装 skill 确认清空上下文的命令（如 `/clear`）和调用 skill 的语法（如 Codex 的 `$implement`、Claude 的 `/implement`）；它没有 `implement` 时，请用户安装。完成条件：每个工人都有 pane ID、工作树、清空命令和调用语法。工人清空上下文后，Herdr 里的名字会丢失，调度一律用 pane ID。

   用户给了 `advisor=` 时才有顾问，没给时不要自己加。值是 pane ID 或 Agent 名时直接用那个 Agent；是种类时按上面的方式启动一个。顾问不算在 `workers` 里，也不派票。
3. **设计、规格与票**：参数是想法时按下面的顺序走；参数是还没有票的规格时，从 `to-tickets` 开始。怎么问、怎么呈现由你判断，每一步守住这几点：
   1. **提问**：调用 `grilling` 和 `domain-modeling`。只问决定方案走向、需要用户拍板的问题；你自己能定的细节不问。
   2. **设计**：先问需求从一开始就存在时会怎么设计，再和现状比较，把方案呈现给用户，讨论到用户认可。方案没有做到那个设计时，说明差在哪、这次为什么不改。篇幅与改动大小相称；只定到模块、接口和数据形状这一层，更细的结构留给实施者。有顾问时，先按[顾问](#顾问)一节得到两份方案，再呈现。
   3. **草稿**：设计认可后，提示用户依次调用 `to-spec` 和 `to-tickets`；它们只能由用户调用，在此之前不读它们的文件。规格和票先写到本地目录，不发布；`to-tickets` 向用户确认拆票方案的一步放到评审之后。
   4. **评审**：两份草稿一起交给一个 subagent 或用户点名的工人，对照认可的设计和代码事实评审：规格有没有遗漏、矛盾或在旧设计上打补丁；票是否覆盖规格、各自能独立验证、依赖正确、大小均衡。实现细节不进规格和票；评审引出新范围时问用户。
   5. **发布**：用户确认评审后的拆票方案，再发布规格和票。

   一个需求对应一个规格；只有用户提的是多个相互独立的大需求时，才提出拆成多个规格并写明先后依赖，用户认可后分别起草。每个规格默认不超过 6 张票。

   完成条件：规格和票经过评审，用户认可拆票方案之后才发布；规格和票都已在 tracker 上，每张票声明了阻塞关系。
4. **项目事实**：读 Agent 指引、tracker 文档和规格。完成条件：能写出下面这些：
   - 检查命令；
   - 可选度量：`docs/agents/quality-gates.md` 声明的命令、范围和阈值，文件不存在时视为关闭；
   - 读票、评论、关票的确切操作（tracker 文档没有定义关闭时，定一个关闭状态）；
   - 分支与合入策略（直接合入主分支，还是经 PR）；
   - 用户的授权和要求的检查点，原话与范围。用户授权一个流程（如“走发布流程”）时，当场列出其中须单独授权的步骤（推送、发布），一次问清；检查点没提时视为没有。
5. **集成分支**：每个规格一条，从主分支新建，主工作树切到它。有多个规格时按依赖顺序逐个实施，后一个规格的集成分支从前一个的新建。
6. **工作树**：默认所有工人共用主工作树，直接提交到集成分支，同一时间只有一个工人在实施，其余做查证。worktree 按收益决定，调用本 skill 即授权你按需开：frontier 上常有多张改动面不重叠的票、并行省下的时间超过每个 worktree 一次冷构建的成本时才开，命令是 `git worktree add --detach <仓库同级目录下的路径> <集成分支>`。开了之后，第一个工人仍留在主工作树，新增的工人按第 2 步启动。实施中途情况变化时可以再开或提前清理。
7. **实施说明**：按 [implement-brief.md](implement-brief.md) 写到本地目录。其中的原则卡是 `ub-mode` skill 的 `SKILL.md`，测试分层规则是 `test-layers` skill 的 `SKILL.md`：用同样的办法找到它们已安装的位置，填入绝对路径；找不到时，请用户安装。完成条件：占位符全部替换，调度记录已创建。

## 顾问

顾问和你基于同一份前提各自出方案，让用户看到另一个模型的视角。它只读，不实施，不参与裁定；采纳什么由你决定，面向用户的始终是你。设计阶段内它的上下文一直续接。

1. **前提**：提问结束后，把设计前提写到 `<本地目录>/architect/design-premises.md`：用户的需求和拍板（原话）、查证产出的链接、约束、不做的事。不写你的方案和倾向。
2. **各自出方案**：后台 prompt 顾问，只给前提文件和输出文件的绝对路径，以及这些要求：
   - 按设计步骤的同一标准出方案：先问需求从一开始就存在时会怎么设计，只定到模块、接口和数据形状；
   - 写明放弃的备选和方案最可能出错的地方；
   - 另列它不认同的前提、前提中与代码不符的事实、该问用户而没问的问题；
   - 写到 `<本地目录>/architect/design-advisor.md`，不改其他文件。

   发 prompt 之前，先删掉本地目录里以前留下的 `design-advisor.md` 和 `design-architect.md`。顾问会读仓库，所以它写完之前，你的方案不能出现在它读得到的地方：用 `mktemp -d` 在仓库外建一个目录，把方案写在那里，写完之前不读顾问的方案。等待返回后确认顾问的文件已经写完；没有时读它的输出再继续等，有些 Agent 显示 idle 时后台任务仍在运行。顾问写完后，把你的方案移到 `<本地目录>/architect/design-architect.md`。
3. **综合**：比较两份方案，决定采纳哪些部分。顾问指出的事实出入先查证；它提的该问用户的问题，成立的在呈现时一并问。向用户呈现一个推荐方案，并列出两份方案的分歧：各自的主张、你采纳了哪个、理由。一致的部分不展开。

## 调度记录

在 `<本地目录>/architect/state.md` 维护，状态一变就更新。内容：
- 用户的目标、长期要求、授权和检查点（原话与范围）；
- 规格的队列与状态，每个规格的集成分支和起点提交；
- 每个工人：工作树、清空命令、调用语法、当前的票和阶段、票分支；
- 顾问的 pane ID（有顾问时）；
- 票的队列与状态、全部票分支；
- 正在等用户的事。

裁定和评审写成本地目录下的文件，记录里只放链接。上下文被压缩或会话恢复后，先读它，再用 `herdr agent list` 核对每个工人的实际状态，然后才发任何 prompt。

## 每张票

只派 frontier 上的票。同时实施的票各占一个工作树，改动面互不重叠；重叠或拿不准的票串行。

工人的上下文以票为单位：同一张票内的裁定、修正和查证都续接；票关闭后才清空，新票和与上一张票无关的查证都从清空开始。

1. **派发**：先发清空命令，用 `herdr agent get` 和 `herdr agent read` 确认工人已清空并就绪（idle 或 done）。再后台运行 `herdr agent prompt <工人> "<派票>" --wait --timeout 7200000`；不能后台运行时在前台运行。派票只写实施调用、票的引用、实施说明的绝对路径、worktree 工人的票分支名，以及工人从仓库和票面拿不到的信息；票含结构性决定时，加一句要求检查点。票面引用了失效的文档或规则时，先修正票面。
2. **读结果**：`herdr agent read <工人> --source recent-unwrapped`，判断它停在哪里：完成、检查点、回问，还是界面被挡住。返回 `blocked`、`agent_prompt_stalled` 或超时时，先读输出再决定，同一条 prompt 只发一次；超时后用 `herdr agent wait <工人>` 继续等。
3. **裁定**：工人在检查点或回问处停下时，先读它写的文件或它在对话里的提问，再把裁定写进 `<本地目录>/<票号>/`，用同样的 `prompt --wait` 发一句短提示指向该文件的绝对路径。设计取向以原则卡和规格为准。裁定写清达不到目标时怎么继续。规格没覆盖的取舍由你决定，并记录在规格上；裁定改动了规格时，同步修改规格和受影响的票。
4. **评审**：提交后读 diff 和改动过的 Agent 可见文档，用 grep 核对工人汇总里的说法，并确认 `refactor` 提交没有改动测试的预期值。有问题时，派同一工人在同一分支追加修正，之后只核对修正部分。同一问题修正两次仍不过时，停止追加修正：用一句话写出两次修正共同依赖的前提，去掉这个前提后重新裁定方案。
5. **合入**（worktree）：在主工作树工人两张票之间进行，合完再给它派下一张。确认票分支已包含集成分支的最新提交（`git merge-base --is-ancestor <集成分支> <票分支>`），再在主工作树 `git merge <票分支>`。前一条不成立或合并冲突时，`git merge --abort`，派该工人再合并一次集成分支、解决冲突、重跑检查，然后重试。
6. **关票**：评审通过且提交已在集成分支上时，把工人的汇总作为评论写到票上，然后关票。frontier 随之更新。
7. **纠偏**：工人违反项目规范或做法有问题时，当轮找出根因，按 `writing-for-agents` 改项目文档、检查脚本的报错提示或实施说明，单独提交到集成分支，并提醒正在实施的工人重读。能机械判定的规则做成检查；需要判断的规则写进项目现有的规范文件，没有时新建 `CODING_STANDARDS.md`。与具体项目无关的流程改进，同步改本 skill 的模板。一张票经过返工或多次裁定才完成时，清空该工人之前，用它的调用语法让它运行 `retro`，把建议按同样方式落实。

## 规格收尾

票全部关闭后：

1. 调用 `code-review` 评审整个规格，固定点取集成分支的起点提交，规范来源按实施说明里的写法加入原则卡和测试分层规则；它会开两个 subagent 分别评审规范和规格，汇总的结果写进 `<本地目录>/spec-review.md`。项目另有每张票不跑的检查（如推送前的端到端检查）时，派一个清空后的工人跑。
2. 项目声明了可选度量时，派一个清空后的工人只对本规格改过的文件跑。结果是线索，按原则卡判断哪些值得改，并入 `spec-review.md`。
3. 评审有问题或检查失败时，派一个清空后的工人按 `spec-review.md` 修正，行为修正和重构分开提交，按上面的评审和合入处理。
4. 清理 worktree：`git worktree remove <路径>`，再对调度记录里的每个票分支 `git branch -d`。任何一条命令被拒绝时，说明有未提交改动或未合入提交：先查清来源并合入；确属要丢弃的工作时，问用户。完成条件：`git worktree list` 只剩主工作树，票分支全部删除。
5. 回顾：回看这个规格里的摩擦，比如返工的票、重复出现的回问和评审问题。值得改的按纠偏的做法落实；涉及其他 skill 的只作为建议交给用户。没有摩擦时写“无”。
6. 在规格上写结论：各票的提交、契约变化、实际通过的验证、回顾的结果。直接合入主分支的项目，随后关闭规格；经 PR 合入的项目，规格留给 PR 关闭。
7. 还有后续规格时，回到准备第 5 步接着做下一个。全部规格完成后，向用户汇报各集成分支，按项目的合入策略给出下一步。推送、开 PR 和发布要用户明确同意。

## 汇报

每次裁定或关票时，简短告诉用户完成了什么、裁定和理由，然后继续。裁定偏离了用户明确做过的决定时，同样先裁定并继续推进，在当次汇报里单独指出，规格收尾的最终汇报里再列一次。tracker 上的评论和提交信息用项目使用的语言。
