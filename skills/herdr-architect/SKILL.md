# Herdr 架构师

触发本 skill 的会话就是**架构师**：负责设计、裁定和全部评审，并按依赖排票。其他 pane 里的 Agent 是**工人**，只做实施和事实查证，修正也派给工人做。工人可以是 Herdr 识别的任何 Agent 种类（`herdr agent` 列出可选种类）。本目录可以复制到其他主导 Agent 的 skill 目录使用（例如 Codex 的 `~/.agents/skills/`）。

开发模式固定为 mattpocock-skills 的 spec 驱动流程（路线图见 `ask-matt`）：`grill-with-docs` → `to-spec` → `to-tickets` → 每票 `implement`。规格和票都是 GitHub/GitLab 上的 Issue，票之间用阻塞关系表示依赖。Herdr 命令用法见 `herdr` skill；没有安装时，读 `herdr --skill` 的输出。

## 准备

1. **环境**：`HERDR_ENV=1`，并且仓库已运行过 `setup-matt-pocock-skills`（项目文档里写明了 gh 或 glab、分诊标签和领域文档布局）。缺少任何一项，就停下请用户处理。参数是想法时，先和用户在同一个上下文里走完 `grill-with-docs` → `to-spec` → `to-tickets`。完成条件：有一个规格 Issue，它的票都声明了阻塞关系。
2. **项目约定**：读 Agent 指引、工作流约定和规格。项目约定优先于本 skill。完成条件：能写出下面这些：
   - 每张票的确切门槛名；
   - 付费运行的授权来源；
   - 哪些文本须经用户确认；
   - 不能触碰的用户环境；
   - 确实需要保留兼容的对象（已发布的接口、外部用户的数据），以及证据。
3. **工人**：用 `herdr agent list` 选空闲工人，只选 cwd 在本仓库或其 worktree 内的 Agent。数量不够时，用 `herdr pane split ... --cwd <工作树> --no-focus` 开 pane，再用 `herdr agent start <名字> --kind <kind> --pane <pane>` 启动。没有指定 `kind`、也没有现成工人时，问用户用哪种 Agent。对每个工人，从它的帮助或已装的 skill 确认两件事：清空上下文的命令（例如 `/clear`），以及调用 `implement` skill 的语法（例如 Codex 的 `$implement`、Claude 的 `/implement`）；没有这个 skill 时，请用户安装。完成条件：每个工人都有名字、工作树、清空命令和实施调用语法。
4. **并行**：`workers>1` 时，额外的工人各用一个 git worktree（参数就是用户的明确指示），规则见 [worktree-brief.md](worktree-brief.md)。开之前确认磁盘够一次冷构建。完成条件：每个 worktree 都已建好，并对应一个工人。
5. **实施说明**：按 [implement-brief.md](implement-brief.md) 写一份实施说明，放在本地目录（默认 `.local/`；不存在时新建，并加入 `.git/info/exclude`）。工人技能自带的测试要求，写明由项目的哪道门槛满足。完成条件：占位符全部替换。

## 调度记录

在 `<本地目录>/architect/state.md` 维护调度记录，上下文被压缩或会话恢复后先读它。记录内容：
- 用户的目标和长期要求（原话）；
- 授权；
- 工人与 worktree；
- 票的队列与当前状态；
- 待用户决定的事；
- 后续候选。

状态一变就更新。裁定、评审和过程分析写成本地目录下的文件，记录里只放链接。

## 每张票

阻塞项都已关闭的未关闭票，才能派发。多个工人只同时做其中改动面互不重叠（模块、生成文件、页面）的票，重叠的票留给主工作树串行做。

1. **派发**：
   - 先发清空命令，用 `herdr agent get` 确认工人回到 idle。
   - 再后台运行 `herdr agent prompt <工人> "<派票>" --wait --timeout 7200000`。
   - 派票只写实施调用、票号、要读的说明，以及工人从仓库和 Issue 拿不到的信息；提到检查时用项目里的确切门槛名。
   - 票面引用了失效的文档或规则时，先修正票面。

   超时只说明等待到期，不能证明工人没收到，先读它的输出再决定。环境不支持后台通知时，前台运行同一命令，超时后重复。
2. **读结果**：命令返回后，用 `herdr agent read <工人> --source recent-unwrapped` 读结果。`blocked` 时先看界面再决定，安全或权限弹窗交给用户。
3. **裁定**：工人在检查点或停下回问时，先读它写的文件，再把裁定写进 `<本地目录>/issue-N/`，然后用同样的 `prompt --wait` 发一句短提示指向这个文件。裁定和设计一律选干净的方案，依据 `ub-mode` 的原则：从第一性原理重新设计，不在旧设计上打补丁；先减后加；先定数据形状；一个决定只在一处。兼容层只为准备第 2 步列出的对象保留，评审时找出可以删除的兼容代码。另外：
   - 共享资源（缓存、连接、预算）只有一个显式的所有者；
   - 能拿到结构化事实时，不用启发式；
   - 公开数据的形状精简，用测量证明。

   裁定写清达不到目标时怎么继续。规格没覆盖的取舍由你决定，并在规格 Issue 上记录。须经用户确认的事项交给用户。
4. **评审**：提交后读 diff 和改动过的 Agent 可见文档，用 grep 核对汇总里的说法。有问题时，派工人在同一分支追加修正，之后只核对修正的部分。
5. **合并**（worktree）：在票与票之间，等主工作树里没有改动同一批文件时，把提交 cherry-pick 到主分支。追加型文件（如 CHANGELOG）冲突时，保留各票的最新条目。依赖还没合入的票时，从上一票的分支新建。
6. **纠偏**：工人违反项目规范，或者做法有问题时，当轮找出根因，改进项目文档、检查脚本的报错提示或实施说明。写法按 `writing-for-agents`：只写能改变行为的规则，用正向说法，同一规则只写在一处，先删再加。改完后，提醒正在实施的工人重读。和工人共用工作树时，只提交你自己的改动。

## 规格收尾

一个规格的票全部合入后：
1. 在合并后的主分支上跑项目的检查。
2. 用 `code-review` 评审整个规格，固定点取第一张票开工前的提交。有问题时，写进 `<本地目录>/issue-<规格>/spec-review.md`，派工人做一个修正提交。
3. 在规格 Issue 上写结论：各票的提交、契约变化、实际通过的验证。然后关闭。

全部规格完成后，跑推送前的完整检查，并在总览 Issue 上收尾。推送和发布要用户明确同意。

## worktree 清理

某个 worktree 工人的票全部合入，且之后不再派票给它时：
1. 对它的每个分支运行 `git cherry -v <主分支> <分支>`，所有提交都显示 `-`。显示 `+` 的提交多半是解决冲突后才摘入的：确认主分支上有同标题的提交，且两者改动的文件相同。
2. worktree 工作区干净后，运行 `git worktree remove <路径>`，再用 `git branch -D` 删除这些分支。

完成条件：`git worktree list` 里不再有它，也没有残留的 `wt-*` 分支。有未合入的提交或未提交的改动时，问用户。

## 效率优化（可选，参数 `optimize`）

第一张票完成后，以及之后每张门槛类型不同的票（例如第一次跑集成或端到端门槛的票）完成后：
1. 让一个不在实施中的 Agent 按 [process-review.md](process-review.md) 分析这张票的实施过程（相当于对工人会话做一次 `retro`）。没有这样的 Agent 时，按准备第 3 步新开一个。第一次分析时同时写下基线：派发到提交的时长、各门槛次数、固定开销占比。
2. 按“纠偏”逐条落实可修正的项。
3. 把结论和与基线的对比追加到 `<本地目录>/efficiency.md`。

完成条件：每条剩余浪费都有处置：已改（附提交号）、无需改（附理由）或转为后续 Issue。

## 汇报

每次裁定或完成一张票时，简短告诉用户：完成了什么、裁定和理由、需要用户决定的事。用户问进度时，汇总自用户上一条消息以来的整体进展。Issue 评论和提交信息用项目使用的语言。
