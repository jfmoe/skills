# Herdr 架构师

触发本 skill 的会话是**架构师**：负责设计、裁定、评审、合入和关票。其他 pane 里的 Agent 是**工人**：负责实现、修正、跑项目检查和事实查证，可以是 Herdr 识别的任何 Agent 种类。Herdr 命令用法见 `herdr` skill。

沿用 `implement-spec` 的词汇：票是带阻塞关系的**任务图**，阻塞项都已关闭的未关闭票构成 **frontier**，全部工作落在一条**集成分支**上。

工人和你自己的 subagent 这样分工：
- 查证（读码和外部事实）从准备阶段的 grill 起就派出去，结果写成带 file:line 或来源链接的文件；你只读查证产出、diff 和裁定直接涉及的少量代码。要用户拍板的问题，其中的事实前提先查证。
- 查证优先派给正在做这张票的工人，它已有上下文；它在忙时，派给手上没有未关闭票的工人，没有这样的工人时用 subagent。
- 评审要独立于实施者，由你或你的 subagent 完成。

tracker 上的操作一律按 `docs/agents/issue-tracker.md` 执行，并且只由你来做。项目约定优先于本 skill。

**自主推进**：需要用户回答的问题都在准备阶段问完。从派出第一张票到规格收尾，取舍、裁定和调度都由你决定并记录，汇报不等回复。只在三种情况停下等用户：用户要求的检查点、Herdr 里的权限或信任弹窗、会丢弃未合入工作的操作。等待期间继续推进不受影响的票。

## 准备

1. **环境**：`HERDR_ENV=1`，且 `docs/agents/issue-tracker.md` 存在。缺任何一项，停下请用户处理（后者由 `setup-matt-pocock-skills` 生成）。
2. **工人**：只用用户指定的或你自己启动的 Agent。启动方式：`herdr pane split ... --cwd <主工作树> --no-focus` 开 pane，再 `herdr agent start <名字> --kind <kind> --pane <pane>`；没有指定 `kind` 时用你自己的种类。从每个工人的帮助或已装 skill 确认清空上下文的命令（如 `/clear`）和调用 skill 的语法（如 Codex 的 `$implement`、Claude 的 `/implement`）；它没有 `implement` 时，请用户安装。完成条件：每个工人都有名字、工作树、清空命令和调用语法。
3. **规格与票**：参数是想法时，先在本会话依次完成 `grill-with-docs` → `to-spec` → `to-tickets`；参数是还没有票的规格时，只做 `to-tickets`。这三个 skill 只能由用户调用，你调不动：每进入一个阶段，先读本 skill 同级目录的 `../<名字>/SKILL.md` 全文，再逐条照做，包括其中调用其他 skill 和等用户确认的环节。读不到文件时，请用户手动调用。票数从少：每张票是一条能独立验证的完整路径，每个规格默认不超过 3 张。完成条件：用户认可拆票方案之后才发布；规格和票都已在 tracker 上，每张票声明了阻塞关系。
4. **项目事实**：读 Agent 指引、tracker 文档和规格。完成条件：能写出下面这些：
   - 检查命令；
   - 读票、评论、关票的确切操作（tracker 文档没有定义关闭时，定一个关闭状态）；
   - 分支与合入策略（直接合入主分支，还是经 PR）；
   - 需要保留兼容的对象（问用户，没有就记为无）；
   - 用户的授权和要求的检查点，原话与范围。用户授权一个流程（如“走发布流程”）时，当场列出其中须单独授权的步骤（推送、发布），一次问清；检查点没提时视为没有。
5. **集成分支**：从主分支新建，主工作树切到它。
6. **工作树**：默认所有工人共用主工作树，直接提交到集成分支，同一时间只有一个工人在实施，其余做查证。worktree 按收益决定，调用本 skill 即授权你按需开：frontier 上常有多张改动面不重叠的票、并行省下的时间超过每个 worktree 一次冷构建的成本时才开，命令是 `git worktree add --detach <仓库同级目录下的路径> <集成分支>`。开了之后，第一个工人仍留在主工作树，新增的工人按第 2 步启动。实施中途情况变化时可以再开或提前清理。
7. **实施说明**：按 [implement-brief.md](implement-brief.md) 写到本地目录（默认 `.local/`；不存在时新建，并加入 `.git/info/exclude`）。完成条件：占位符全部替换，调度记录已创建。

## 调度记录

在 `<本地目录>/architect/state.md` 维护，状态一变就更新。内容：
- 用户的目标、长期要求、授权和检查点（原话与范围）；
- 集成分支和它的起点提交；
- 每个工人：工作树、清空命令、调用语法、当前的票和阶段、票分支；
- 票的队列与状态、全部票分支；
- 正在等用户的事。

裁定和评审写成本地目录下的文件，记录里只放链接。上下文被压缩或会话恢复后，先读它，再用 `herdr agent list` 核对每个工人的实际状态，然后才发任何 prompt。

## 每张票

只派 frontier 上的票。同时实施的票各占一个工作树，改动面互不重叠；重叠或拿不准的票串行。

工人的上下文以票为单位：同一张票内的裁定、修正和查证都续接；票关闭后才清空，新票和与上一张票无关的查证都从清空开始。

1. **派发**：先发清空命令，用 `herdr agent get` 和 `herdr agent read` 确认工人已清空并就绪（idle 或 done）。再后台运行 `herdr agent prompt <工人> "<派票>" --wait --timeout 7200000`；不能后台运行时在前台运行。派票只写实施调用、票的引用、实施说明的绝对路径、worktree 工人的票分支名，以及工人从仓库和票面拿不到的信息；票含结构性决定时，加一句要求检查点。票面引用了失效的文档或规则时，先修正票面。
2. **读结果**：`herdr agent read <工人> --source recent-unwrapped`，判断它停在哪里：完成、检查点、回问，还是界面被挡住。返回 `blocked`、`agent_prompt_stalled` 或超时时，先读输出再决定，同一条 prompt 只发一次；超时后用 `herdr agent wait <工人>` 继续等。
3. **裁定**：工人在检查点或回问处停下时，先读它写的文件或它在对话里的提问，再把裁定写进 `<本地目录>/<票号>/`，用同样的 `prompt --wait` 发一句短提示指向该文件的绝对路径。设计取向以实施说明为准，兼容层只为准备阶段记下的对象保留。裁定写清达不到目标时怎么继续。规格没覆盖的取舍由你决定，并记录在规格上。
4. **评审**：提交后读 diff 和改动过的 Agent 可见文档，用 grep 核对工人汇总里的说法。有问题时，派同一工人在同一分支追加修正，之后只核对修正部分。同一问题修正两次仍不过时，停止追加修正，重新裁定方案。
5. **合入**（worktree）：在主工作树工人两张票之间进行，合完再给它派下一张。确认票分支已包含集成分支的最新提交（`git merge-base --is-ancestor <集成分支> <票分支>`），再在主工作树 `git merge <票分支>`。前一条不成立或合并冲突时，`git merge --abort`，派该工人再合并一次集成分支、解决冲突、重跑检查，然后重试。
6. **关票**：评审通过且提交已在集成分支上时，把工人的汇总作为评论写到票上，然后关票。frontier 随之更新。
7. **纠偏**：工人违反项目规范或做法有问题时，当轮找出根因，按 `writing-for-agents` 改项目文档、检查脚本的报错提示或实施说明，单独提交到集成分支，并提醒正在实施的工人重读；与具体项目无关的流程改进，同步改本 skill 的模板。一张票经过返工或多次裁定才完成时，清空该工人之前，用它的调用语法让它运行 `retro`，把建议按同样方式落实。

## 规格收尾

票全部关闭后：

1. 调用 `code-review` 评审整个规格，固定点取集成分支的起点提交；它会开两个 subagent 分别评审规范和规格，汇总的结果写进 `<本地目录>/spec-review.md`。项目另有每张票不跑的检查（如推送前的端到端检查）时，派一个清空后的工人跑。
2. 评审有问题或检查失败时，派一个清空后的工人按该文件做一个修正提交，按上面的评审和合入处理。
3. 清理 worktree：`git worktree remove <路径>`，再对调度记录里的每个票分支 `git branch -d`。任何一条命令被拒绝时，说明有未提交改动或未合入提交：先查清来源并合入；确属要丢弃的工作时，问用户。完成条件：`git worktree list` 只剩主工作树，票分支全部删除。
4. 在规格上写结论：各票的提交、契约变化、实际通过的验证。直接合入主分支的项目，随后关闭规格；经 PR 合入的项目，规格留给 PR 关闭。
5. 向用户汇报集成分支，按项目的合入策略给出下一步。推送、开 PR 和发布要用户明确同意。

## 汇报

每次裁定或关票时，简短告诉用户完成了什么、裁定和理由，然后继续。tracker 上的评论和提交信息用项目使用的语言。
